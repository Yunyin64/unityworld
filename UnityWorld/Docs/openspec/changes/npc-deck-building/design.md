## Context

当前 NPC Deck 的**来源**已明确（功法节点解锁的 Card 实例 + 其他来源），但从候选池到战斗卡组的**构建流程**尚未定义。同时，战斗核心机制文档中 Mana 系统的数值参数（转化频率、转化量、元素分配）写为"待定"，实际上这些参数都应属于 NPC 的动态属性。

当前状态：
- 功法系统已定义 Card 解锁机制（CultivationPoint → Card 实例入候选池）
- 战斗引擎已实现 Tick 驱动 + 待发槽 + 对拼流程
- NPC 数据结构中尚无"战斗卡组"与"战斗属性"的明确字段
- Card 是实例，同一 DefineID 可有多份

## Goals / Non-Goals

**Goals：**
- 定义 NPC 从候选卡池 → 战斗卡组的完整构建流程
- 定义当前阶段的选卡策略（随机），并预留"实战水平"机制的设计接口
- 将战斗系统中所有"NPC 相关的动态数值参数"明确为 NPC 属性，建立清单
- 定义卡组内卡牌排序规则

**Non-Goals：**
- 不实现"实战水平"的模拟推演系统（仅定义概念和接口预留）
- 不实现战斗参数属性的具体计算公式（属性值如何受道途/功法/境界影响）
- 不涉及玩家 UI 操作的卡组编辑界面设计
- 不改动战斗引擎的对拼/待发槽核心逻辑

## Decisions

### Decision 1：候选池与战斗卡组是两个独立概念

**选择**：NPC 持有一个**候选卡池**（CardPool，所有拥有的 Card 实例），战斗时从中选取子集组成**战斗卡组**（BattleDeck）。

**理由**：
- 候选池只增长（获得新卡就加入），战斗卡组按需构建
- 伤势卡在战斗中临时塞入 BattleDeck，不进入 CardPool
- 这个分离让"选卡策略"有了明确的操作空间

**替代方案**：所有卡直接就是卡组 → 否决，因为 SP 约束意味着不可能全带。

### Decision 2：当前选卡策略为随机，预留策略接口

**选择**：选卡策略抽象为一个可替换的决策模块。当前实现为随机策略；未来替换为"实战水平"策略。

**随机策略**：从 CardPool 中随机选卡，逐张加入 BattleDeck 直到 SP 用满或无法再加。

**实战水平概念（未来）**：
- 生成 K 种随机卡组方案
- 每种方案与"标准模型 NPC"对战 N 轮
- 选胜率/表现最优的方案
- K 和 N 本身是 NPC 属性（代表 NPC 的推演能力/战斗智慧）

**理由**：随机策略几乎零成本，足够支撑早期开发。策略接口让未来替换无需重构。

### Decision 3：卡牌排序由玩家/AI 决定，引擎只读取

**选择**：BattleDeck 中卡牌的排列顺序是一个有意义的决策维度（影响待发槽挤出顺序等），由构建者决定，战斗引擎按顺序读取。

**当前阶段**：随机排序。
**玩家操纵的 NPC**：玩家在 UI 中手动排列。
**未来 AI**：实战水平模拟时同时优化排序。

### Decision 4：战斗参数属性化——"NPC 战斗属性"清单

**选择**：以下参数从战斗系统常量中移出，定义为 NPC 身上的动态属性：

| 属性 | 说明 | 来源（影响因素） |
|------|------|-----------------|
| ManaConvertInterval | 灵元转化频率（每 N Tick 转化一次） | 境界、功法、天赋 |
| ManaConvertAmount | 每次转化的灵元数量 | 境界、功法、天赋 |
| ManaElementDistribution | 灵元的元素分配方案 | 道途、功法、所在 Tile 的五行浓度 |
| SimulationDepth | 实战水平推演深度（K × N） | 境界、阅历（未来） |

**理由**：这些数值因 NPC 而异，不可能是系统常量。战斗引擎只是一个执行引擎，所有参数从 NPC 身上读取。这与设计哲学中"Tag 是世界语言、一切能力是自身属性投影"的核心思想一致。

**属性值如何确定**：本次不定义计算公式。属性值的来源（道途/功法/境界/天赋/环境）由各自的系统在未来实现时注入。当前阶段给默认值即可。

### Decision 5：Card 是实例，卡组中允许重复 DefineID

**选择**：确认 Card 是实例化对象，候选池和卡组中可以有多张同一 DefineID 的卡。

**理由**：多本功法可能解锁同一张卡；其他来源也可能给予重复卡。实例化设计已在 TCA 体系中确立（ActionData 是运行时实例）。

## Risks / Trade-offs

- **[随机策略可能产生荒谬卡组]** → 当前阶段可接受，NPC 的"笨"本身也是世界真实感的一部分。未来实战水平系统是正式解法。
- **[战斗属性清单可能不完整]** → 先建立框架和清单概念，后续发现新的"应该是 NPC 属性"的参数时随时追加。
- **[实战水平系统的性能开销]** → 未来实现时需要关注。但因为战斗是离线模拟（同步跑完），模拟推演本质上就是多跑几场 CombatScene，架构上天然支持。
