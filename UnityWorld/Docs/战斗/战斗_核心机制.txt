## 一、设计原则

1. 离线模拟（Offline Simulation）
   战斗是"发生在一瞬间"的事件。CombatScene 从外部接收参数，
   同步跑完整场战斗，输出结果，不依赖任何全局 Tick 或协程。

2. 纯实例，无单例
   CombatScene 是完全独立的对象，不挂靠 WorldMgr/NpcMgr 的
   生命周期。多场战斗可以并发存在，互不干扰。

3. 大世界隔离
   战斗内的所有状态变化（HP损耗、伤势等）记录在 CombatNpc
   上，不直接修改大世界的 Npc/StatBlock。结算后由调用方凭
   CombatResult 决定如何回写。

4. 构筑决定胜负
   玩家的核心决策在战前选卡构筑，战斗本身自动推演。
   乐趣来自构筑验证与事后复盘。

---

## 二、体验循环

  选卡构筑 → 战斗(自动) → 伤势累积 → 疗伤/修养 → 再战
     ▲                                              │
     └──────────────────────────────────────────────┘

  战斗中受伤产生的「伤势卡」持续到战后，需要疗伤去除。
  伤势卡挤占卡组空间，使后续战斗力下降，
  形成"冒险继续 vs 回去疗伤"的战略决策。

---

## 三、核心属性

  HP（体魄决定）
    伤害缓冲区。HP清零不意味着战败，而是产生伤势。
    清零后恢复50%继续战斗。

  SP（ Tribune决定）
    卡组空间上限 = 真正的"生命线"。
    NPC 默认拥有 5 + ψ意调整值 的可用空间。
    卡的 Cost 总和超过 SP → 判负。

  MP（蓝条）
    战斗资源池。定期转化为带元素属性的灵元(Mana)，
    供高级卡牌使用。

## 四、战斗驱动模型：Tick + 独立计时器

  核心变化：不再是回合制顺序出招，
  而是每张卡有独立的CD计时器，并行推进。

  每个 Tick：
    0. Modifier 结算（详见 → 战斗/战斗_Modifier系统.txt）
       ├─ Modifier 持续时间倒计时
       ├─ Modifier 的 OnTick 类 TCA 触发
       └─ 移除到期的 Modifier
       （此后卡牌 CD 推进时，Modifier 的数值修正 B 已生效/失效）
    1. 所有存活NPC的所有卡，计时器+1
    2. 检查哪些卡CD到了
    3. CD到的卡按类型处理：
       ├─ 效果卡（无攻防数值）→ 直接结算效果，重置计时器
       └─ 攻防卡（有攻击/盾/防数值）→ 尝试推入本方待发槽
            ├─ 待发槽未满 → 入槽
            │    └─ 检查：双方待发槽都有卡？→ 立刻对拼！
            └─ 待发槽已满 → 挤出最前面的卡
                 └─ 被挤出的卡 → 直击对方本体（全额伤害）
                      新卡进入待发槽
    4. 每Tick检查SP溢出 → 卡占用 > SP → 判负

## 五、待发槽机制

  每个NPC有一个待发槽，默认上限1张（预留可扩展）。
  NPC固定Target，所有卡打向同一个敌人。

  节奏示意：

  甲: Card1(CD=3)  ░░▓→待发槽[Card1]
                                      等...等...
  乙: Card1(CD=5)  ░░░░▓→待发槽[Card1]  ← 来了！
                                      
  此时：甲Card1 vs 乙Card1 → 对拼！

  ──────────────────────────────────────────

  另一种情况：乙太慢了

  甲: Card1(CD=3)  ░░▓→待发槽[Card1]
                                      等...等...
  甲: Card2(CD=4)  ░░░▓→要进待发槽！但满了！
                   → Card1 被挤出 → 直击乙本体！
                   → Card2 进入待发槽

  战略意义：
    CD短的卡 → 频繁出招 → 容易挤出旧卡打脸
    CD长的卡 → 数值高 → 但可能防不住连续攻击
    你的出卡节奏 vs 对手的出卡节奏 = 战斗核心

## 六、对拼规则

  对拼触发：双方待发槽都有卡的那一刻，立刻结算。

  统一框架：比数值大小
    数值高者赢 → 效果由赢方卡类型决定
    数值相同 → 平局，两卡消耗，无伤害

  ── 赢方效果（取决于赢方卡类型）──────────────────────

    攻击卡赢 → 差值作为伤害打到输方
    盾卡赢   → 差值加入己方血条（溢出加血）
    防卡赢   → 差值消失（纯减伤，无额外收益）

  ── 攻击卡属性 ────────────────────────────────────────

    五行属性：金 / 木 / 水 / 火 / 土 / 无（物理）
    物理类型：斩 / 刺 / 打 / 射击

  ── 特殊规则：赢家通吃 ────────────────────────────────

    同物理类型攻击对打（斩vs斩 / 刺vs刺 / 打vs打）：
    → 赢家造成全额数值伤害（不是差值！）
    → 同行相杀，高下立判

    射击不触发赢家通吃，但数值偏低、CD偏长。

  ── 三种防御型定位对比 ────────────────────────────────

           盾 Shield          防 Defend
  数值     低(但>同级攻击)     高
  CD       长                 短
  赢了     溢出加血！          溢出浪费
  输了     受差值伤害          受差值伤害
  定位     低频但有收益        高频纯减伤

## 七、血量与伤势机制

  核心理念：你不是被打死的，你是被伤势压垮的。

  HP = 缓冲区，不是生命值
  SP = 卡组空间上限 = 真正的生命线

  流程：
    1. 受到伤害 → 扣HP
    2. HP清零 → 触发 AddWound(Npc, DamageInfo)
    3. 伤势卡强制塞入NPC卡组，占用空间
    4. HP恢复50%，继续战斗
    5. 每Tick检查：卡Cost总和 > SP → 判负

  ── 伤势生成规则：AddWound(Npc, DamageInfo) ────────────

    Step 1：判定伤势等级
      ratio = 最后一击伤害 / Npc.体魄
        ratio ≤ 1   → 小伤（抽 Size1 伤势卡）
        ratio ≤ 2   → 中伤（抽 Size2 伤势卡）
        ratio > 2   → 重伤（抽 Size3 伤势卡）← 预留

    Step 2：Tag匹配抽取伤势卡
      根据 DamageInfo 的元素属性 + 物理类型，
      从对应 Size 等级的伤势卡池中进行 Tag 匹配（OR逻辑），
      在候选集中随机抽取一张。

      匹配示例：
        火+斩 → 候选 = {烧伤, 伤口} → 随机
        水+刺 → 候选 = {冻伤, 流血} → 随机
        纯斩  → 候选 = {伤口}
        纯火  → 候选 = {烧伤}

    Step 3：伤势卡塞入卡组，HP恢复50%

  ── 伤势卡本质 ──────────────────────────────────────────

    伤势卡就是普通的效果卡，正常参与CD循环。
    战斗引擎无需感知"伤势"概念——
    它只是一张会 SelfDamage 的卡（或附带 ReduceMana 等效果）。
    伤势卡不进待发槽，不参与对拼，CD到直接结算。

    伤势卡分为两大类：
      物理伤势（4张）：匹配物理类型，CD4，SelfDamage(1)
      元素伤势（5张）：匹配五行元素，CD6，SelfDamage(1) + ReduceMana
        元素伤势的Mana干扰遵循五行相克：
          烧伤(火)→减金  冻伤(水)→减火  毒伤(木)→减土
          金伤(金)→减木  土伤(土)→减水

    完整伤势卡表见 → 战斗/CardOverview.md「伤势卡」章节

  ── 伤势持续到战后 ──────────────────────────────────────

    战后NPC带着伤势生活
    → 需要疗伤/修养/丹药去除伤势卡
    → 伤势越多 → 卡组空间越少 → 战斗力越低

  ── 构筑博弈 ──────────────────────────────────────────

    满编卡组(7/7) → 强但脆，一个伤势就可能溢出
    留空卡组(5/7) → 弱但韧，能扛几次伤势不崩

## 八、Mana（灵元）系统

  蓝条(MP) → 定期转化 → 灵元池(带元素属性的Mana)

  机制（所有参数均为 NPC 动态属性，战斗引擎只读取）：
    开战时 + 每隔 NPC.ManaConvertInterval 个 Tick，触发一次"转化"：
    扣除 NPC.ManaConvertAmount 点蓝量 → 按 NPC.ManaElementDistribution 方案
    产生对应数量的灵元 → 灵元有五行属性

  → 详见「NPC 战斗属性清单」（本章第九节）

  卡牌与Mana：
    无Mana需求的卡 → 开局直接进入CD计时
    有Mana需求的卡 → 需先获得对应灵元，消耗后才开始CD

  Mana消耗模式由 CardType 决定：
    法术 → 每次CD循环都需消耗Mana
    法宝 → 首次消耗Mana激活，后续N次免费，次数用完需再激活
    其他类型 → 各有规则，按需设计

## 九、NPC 战斗属性清单

  核心原则：战斗系统中所有因 NPC 而异的数值参数，都是 NPC 身上的动态属性。
  战斗引擎只是一个执行引擎，所有参数从 NPC 身上读取，不定义其值。

  | 属性 | 说明 | 影响因素 |
  |------|------|----------|
  | ManaConvertInterval | 灵元转化频率（每 N Tick 转化一次） | 境界、功法、天赋 |
  | ManaConvertAmount | 每次灵元转化时产生的灵元数量 | 境界、功法、天赋 |
  | ManaElementDistribution | 灵元的五行元素分配方案 | 道途、功法、所在 Tile 的五行浓度 |
  | SimulationDepth | 实战水平推演深度（K × N），决定 NPC 选卡策略的优化程度 | 境界、阅历（未来） |

  **属性值的来源**：每个属性的具体数值由道途、功法、境界、天赋、环境等系统注入。
  当前阶段使用默认值，足以支撑战斗系统正常运行。未来各系统实现时逐步替换为计算值。

  **清单可扩展**：当发现战斗系统中某个参数应该因 NPC 而异时，随时追加到此清单。
