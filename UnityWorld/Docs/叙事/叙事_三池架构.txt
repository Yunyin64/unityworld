## 一、设计核心理念

叙事系统的目标，不是提供一套线性剧情播放器，而是构建一个让**世界自己在运转**的事件驱动引擎。

玩家来之前，世界已经在发生事情。NPC 在衰老、门派在兴衰、五行在失衡。这些变化不是预设动画，而是由事件系统实时驱动的真实状态变化。玩家的介入，只是这个运转世界中的一个变量。

**核心原则：叙事证明创造，创造证明战斗，战斗证明叙事。**

叙事系统是这个循环的起点——它是"已走通的语义案例库"，向玩家展示这个世界中已经存在的道途与规律。

---

## 二、底层统一：弹窗事件驱动

整个叙事系统的底层，是同一套**弹窗事件驱动引擎**。

无论是百年后必然爆发的妖荒之战，还是修士今天随机遭遇的劫匪，还是玩家主动选择去炼丹——本质上都是同一件事：**一个 StoryDefine 被触发，执行条件判断，产生世界状态变化**。

这套引擎对作用主体是通用的：
- 一个 NPC 个体
- 一个门派/家族
- 一个城市/国家
- 世界本身

同一套驱动，作用在不同尺度的主体上，形成从微观到宏观的叙事层次。

## 三、天地人·三池架构

```
┌─────────────────────────────────────────────────────────────┐
│                    主体（Subject）                            │
│          个人 / 门派 / 国家 / 世界  ← 同一套驱动               │
└─────────────────────────────────────────────────────────────┘
          │                    │                    │
          ▼                    ▼                    ▼
   ┌─────────────┐    ┌─────────────┐    ┌─────────────────┐
   │  天：宿命池  │    │  地：劫缘池  │    │   人：抉择池      │
   │  FatePool   │    │  KarmaPool  │    │   WillPool      │
   └─────────────┘    └─────────────┘    └─────────────────┘
   时间→StoryId映射   带权重+条件的       个体持有的
   时间到→触发         事件条目列表       BehaviorCard 实例
   必然（条件可拦截）   周期性权重随机      主动行为选择
```

### 3.1 天——宿命池（FatePool）

**本质**：时间与事件 ID 的有序映射。`Map<float time, List<StoryId>>`。

**触发规则**：当 WorldTime 到达指定时间，检查对应 StoryDefine 的 Conditions。满足则触发，不满足则跳过。无论是否触发，条目均从池中移除（宿命只有一次）。

**设计哲学**：宿命是"天"写好的剧本。它代表世界历史上必然发生的节点——大战、传承、天灾。但"必然发生"不等于"必然以此方式发生"，Conditions 允许特定情况下拦截或替换宿命。

**使用场景**：
- 某门派建立100年后，必然触发"传承危机"事件
- 世界开局后第X年，必然触发"妖荒之战"序章
- 某 NPC 到达暮年时刻，触发"生死抉择"

### 3.2 地——劫缘池（KarmaPool）

**本质**：带权重和条件的事件条目列表。`List<{StoryId, Weight, Conditions}>`。

**触发规则**：每隔固定周期，筛选所有 Conditions 满足的条目，按 Weight 加权随机触发其中一个。无满足条目时静默跳过。

**设计哲学**：劫缘是"地"（环境）带来的随机变化。"劫"字有意为之——这是修行路上必经的考验与际遇。渡过了是机缘，渡不过是劫难。权重和条件让"际遇"不是纯随机，而是受当前世界状态影响的有倾向的随机。

**使用场景**：
- 在火属性浓度高的区域，更高概率触发"走火入魔"事件
- 拥有"孤独"Trait 的 NPC，更高概率触发"奇人相遇"际遇
- 门派实力强盛时，有概率触发"他派招募"事件

### 3.3 人——抉择池（WillPool）

**本质**：个体持有的 BehaviorCard 实例集合，通过 BehaviorCardMgr 管理。

**触发规则**：个体在空闲时，由 AI（或玩家主观能动性）从持有的 BehaviorCard 中选择一张使用，触发对应的 Story。

**设计哲学**：抉择是"人"的主动意志。这是修行路上唯一可以**改命**的手段——宿命可能无法改变，劫缘随机降临，但抉择是个体对自身命运的主动书写。移动、修行、炼丹、社交、挂机……所有行为都是一张张可选择的卡牌。

**使用场景**：
- 玩家持有"外出游历"BehaviorCard，主动触发随机遭遇事件
- NPC 持有"闭关修炼"BehaviorCard，AI 判断当前应该修炼时自动触发
- 获得特殊机缘后，NPC 解锁"渡劫"BehaviorCard

## 四、StoryDefine·事件本体

所有故事事件的定义，统一使用 `StoryDefine`，不设类型区分。

```
StoryBaseDefine（基类）
    ├── Tags             ← 语义标签，用于 TagBag 匹配
    ├── Conditions       ← 触发/出现条件
    ├── Effects          ← 执行效果（简单轨）
    └── LuaScript        ← 复杂逻辑脚本路径（复杂轨，预留）

StoryDefine（事件定义）
    ├── IsHide           ← 核心开关：隐形 or 显示
    ├── Title            ← 显示用标题（IsHide=false 时必填）
    ├── Text             ← 显示用正文
    └── OptionIds        ← 正向持有的选项列表

OptionDefine（选项定义）
    ├── Text             ← 选项文本
    └── StoryIds         ← 反向注入：我要出现在哪些 Story 中
```

### IsHide：最关键的一个布尔值

| IsHide = true（隐形） | IsHide = false（显示） |
|---|---|
| 自动执行，不显示任何 UI | 弹出事件窗口，展示标题与正文 |
| 只有 Conditions + Effects | 有 OptionIds，玩家/NPC 做选择 |
| 世界在"后台"运转 | 玩家感知到"有事发生了" |
| 驱动世界状态的无声引擎 | 叙事体验的直接载体 |

**隐形事件是世界自运转的引擎。** 大量隐形事件在后台静默推进世界状态，玩家感受不到这些事件的过程，只看见最终浮出水面的显示事件——就像只看见浪花，感受不到洋流。

## 五、OptionDefine·双向持有设计

选项（Option）与事件（Story）的关系，采用**双向持有**设计。

```
正向（Story → Option）：
  StoryDefine.OptionIds 指定"这个事件标配哪些选项"

反向（Option → Story）：
  OptionDefine.StoryIds 声明"这个选项注入到哪些事件"
```

**合并规则**：触发某个 StoryDefine 时，最终选项列表 = StoryDefine.OptionIds（正向）+ 所有声明了该 StoryId 的 OptionDefine（反向注入），去重后呈现。

**双向持有的威力**：

- 设计一个"散尽家财救济"选项，在 OptionDefine.StoryIds 中列出所有灾难类事件，该选项自动出现在这些事件中，无需逐一修改
- 新增一个灾难事件，只需在 StoryIds 中引用已有的通用选项，立刻获得完整的选项集合
- 修改一个选项的效果，全局生效

**Option 本质是迷你 Story**：OptionDefine 继承 StoryBaseDefine，拥有完整的 Conditions/Effects/LuaScript。选项被选中的瞬间，就是一次迷你事件触发。
