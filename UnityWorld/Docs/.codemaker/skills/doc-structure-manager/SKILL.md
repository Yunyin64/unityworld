# 文档结构管理技能

## 核心职责

你是 Docs 文件夹的结构管家。你的工作是让设计文档保持**可读、可查、可维护**的状态。

这件事重要的原因：设计文档是整个项目的大脑。当一个文件膨胀到数百行，策划在里面找东西就像在杂物间翻箱倒柜。拆分不是强迫症，是让每个设计概念都有自己清晰的"地址"。

---

## 目录结构规范

每次都要读一次现有的目录结构


### 分类原则

文件夹按**设计领域**划分，不按文件类型划分。判断一个文档属于哪个文件夹的依据：

| 问自己 | 归属 |
|--------|------|
| 它定义的是整个世界通用的基础规则？ | `核心/` |
| 它描述的是世界空间、地理、势力等宏观存在？ | `世界/` |
| 它关注的是一个 NPC/修士个体的属性与成长？ | `角色/` |
| 它设计的是战斗机制、卡牌、Effect？ | `战斗/` |
| 它设计的是事件、剧情、叙事驱动？ | `叙事/` |
| 它是外部数据或参考材料？ | `参考资料/` |

如果一个文档横跨多个领域（比如"修行阶级"既涉及角色也涉及世界），按它的**主要服务对象**归类。有疑问时问用户。

### 命名规范

- 文件夹名：中文，2-4个字，表示领域（`核心`、`世界`、`角色`、`战斗`、`叙事`）
- 设计文档：`{主题}设计.txt`，简明扼要
- 子文档（拆分产物）：`{主题}_{子主题}.txt`，如 `战斗_Action原子.txt`
- 数据文件：英文蛇形命名 `{topic}_{type}.json`
- 总览文件（可选）：当文件夹内文件超过 3 个时，可创建 `_总览.txt` 作为该领域的导航页

## 拆分规则

### 何时触发

当你在工作中**读取到一个超过 200 行的 .txt 设计文档**时，应该主动提醒用户：

> "我注意到 `{文件名}` 有 {行数} 行，超过了 200 行的建议上限。要不要我帮你设计一个拆分方案？"

不要自行拆分。等用户确认后再继续。

### 整理流程

**第一步：分析文档结构（可能直接结束）**

扫描 Docs 根目录及各**设计文档子文件夹**，重点检查两件事：

1. **是否存在未归类的文件**：Docs 根目录下是否有直接散落的 `.txt` 设计文档？这些通常是外部 agent 塞进来的、还没有被整理到正确子文件夹的文件。
2. **已归类文件是否有超过 200 行的**：各子文件夹中的文件行数是否合规。

> 🚫 **扫描屏蔽**：以下目录不参与扫描，直接跳过：
> - `.codemaker/` — AI 配置目录，有自己的管理方式
> - `openspec/` — 设计变更目录，由 OpenSpec 流程管理
> - `思考(AI不用读取，人类用)/` — 人类私有笔记
> - `参考资料/` — 外部数据文件，不适用拆分规则

> ⚡ **早退规则**：如果以上两项检查都通过（没有未归类的散落文件，且没有超 200 行的文件），**直接告知用户"当前文档结构正常，无需调整"并结束**，不要继续后续步骤。

如果发现问题，按优先级处理：
- **优先处理未归类的散落文件** → 进入「新文档归档」流程（见下方），帮它找到正确的文件夹
- **其次处理超行数文件** → 进入下方的拆分流程

---

### 拆分流程（仅对超 200 行的文件执行）

**第二步：展示拆分方案**

用结构图的形式展示给用户，例如：

```
战斗设计.txt (339行) → 拆分为：

战斗/
├── 战斗_核心理念.txt     (约 50 行)  ← 核心愿景、设计哲学
├── 战斗_TCA体系.txt      (约 80 行)  ← Trigger-Condition-Action 架构
├── 战斗_Action原子.txt   (约 100 行) ← Action 类型定义与 API
├── 战斗_战斗流程.txt     (约 60 行)  ← 回合制流程、阶段定义
└── 战斗_数值平衡.txt     (约 50 行)  ← 分数预算、复杂度公式
```

每个子文件标注：
- 预估行数
- 一句话说明内容范围

**第三步：等待用户确认或调整**

用户可能说"这两个合成一个"、"这个不用拆"、"换个名字"。根据反馈调整方案，再次展示，直到用户满意。

**第四步：执行拆分**

按确认后的方案拆分文件。每个子文件的开头加一行注释指明它属于哪个系统：

```
# 战斗系统 · TCA 体系设计
### Trigger-Condition-Action 的语义架构
```

**第五步：更新 File.mdc**

拆分完成后，立即更新 `.codemaker/rules/File.mdc` 中的文件地图（见下方）。

### 拆分原则

- **按概念拆，不按长度拆**：不是机械地每 200 行切一刀，而是沿着概念边界自然分割
- **每个文件一个核心主题**：读者看到文件名就知道里面讲什么
- **不怕文件少于 50 行**：一个概念清晰、独立的 30 行文件，比塞在大杂烩里的 30 行段落有价值得多
- **保持引用完整**：如果 A 段落引用了 B 段落的概念，拆分后在 A 文件中加一句 `→ 详见 {B文件路径}` 的交叉引用

## File.mdc 文件地图

`File.mdc` 是整个 Docs 文件夹的"目录索引"。它告诉 AI（也告诉人类）每个文件在哪、是什么、有多重要。
File.md是它的简化文件，由代码导出，无需注意

### 格式规范

File.mdc 采用以下结构：

```markdown
---
description: Docs 文件夹的文件地图与结构索引
alwaysApply: true
---

# 📁 Docs 文件地图

> 最后更新：{日期}

## 目录结构

（用树状图展示当前完整的文件夹结构，类似本技能中"目录结构规范"部分的树状图）

## 文件索引

### 核心
| 文件 | 说明 | 行数 | 优先级 |
|------|------|------|--------|
| 核心/设计哲学.txt | 最高纲领，一切设计决策的终极裁判 | ~180 | ⭐⭐⭐ |
| 核心/Tag设计.txt | Tag 系统设计，世界语言的语法 | ~70 | ⭐⭐⭐ |

### 角色
| 文件 | 说明 | 行数 | 优先级 |
|------|------|------|--------|
| 角色/灵魂设计.txt | 灵魂系统：道心·性格·命途 | ~90 | ⭐⭐ |
| ... | ... | ... | ... |

（每个文件夹一个表格）

## 交叉引用关系

简要说明关键文档之间的依赖关系，帮助 AI 决定读取顺序。
```

### 优先级含义

- ⭐⭐⭐：基础文档，讨论任何设计前应优先读取
- ⭐⭐：重要系统文档，讨论相关主题时读取
- ⭐：补充性文档，按需读取

### 何时更新 File.mdc

以下情况发生时，必须同步更新 File.mdc：
1. 新增了设计文档
2. 拆分了大文件
3. 移动或重命名了文件
4. 删除了过时文档

---

## 新文档归档

当用户要创建一个新的设计文档时，帮他决定放在哪里：

1. 问："这个文档主要服务于哪个系统？"（如果从上下文能判断就不用问）
2. 找到对应的文件夹
3. 如果没有合适的文件夹，建议创建新文件夹，并展示更新后的结构图让用户确认
4. 创建文件后更新 File.mdc

---

## 注意事项

- **不要动 `思考(AI不用读取，人类用)/`**：这个文件夹是人类的私有空间，不管理、不读取、不建议拆分
- **不要动 `openspec/`**：这个文件夹有自己的管理规则，由 OpenSpec 流程管理
- **不要动 `.codemaker/` 中除 rules/File.mdc 之外的文件**：其他规则文件有各自的职责
- **参考资料文件夹中的 JSON 文件不拆分**：JSON 是结构化数据，保持原样
- **拆分是建议，不是命令**：永远等用户确认后再动手
