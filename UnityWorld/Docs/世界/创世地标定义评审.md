# 创世地标定义评审

> 评审过程与参考资料。最后确认的字段和数值规则见 [《创世地标生成需求》](创世地标生成需求.md)。

世界生成时，先确定河流、海岸、地形和地区拼图，再决定首批地标出现在哪里。策划可以直接指定全图数量区间，也可以给特定地标配置逐格概率。两种生成方式都从已经落地的地区布局出发。本次按开发期重构，可同时更新定义、数据、编辑器和校验。字段取舍仍在评审中。

当前大陆的独立散布在空闲 Fill 格上先按 0.003 的默认触发率抽一次，触发后再按 `SpawnWeight` 选定义。新方案把「全图要几处」「某个合法格的命中率」和「几种地标竞争时选哪种」分开表达。首版有前两种需求。竞争默认使用世界种子平等裁决，权重字段暂不进入新定义。 [现行地图配置](地图生成配置.md#元气与生命周期) · [创世散布](../../Scripts/Game/Domain/Object/Plane/Generation/WorldMapFill.cs) · [生成地块与水文数据](../../Scripts/Game/Domain/Object/Plane/Generation/GeneratedWorld.cs)

## 主世界第一次生成的实际顺序

`WorldMgr.Initialize` 调用 `PlaneMgr.CreateMainPlane`。主世界先用 `WorldMapGenerator.Generate` 建成一份尚未发布的地图，再由 `PlaneGenerator.BuildContinent` 创建实体和原初快照。普通地区确实在独立地标之前。固定地区和必需湖泊分别提前，以便保护固定地貌和确定水系。 [世界初始化](../../Scripts/Game/World/WorldMgr.cs) · [主世界创建](../../Scripts/Game/Domain/Object/Plane/PlaneMgr.cs) · [当前生成阶段](../../Scripts/Game/Domain/Object/Plane/Generation/WorldMapGenerator.cs)

```text
固定地区、绝对地标坐标预留
    -> 连续环境、海域、必需湖泊、河网
    -> 普通必需地区、普通可选地区
    -> 填充剩余格、水系修整
    -> 独立地标散布、候选地图审计
    -> 创建 Tile 和基础元气、创建自然地标、原初快照、创建人工地标
    -> 一起发布位面、地区、地标和快照
```

**地区落地时，由它带来的地标位置也已经落进地图计划。** 每个成功放置的地区实例把 `LandMarkLayout` 和 `AdditionalLandMarks` 的相对坐标换成实际格子。后者支持作者配置同格的主地标与附加地标。地区撤销时，其整组地标位置也撤销。绝对坐标的预留同样先进入候选地图。此时自然和人工地标的位置都能查到，运行时实例在后面的创建阶段才出现。 [地区配置](../../Scripts/Game/Data/Defines/RegionDefine.cs) · [地区提交与撤销](../../Scripts/Game/Domain/Object/Plane/Generation/WorldMapRegions.cs) · [绝对地标预留](../../Scripts/Game/Domain/Object/Plane/Generation/WorldMapFixedPlacements.cs) · [地标实际创建](../../Scripts/Game/Domain/Object/Plane/System/PlaneGenerator.cs)

**数量统计和独立候选各看一套范围。** 配额统计用整张候选地图的全部已规划地标，包含主地标、同格附加地标和绝对坐标地标。独立补位仍只从空闲 Fill 格筛选。如果选址依赖附近的灵脉眼，地区带来的灵脉眼也能作为参照。当前代码已经保护占位并检查全局唯一性，普通地标的数量上下限和同类间距属于拟议规则。 [候选地标列表](../../Scripts/Game/Domain/Object/Plane/Generation/GeneratedWorld.cs) · [创世散布](../../Scripts/Game/Domain/Object/Plane/Generation/WorldMapFill.cs) · [地图审计](../../Scripts/Game/Domain/Object/Plane/Generation/WorldMapAudit.cs)

用当前配置重跑主大陆种子 `12345`，40,000 格里有 **4 个地区自带的灵脉眼、63 个独立散布的灵脉眼**，另有 **11 座古观星台全部来自地区**。如果给灵脉眼试填首批总量 4–8，独立补位只能再放 0–4 个。如果古观星台上限试填 8，这张图地区配置已经贡献 11 座，应该明确报冲突并保留作者布局的完整性。数字只说明计数口径。

## Odyssey 的地标怎么组成

Ludeon 把世界地图上有专用图标的地标，和进入该地点后影响实际地图的特征联系起来。普通地图也有特征。河源、汇流、入海口等特征取决于所在位置。有辨识度的地标还能组合地形、资源和风险。对 UnityWorld 有用的是两点。**选址读取真实地理，地标特色有具体的玩法载体。** 例如灵泉由地点标识、适用环境和水元气效果共同定义，三个部分各有用途。 [Ludeon 官方地标预览](https://ludeon.com/blog/2025/06/odyssey-preview-1-map-features-landmarks-and-biomes/) · [Odyssey 官方商店说明](https://store.steampowered.com/app/3022790/RimWorld__Odyssey/)

本机 Steam 安装版 `1.6.4871 rev590` 的 Odyssey XML 中，地标定义文件有 45 条具名记录和 6 条抽象模板。世界地标生成步骤排在河流、道路等步骤之后。以温泉为例，其地标定义把温泉本身标成必备特征，并配置了可选特征和地标组合。对应的地块特征有自己的适用生态规则。河源、汇流和河口分别指定不同的处理器。由此可以确认配置职责的拆分。XML 里的 `commonality` 和组合数值用于本次对照，UnityWorld 的总量区间采用下文自己的规则。 [Odyssey 地标定义](<C:/Program Files (x86)/Steam/steamapps/common/RimWorld/Data/Odyssey/Defs/TileMutators/Landmarks.xml>) · [自然地块特征](<C:/Program Files (x86)/Steam/steamapps/common/RimWorld/Data/Odyssey/Defs/TileMutators/TileMutators_Natural.xml>) · [世界生成顺序](<C:/Program Files (x86)/Steam/steamapps/common/RimWorld/Data/Odyssey/Defs/WorldGeneration/WorldGenerator.xml>)

### commonality 的实际抽法

本机正式版的 `WorldGenStep_Landmarks.GenerateFresh` 先算本层总目标，公式为 **格数 × 约 0.00222222 × 地标密度档系数，再取整**。普通档系数为 1，40,000 格的例子目标约 89 处。生成器先为各地标类型从打乱后的格子中收集合格候选，排除已有地图对象的位置。每轮以 `commonality` 为权重抽地标类型，从对应候选取一个位置，只有未占用位置才计入已放数量，直到达到总目标或用完尝试预算。

例如参加同一轮抽选的两种定义权重为 0.25 和 0.75，当轮选中类型的比例是 1 比 3。最终各有几处还取决于候选容量和占位竞争。装配特征另走 `WorldLandmarks.AddLandmark`。`mutatorChances` 可叠加多个满足条件的特征，`comboLandmarkMutators` 添加第一个成功的组合后停止。必备特征也参与 `LandmarkDef.IsValidTile` 的候选检查。 [本机正式版程序集](<C:/Program Files (x86)/Steam/steamapps/common/RimWorld/RimWorldWin64_Data/Managed/Assembly-CSharp.dll>) · [Odyssey 地标定义](<C:/Program Files (x86)/Steam/steamapps/common/RimWorld/Data/Odyssey/Defs/TileMutators/Landmarks.xml>)

## UnityWorld 首批摆放规则

1. **在地图方案完成后读取实际输入。** 统计地区和绝对坐标已有的地标，再从空闲 Fill 格筛独立落点。保底和普通补位共同遵守有效空位、固定边界、全局唯一性和明确配置的最小间距。同格附加地标通过地区显式配置。
2. **按量生成。** `MinCount–MaxCount` 表示含作者地标的正常目标区间。合法位置充足时从实际可完成的区间抽总量，扣掉已放的数量再补。普通候选够不到 `MinCount` 时尽量放，记录实际数量，地图可继续发布。作者布局已超过明确配置的上限时报告配置冲突。
3. **逐格抽签。** 每个通过 `SiteConditions` 的空格以 `PerTileChance` 掷一次。100 个合格候选用 20%，期望有 20 次命中，实际数量随种子变。间距、竞争和占位裁决可能让最终落点少于命中数。同一个定义首版选一种正常生成方式。
4. **确实需要的数量单独保底。** `NeedCount` 省略就没有强制保底。已放地区和绝对坐标都计入。先为各类型预留保底位置，优先用正常候选。仍有缺口时，可以跳过一般选址条件，从符合通用硬约束的空格里随机补。若配置了单独的保底选址条件，放宽时按该条件选格。连保底空位都没有时，报告 `NeedCount` 无法满足。
5. **前置看已规划地标。** `SiteConditions` 能读取地区留下的灵脉眼，也能读取已经计划完成的独立地标。若要依赖同一批独立地标，需要显式声明依赖顺序并检查成环。这个顺序决定候选能看到什么。实际创建仍沿用「自然地标 → 原初快照 → 人工地标」。

**数字例子。** 河心水府设为 3–5 座，最小同类间距 6 格。地区已经摆 1 座，合法空格只有 1 个时，普通结果是 2 座。若另填 `NeedCount=3`，第 3 座才走保底。此时如果允许跳过河道条件，就可能在陆地上得到一座名为「河心水府」的地标。水域身份必须成立的内容可以额外配保底条件，例如从主河放宽到任意河段。

### 选址 Lua 怎么接

建议 `SiteConditions` 是一个字符串，填写 Lua 规则名或文件 ID，例如 `river_centerline`。规则本身放在 Lua 文件里，输入为本次创世的只读地图数据，返回能否使用当前格。简单关系也可以共用现成规则，例如「附近有某类地标」。规则可读取本格、邻格、水文和已经规划的地标。生成器负责候选顺序、掷骰和落位。同一套规则可供地图预览与正式创世使用。现有 `LuaRuntime` 可以执行 Lua，但这里需要只读的创世上下文及一致的执行约束。创世筛选读取 Lua 的结果，额外创建附属地标仍由生成规则负责。 [Lua 执行入口](../../Scripts/Core/Lua/LuaRuntime.cs)

### 地标的显示与感知

`DrawType` 决定**画什么**。图标类画在格心，遮罩贴在 Tile 形状内，Shader 给格子施加视觉表现，氛围类可以播放雾或粒子，无绘制型可以只通过名称或互动被感知。每种方式复用或引用自己的素材，具体绘制参数由相应表现规则解释。

`IsHide` 决定**谁能知道地标存在**。玩家和 NPC 的观察结果都要过滤隐藏实例。地图标记、详情名称、同格地标数量提示和自动互动候选均使用过滤后的数据。创世条件和内部规则仍可读取隐藏实例，它也仍可占位、计数和施加效果。若用元气或环境效果留下间接线索，玩家能据此推测地点，观察结果依然没有直接暴露地标。 [探索地标读取](../../../scripts/client/exploration/ExplorationSession.cs) · [地图地标与附加数量绘制](../../../scripts/client/exploration/ExplorationMap.cs)

### 动态条件示例

这些条件读取创世候选地图的实际结果，名称用于评审含义。

| 条件 | 示例 | 读取的事实 |
| --- | --- | --- |
| 属于指定水域 | 河心水府只出现在河道 | `MapWater.Kind = river`，包括河带侧翼 |
| 处于河道中心线 | 镇水碑只放在河道中心 | 河水类型加 `IsCenterline`。可以再要求最低汇水量，表达河段规模 |
| 紧邻水域的可步行陆格 | 云渡码头贴着河岸，且本格能步行到达 | 本格通行规则及六邻格水域。若要保证可渡，再检查沿跨河方向的对岸落脚点 |
| 河源、汇流或下游落差 | 灵瀑放在有足够落差的河段 | 河源标记、实际入流方向或下游方向与地形海拔差。海拔差先作为选址近似 |
| 环境范围 | 云涌灵泉只落在指定温湿度和海拔范围内 | 最终 `MapEnvironment` 的连续数值，用于比较明确的上下限 |
| 与已有地标的距离 | 闭关洞府在灵脉眼 1–3 格之内 | 本张地图已规划的灵脉眼坐标，使用六边形格距 |

当前大陆的河带水格共用 `river-network` 这个 `BodyId`。若以后要表达「每条主河各放一座」，需要先定义并识别河系或河段。本次可先用全图数量和同类间距表达分布。 [水域数据](../../Scripts/Game/Domain/Object/Plane/Generation/GeneratedWorld.cs) · [河带写入](../../Scripts/Game/Domain/Object/Plane/Generation/WorldMapHydrology.cs)

首轮用三个定义就能核对清楚。河心水府验证按量与 `NeedCount`，云渡码头验证河岸候选与逐格概率，闭关洞府验证 Lua 前置与隐藏观测。每个种子的报告应能查到作者数量、普通补位、保底补位、拒绝原因和最终坐标。同一份配置和种子应生成同一批地标。
