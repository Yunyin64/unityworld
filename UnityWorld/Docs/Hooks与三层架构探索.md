# Hooks 与三层架构探索

> 2026-04-20 讨论记录。纯思考笔记，不涉及实现。

## 一、核心想法：AI 时代的三层开发架构

### 1.1 三层定义

| 层级 | 别名 | 文件形态 | 主要作者 | 核心职责 |
|------|------|---------|---------|---------|
| ① 策划层 | 设计层 / 自然层 | JSON、TXT | 策划 / AI | 人类可读的数据聚合（卡牌概览、效果描述、数值字段） |
| ② 脚本层 | AI层 / 执行层 | Lua、Python | AI 为主 | 每张卡/每个效果的具体逻辑实现 |
| ③ 框架层 | 程序层 / 代码层 / 结构层 | C# | 程序员 | 底层运行框架（Hook 注册/触发、阶段管理、暴露给脚本的 API） |

### 1.2 信息流向

```
① JSON（意图声明）
     │
     │  AI 翻译 or 模板编译
     ▼
② Lua（可执行逻辑）  ← Source of Truth
     │
     │  调用暴露的 API
     ▼
③ C# Hooks 框架（运行时引擎）
```

**关键决策**：② 是 Source of Truth，① 是可读视图，③ 是不变的基础设施。

## 二、TCA 在新模型中的定位

### 2.1 核心洞察

> TCA 不是一种"和 Lua 并列的执行方案"，而是"可以被编译成 Lua 的声明语言"。

TCA（Trigger + Condition + Action）本质上就是我们已有的"半结构化意图声明"——它天然可以被翻译成 Lua 代码。

### 2.2 TCA = Lua 的语法糖

```
旧理解：TCA JSON → C# APIMgr 直接解释执行
新理解：TCA JSON → 编译为 Lua → Hooks 执行

TCA 从"被解释执行的 DSL"升级为"被编译成 Lua 的 DSL"
```

### 2.3 已有工作不废弃

- 现有 TCA 的 T/C/A Define 数据 = 积累的"Lua 模板零件库"
- 随机组合生成卡牌的能力完全保留（纯模板拼接，零 AI，毫秒级）
- 演进路径是渐进的，不需要一步到位

## 三、T/C/A 作为 Lua 代码片段模板

### 3.1 每个 Define 携带 lua_template

```
TriggerDefine → 决定生成哪个函数名（OnUse / OnAttack / OnContestWin）
ConditionDefine → 生成 if 判断 或 目标选择代码
ActionDefine → 生成具体执行调用
```

### 3.2 组合 = 拼接

以 card_jin_whirlwind 为例：

```
Effect 1: trigger_on_use + (无condition) + action_atk_3
Effect 2: trigger_on_attack + cond_card_self + action_charge_1
```

编译产物：

```lua
function OnUse(ctx)
    CombatCmd.Attack(ctx, "None", "Zhan", 3)
end

function OnAttack(ctx)
    CombatCmd.Charge(ctx, ctx.self_card, 1)
end
```

纯字符串模板替换 + 参数填入，确定性编译，不需要 AI。

### 3.3 模板的边界

模板能搞定的：每个 Effect 独立、无跨 Effect 状态共享的卡牌（大部分卡）。

模板搞不定的：需要本地状态在多个函数间共享的效果。例如"每使用一张攻击卡，本卡伤害永久+1"——这种需要 AI 或人来写 Lua。

## 五、Lua 脚本的设计原则

### 5.1 约定优于配置

**函数存在 = 声明监听。** 不需要额外的 hooks 声明表。

```lua
-- 卡牌作者只需要定义函数，框架自动匹配

function OnUse(ctx)         -- 框架：CD就绪时直接调用
    ...
end

function OnAttack(ctx)      -- 框架：自动注册 trigger_on_attack 到 EventMgr
    ...
end
```

框架加载 .lua 时扫描函数名 → 对照表匹配 → 自动完成注册。

### 5.2 可用的 Hook 函数名（= 框架支持的触发点）

| 函数名 | 触发方式 | 时机 |
|--------|---------|------|
| `OnUse` | 主动调用 | CD 就绪时框架直接 call |
| `OnAttack` | 事件驱动 | 攻击时（注册到 EventMgr） |
| `OnContestWin` | 事件驱动 | 拼点赢时 |
| `OnContestLose` | 事件驱动 | 拼点输时 |
| `OnDominate` | 事件驱动 | 赢家通吃时 |
| `OnDominated` | 事件驱动 | 被通吃时 |
| `OnHitBody` | 事件驱动 | 命中造成伤害时 |
| ... | ... | 按需扩展 |

### 5.3 注册式 EventMgr 保留

运行时仍用 EventMgr 的注册+精准投递机制（Scope 分层、字典查找 O(1)）。Lua 只是**创作层的表现形式**，底层执行引擎不变。

## 六、与杀戮尖塔2 Hooks 的对比结论

| 维度 | 杀戮尖塔2 | 我们的方案 |
|------|-----------|-----------|
| 效果载体 | 每个遗物/能力 = 一个 .cs class | 每张卡 = 一个 .lua 文件 |
| 监听发现 | 每次事件动态扫描所有对象 | 加载时注册到 EventMgr，事件时精准投递 |
| 数值修改 | Hook 方法链临时询问（无状态） | StatBlock Modifier 持久挂载（有状态） |
| 执行顺序 | Early / Normal / Late 三阶段 | 注册顺序（未来可扩展优先级） |
| 表达力 | 代码无限制 | Lua 无限制（复杂效果）/ TCA 模板（简单效果） |
| 批量生成 | 不适合（每个效果是一个 class） | 适合（TCA 模板拼接，或 AI 批量写 Lua） |

**我们取了两边的长处**：
- 杀戮尖塔的"对象即逻辑"可读性（Lua 文件自包含）
- 我们 TCA 的数据驱动组合能力（模板编译）
- EventMgr 的精准投递性能（大量对象场景）

## 七、未来可能探索的方向

- Should 否决机制（ShouldDie、ShouldDraw 之类的全局拦截层）
- Early/Normal/Late 执行阶段（EventMgr 加优先级）
- Modify 数值修改管线（战斗中的临时伤害修正）
- AI 生成新的 T/C/A 零件（一次投入，无限复用）
- Lua 沙箱测试机制（自动验证 AI 生成的脚本）
