# Design

状态：**核心实现已接通，正在完成验收记录（2026-10-24）。** 已有开场抽取保留；灵元进入卡即点亮 1/n，没有资源池；扫完后才点满须等下一轮再扫完整；每方待发槽仅有一个位置；伤口必须按完整卡牌形状插入，不可拆成散格。用户进一步确认：由设计保证存在完整伤口位置。逐格顺序、下左方偏好、跨轮保留、独立轮末、实际 MP 成本和 SP 判负不变。实施证据见 implementation.md。

## Goals / Non-Goals

**Goals:**

- 用背包布局、位置灵元和扫描时钟驱动出招；卡牌被完整扫描且资源满足，才有资格占用本行唯一发动机会。
- 保留待发槽和拼点结果计算，将普通行切换对拼与轮末强制结算分成明确入口。
- 给出可追溯到代码的改造范围、已确认规则的验收场景和未决问题清单。

**Non-Goals:**

- 不将待定规则伪装成默认行为，不提前修改现有主规格或归档其他变更；代码实施按 tasks.md 推进。
- 不在本变更中实现 Godot 拖拽背包界面、重做美术或全量卡牌重设计；先用符合新机制的最小测试卡验证核心，旧特殊卡效果后续调整。
- 不借此次改造重写伤害类型、护盾或大世界修炼系统。

## Decisions

以下区分用户已经确定的玩法与承载这些玩法的技术建议。不得用旧代码限制推翻本次确认。

### 1. 数据分成定义、战前布局和战斗状态

- 主功法侧提供按等级配置的背包有效格、大小和主卡固定占格。选择主功法及等级即可确定这些布局约束，不根据总 SP 临时生成通用矩形。主功法本身仍是 Card，固定位置也计入卡牌占格/SP；副功法按普通 Card 放入，不自动拼接空间。
- 形状建议用有效格坐标集合表达，矩形同样可表达。普通卡形状格数与 Size 一致；主功法布局另记录不可移动的固定位置。是否开放普通卡旋转留给内容/排布配置，不影响核心记录真实占格。
- NPC 侧保存唯一 `MainGongFaCardId`（建议字段名）、对应等级/布局引用及卡 ID → 放置位置，Field/Reserve 继续表达场上与候补归属。有效角色必有主功法；缺失是迁移/数据错误，不能运行时猜默认功法或创建无功法背包。
- 战斗侧建议新增 `CombatBackpackState`，持有当前行、行 Tick、轮次、格子占用、未分配灵元与每卡接收资源；这些是独立战斗快照，不写入共享 CardBaseData。
- 不给集中 ManaPool 叠加一层展示坐标：那会允许卡跳过扫描从全局池扣费，无法表达空间分配机制。兼容查询可由新状态计算，但旧全局扣费入口不能继续作为另一套资源真值。

### 2. 扫描驱动负责点亮与使用时机，Lua 负责卡牌效果

建议由统一扫描入口选出本行卡牌，验证资源并记录一次使用，再调用原有卡牌效果。`FaShu.Tick`、`ZhaoShi.Tick`、`UseFabao` 的旧 CD/扣费/Ready 路径需改造，避免并行存在两个出手入口。

建议增加生命周期阶段表达“等待扫描、已入待发槽、已完成本次使用”，不把旧 CDFull 当作扫描完成。`Contest()` 负责产生拼点数据；无拼点卡执行即时效果，有拼点卡在对拼或直击完成后执行其后续 Apply，并保证只执行一次。暂不重命名全部 Lua hook；按已确认类别规则迁移内容。

灵元从格子进入 Size 为 n 的卡时不再占原格，每进入一个符合要求的灵元就点亮 1/n，直到完全点亮。卡上已接收数量及元素表达点亮进度，不是等待二次扣费的钱包；没有资源池，也没有激活时另付 n 个灵元的步骤。点亮进度和格上未分配灵元跨轮保留，轮次推进不能清零或重排。本次实现采用：只有成功使用才结束本次点亮，将进度复位为 0/n；未使用的卡保持进度。已入待发的卡在结算前不接收下一次点亮资源，结算后重新参与分配。这是供验收的生命周期实现选择，不是轮末清空或额外支付。

灵元选择分为两步：先筛选“仍需要且可接收本次灵元”的候选卡，再在候选中选择最近者。不能先对所有卡取最近，再因最近卡已满而放弃较远需求卡。距离与复杂平距规则留在独立函数中，例如 `SelectNearestNeedingCard(origin, mana, candidates)`；函数返回卡或无目标，等距下左方优先。调用方不写死曼哈顿距离、中心距离、搜索半径或只找未扫描卡。无目标返回时原格灵元保持不变。测试可以注入已知距离排序，先验证筛选、下左方偏好及无目标行为。

保留已有开场抽取：当前 `CombatScene.Start()` 已调用 `DoManaDraw(true)`，迁移后将该批灵元放入背包空格，不把是否开场抽取重新列为玩法决策。开场及本方轮末均按真实空格生成；实际数量由计划量、空格数、可支付 MP 限制。按每灵元 1 MP 的测试配置，计划 5、仅有 2 空格时生成 2、扣 2 MP；无空格生成和扣款均为 0。MP 是生成成本，与卡牌接收灵元形成点亮进度是不同步骤。元素抽取与落点随机沿用战斗种子来源。

### 3. 场景集中调度行事件和轮末事件

建议每 Tick 保留必要的状态/Modifier 更新；到达行边界时各存活参战者按行内从左到右的格子顺序处理。10 Tick/行是当前讨论与测试基准，格子遍历是该行内部的确定顺序，不新增“每格 10 Tick”。多方同 Tick 的收集/结算由场景统一协调，避免 Dictionary 遍历顺序隐式决定先手。

建议处理框架：

```text
基础 Tick / 持续状态
  → 到达行扫描边界
  → 本行从左到右依次访问格子
      遇到灵元：选择最近且需要的可接收卡；无目标则留原格
      遇到卡：记录覆盖；最后占用格扫到时检查资源与本行额度
      卡被使用：产生的拼点数据入待发槽；继续扫描右侧格子
  → 行切换：只匹配双方待发数据
  → 若本方轮次完成：只强制处理本方剩余待发数据，才允许本方直击判定
  → 处理对应伤害、场上变更、败退与目标变更
  → 保留剩余资源，为完成轮次者按空格/MP 补灵并开始下一轮
```

同一行不做“先分配所有灵元，再判所有卡”的批处理；顺序由各自格子位置决定。跨行卡在其最下占用行的最右占用格被扫到时才完整。到这个格子才按当时资源与本行机会判断：缺灵则不使用、不消耗机会，继续向右；资源足够且本行机会未用则使用，并消耗本行机会。不能预先锁定最左卡，也不能让它缺灵时阻挡后面的卡。行机会用尽后仍继续处理右侧灵元；右侧尚未扫到的资源不能提前或追溯计入左侧卡当时的判断。

验收例：依次扫完整 A（缺灵）、B（资源足）、C（资源足），结果为 A 跳过使用，B 使用并消耗机会，C 本行不使用。若 A、B 均缺灵，则机会一直保留到 C；机会限制的是成功使用次数，不是扫描到卡的次数。

后续确认：A 在最后占格处只有 2/3 点亮进度时跳过；右侧灵元后来令其达到 3/3，A 也不在补满当场使用，保持点亮状态等下一轮再次扫完整。

每方待发槽只有一个位置，最多持有一份拼点数据。`ProcessContest` 负责行切换双方配对，场景对完成轮次的具体参战者调用 `ForceOwnPending`，复用 `ResolveContest` / `Straight` 基础数值。双方都有待发则配对并清除各自唯一数据；A 轮末仅强制处理 A 尚有的那一份，不替 B 出槽、不重置 B 的进度。普通对拼已清空的槽不再轮末重复结算。旧容量挤出/CD 不参与轮中直击。本次实现采用：已有待发占位时，新的拼点卡保留满亮，不使用、不占本行机会，继续扫描右侧；下次扫完整时再尝试。无拼点卡仍可成功使用。当前最小卡通过自身 Contest hook 声明拼点能力。

例如 A 三行、B 五行，10 Tick/行，以下行号从 1 起。每个节点均先让双方完成逐格扫描，再尝试双方配对，然后仅对轮末所属者强制剩余数据，统一处理伤害/伤口/败退，最后各自换行或补灵：

| Tick | A 本次扫描 | B 本次扫描 | 配对之后的轮末处理 |
| --- | --- | --- | --- |
| 10 | 第1轮第1行 | 第1轮第1行 | 无 |
| 20 | 第1轮第2行 | 第1轮第2行 | 无 |
| 30 | 第1轮第3行 | 第1轮第3行 | 仅 A 强制自身剩余待发、补灵、进入第2轮；B 继续第4行 |
| 40 | 第2轮第1行 | 第1轮第4行 | 无 |
| 50 | 第2轮第2行 | 第1轮第5行 | 仅 B 强制自身剩余待发、补灵、进入第2轮 |
| 60 | 第2轮第3行 | 第2轮第1行 | 仅 A 强制自身剩余待发、补灵、进入第3轮 |
| 150 | 第5轮第3行 | 第3轮第5行 | 双方各自轮末；刚配对的数据不能再次直击或 Apply |

不同轮长本就代表不同节奏，不加共同轮次屏障，也不按时间给灵元供给做自动归一化。开场抽取发生在 Tick 0。日志内部行/列从 0 起，轮从 1 起。交换参战者注册顺序不改变同种子下的可重放轨迹。

### 4. 伤势优先占用可用空间并保留 SP 判负

保留当前 `SP > SpMax` 判负，HP 清零仍走伤势及恢复流程。设计约束是 SP 容量不超过背包有效空间，而非把 SpMax 自动设为格数，也不是禁止当前占用在败退判断时超过 SpMax。

伤口本质是一张 Card，必须按自身完整形状强行插入，不能将其 Size 个格子拆开散放。先寻找全部为空格的完整位置；若无法仅用空格，则允许该完整位置内的灵元让位，被替代的灵元移除，伤口按 Size 计入 SP。每一阶段按行从上到下、列从左到右选择首个合法平移位置。用户已确认由设计保证存在完整位置；不能仅依据空格加灵元格总数判断成功。若输入违反保证，报告布局/内容数据错误，插入保持原子性；不拆格、不挪动或覆盖其他卡、不丢弃伤口继续运行，也不将其转换为背包满判负。

### 5. 可观察事件支持验收

建议战斗日志记录参战者、Tick、轮次、行列号、灵元起点/分配目标/原地保留、完整扫描时机、使用/未使用原因、待发入队、对拼及带所属者的轮末直击；同时记录实际生成量/MP 扣除及伤口替代灵元事件。固定初始布局和随机种子复现案例，不依赖 Godot 动画验证结算正确性。

| 类型 | 关注点 | 当前处理 |

### 三、机制本身的取舍（不是缺陷）

- **窄而高 vs 宽而矮**：每行最多一张意味着矩形背包每轮发动上限不超过行数；高度增加也延长补灵和强制结算周期。资源足够时，每秒出手上限仍是每行一次，不能仅因高背包每轮出手更多就认为其单位时间输出更高。
- **上下左右位置影响资源到达时机**：右侧灵元不会提前满足左侧卡，资源跨轮保留会使本轮未能发动的卡有积累机会；不额外假设只能给尚未扫描的卡供灵。
- **需求筛选会缓解最近卡一直截流**：卡不再需要资源就退出本次分配候选，较远需求卡仍可获得灵元；每行一次的顺序压力仍然存在，可用固定布局演示。
- **短轮背包更频繁进入自身轮末**：这是用户确认的节奏差异，不按时间自动平衡供给、不等待长轮背包、不让对手随之提前强制结算。
- **空间饱和会压低实际补灵**：空格足够时主要区别是落点分布；不足时依 E 截断生成量，并同比少扣 MP。伤口占用灵元格也会进一步挤压后续供给。

### 四、原代码接入风险（提案阶段观察，修复证据见 implementation.md）

| 位置 / 问题 | 对实施的影响与建议 |
| --- | --- |
| `CombatCard.Use()` 调用 Contest 后才根据 Ready 和 InPending 判断 Apply；FaShu.Contest 清 Ready 并写 Finished，可能覆盖卡脚本刚写入的 InPending | 无拼点卡可能跳过 Apply，拼点卡状态也可能提前结束。扫描接入必须有“无拼点效果一次、有拼点完成后一次”的断言，不能直接沿用旧状态组合 |
| `DrawMana()` 已算 actualCost，却循环 `weights.Length` 次，实际通常生成 5 个 | 不能复用固定循环当生成量；必须符合已确认“实际生成 2 个只扣 2 个成本”，并让跨轮留下的资源参与空格统计 |
| `CombatScene.Tick()` 对所有 Combatants 推进与使用，未在这些循环统一过滤 IsActive | 败退者可能继续计时、供灵或入槽；扫描调度必须明确停止非存活参战者并处理其待发状态 |
| `Run()` 返回新的空 CombatResult；EndCombat 构造的结果未被保留；日志使用 survivors.First() | 自动验收可能拿不到真正结果，双方同时败退时日志可能异常。建议单列最小修复任务，使胜负与轮数断言可靠，不能声称现有结果回写链路已正常 |
| `ApplyHeal()` 算了上限截断值 val，却把原 amount 传给 RecoverHP | 治疗可能超过上限，影响新节奏的对比测试；单列独立问题，避免归因于扫描机制，此提案不默认扩成治疗系统重做 |
| 新伤势卡通过 AddWound → 延迟 Add 入 Field，Add 分支没有完整调用 PreStart/Start | 新背包不仅需要可放置位置，也要明确新卡生命周期；仅把伤势加进占格表不能保证其效果可运行 |
| CardBaseData 共用按 Id 读取；Lua CardData 数值覆写代码目前被注释；JSON 与 Lua 中重复出现 Size/CD/ManaCost | 新形状/费用须选单一权威来源并迁移定义，不能只改 Lua 示例就当作实际数值已改；运行时资源独立保存 |
| 现有主规格多为旧 delta 格式，缺 Purpose，CLI 概览会报告 requirements 0 / 缺 Purpose | 本次只验证本 change；主规格格式整治是独立事项，归档前需处理相关基线格式，不能把当前 CLI 的 0 当成没有历史要求 |

## Risks / Trade-offs

- [同时保留旧调度] → 移除主动卡旧 CD/Ready/全局扣费出手路径，覆盖法术、招式、法宝和事件触发，防止一行多次使用。
- [空间约束与失败条件冲突] → 按已确认规则让伤势占用灵元格，继续 SP 判负，并验证 SP 上限、有效空间与多格放置边界。
- [触发顺序影响玩法] → 固定行内左到右，轮末入口带所属者；用交换双方注册顺序的测试检测隐式先后手，不改变双方独立节奏。
- [旧卡不适配新规则] → 最小新机制卡组用于核心验收；记录 CD、ManaAdj、AboveAll、法宝触发及候补 API 的影响，旧特殊卡不自动加入测试，也不要求本变更完成全量卡牌重设计。
- [把结构检查通过当作全部细节已定] → 骨干规则以本次确认表为准；算法预留与少量边界单列，不将它们伪装成确定默认值。

## Migration Plan

1. 以本次已确认规则为基线，只补齐实际实施涉及的剩余扫描/资源/队列/伤势边界，距离算法保留接口；H/I 的旧卡设计不作为核心实施前置。
2. 在数据层增加唯一主功法身份、按等级的有效格与固定主卡位置、普通卡形状及 NPC 布局；两种不同行数测试功法均有固定主卡。旧存档/测试配置必须显式指定主功法，无主功法数据报错而非推测。
3. 增加战斗私有背包与扫描状态，接入左到右逐格、需求候选选择函数、跨轮资源及按实际生成扣 MP，再拆开行切换对拼与本方轮末强制结算，接通伤势占用灵元和 SP 判负。
4. 仅用符合新机制的最小卡组验证 Lua 效果调用；将旧对拼数值作为回归基线，补齐日志与可断言测试。旧特殊卡记录待重设计，不在核心入口留自动启用的旧 CD/扣费路径。必要的现有结果/参与者过滤问题独立提交，避免混淆新玩法与旧缺陷。
5. 核心验收通过后再另提 Godot 接线变更。若实施回退，恢复整套调度及匹配的数据版本，不让新布局数据配旧计时器运行。当前局部实施状态与未接入项以 implementation.md 为准。
