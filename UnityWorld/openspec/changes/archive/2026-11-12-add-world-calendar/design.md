# Design

## Context

动机见 `proposal.md`，行为合同见 `specs/world-calendar/spec.md`。本次属于新增时间数据模型和兼容接口的设计，需要明确年界与迁移边界。

核查到的当前实现：

- `Scripts/Game/World/WorldTime.cs` 是静态秒时钟：`CurrentTick` 为调用次数，`DeltaTime`、`TotalTime` 为浮点秒数；还承载随机种子。没有年月、月相和节气。
- `WorldMgr.Tick(float)` 先推进秒时钟，再同步遍历领域及玩法管理器，最后处理主位面元气。`scripts/client/GameBootstrap.cs` 的世界宿主每个物理帧调用它。
- `StoryMgr` 自己累计秒数；`TileSystemAura` 按每秒变化率计算。既有世界生成规范也明确保留每秒元气语义，不能把周数直接作为它们的步长。
- `WorldMgr.Initialize()` 在全部地图发布成功后调用 `WorldTime.Initialize(seed)`。`MapRuntimeTests` 已覆盖失败不改时间、成功重启重置时间。
- `Program.cs` 是现有控制台测试分派入口；`Console/UnityWorld.Console.csproj` 自动纳入 `Scripts/Tests/**/*.cs`。纯时间测试可以在创建世界前分派，避免加载 Lua 和生成地图。
- `SaveModel` / `SaveMgr` 尚为空壳；本次不引入完整存档。相邻探索 UI 变更仍是独立预览，不能顺手把它当作真实周历客户端。

## Goals / Non-Goals

**Goals:**

- 周历只保存一个整数时间值，其余日期字段纯推导；单次读取、投影和一周推进不依赖世界对象数量。
- 交付可以独立构造、查询和验证的后端模型，以及现有 `WorldTime` 的兼容接入。
- 节气不仅有名字表，还要可查询当前节气、判断变化、发出变化通知。

**Non-Goals:**

- 不把“玩家阶段”、对象类型或优先级加入周历数据；对象标记及调度另做。
- 不实现周任务队列、分帧预算、对象交互事务、NPC 周行为、移动或前端。
- 不用本轮固定五十周历复刻真实公农历的日、时刻、闰月和天文月相；现实算法用于年份天干锚定。

## Decisions

### 1. 一份已过周数，加不可变日期投影

建议在 `Scripts/Game/World/` 放置 `WorldCalendar`、`WorldDate`、相关枚举和 `WorldCalendarTransition`。`ElapsedWeeks` 为非负 `long`，从 0 开始；日期投影不可变，不公开分别设置年、月或月相的入口。独立构造可接收合法周数用于推导和范围测试，但不等于实现存档。

| 字段 | 类型建议 | 含义 |
|---|---|---|
| ElapsedWeeks | long | 从 4000 年新年经过的周数，唯一可变时间值 |
| Year | long | 4000 加完整经过的年数 |
| WeekOfYear | int | 年内第 1 至 50 周，包含两个特殊周 |
| PeriodKind | enum | NewYear、Regular、NewYearsEve |
| YearStem | enum | 按年份算出的天干 |
| Month / WeekOfMonth | int? | 普通月 1 至 12 / 月内周 1 至 4；特殊周为空 |
| MonthBranch | enum? | 寅月至丑月；特殊周为空 |
| MoonPhase | enum? | 四个月相；特殊周为空 |
| SolarTerm | enum? | 二十四节气；特殊周为空 |

规则先定义清楚：`yearOffset = ElapsedWeeks / 50`，`slot = ElapsedWeeks % 50`。槽位 0 是新年，49 是除夕；1 至 48 为普通周。普通周令 `regularIndex = slot - 1`，则月份为 `regularIndex / 4 + 1`，月内周为 `regularIndex % 4 + 1`，月相索引为 `regularIndex % 4`，节气索引为 `regularIndex / 2`。

数字例子：已过 48 周是当年第 49 周、十二月第四周；已过 49 周是当年第 50 周、除夕；已过 50 周才进入 4001 年新年。

选择整数推导是为了避免浮点累计误差及重复存储字段不同步。直接使用 `ElapsedWeeks % 4` 计算月相不正确，因为新年、除夕是额外周。普通周的月相必须从月内位置推导。

### 2. 现实纪年锚点与固定游戏年内规则分别计算

天干表为甲乙丙丁戊己庚辛壬癸，零基索引为 `(Year - 4) % 10`；全部支持年份均为正数。4000 年索引 6，为庚；4004 年为甲。月份地支固定从寅开始，不因年份天干变化而改变。

依据：香港理工大学应用数学课程资料给出现实公元年份换算干支的方法；其一基“年份减三”写法在这里等价转换为零基“年份减四”。按六十年循环推算，4000 年为庚子，但当前格式只展示年天干。天干在游戏新年换年时切换，不按真实日期查立春或春节时刻。

- [香港理工大学：干支纪年换算](https://www.polyu.edu.hk/ama/profile/hwlee/AMA1D01C/CNY.pdf)
- [香港天文台：天干和地支及月份对应](https://www.hko.gov.hk/sc/gts/time/stemsandbranches.htm)

### 3. 节气覆盖普通周，特殊周明确为空

节气名称用固定枚举和只读名称表，不增加可编辑 JSON 或新的配置加载机制。每月两段分别占前两周、后两周：

| 月份 | 地支 | 第一、二周 | 第三、四周 |
|---|---|---|---|
| 1 | 寅 | 立春 | 雨水 |
| 2 | 卯 | 惊蛰 | 春分 |
| 3 | 辰 | 清明 | 谷雨 |
| 4 | 巳 | 立夏 | 小满 |
| 5 | 午 | 芒种 | 夏至 |
| 6 | 未 | 小暑 | 大暑 |
| 7 | 申 | 立秋 | 处暑 |
| 8 | 酉 | 白露 | 秋分 |
| 9 | 戌 | 寒露 | 霜降 |
| 10 | 亥 | 立冬 | 小雪 |
| 11 | 子 | 大雪 | 冬至 |
| 12 | 丑 | 小寒 | 大寒 |

这是每两普通周一个节气的游戏化安排；真实节气按太阳黄经每隔 15 度划分，不能把现实节气日期表当作本游戏的年内时间表。[香港天文台：二十四节气](https://www.hko.gov.hk/sc/gts/time/24solarterms.htm)

特殊周显示“年份（天干）年 新年／除夕”，普通周显示“年份（天干）年 月份（地支）月 月相”；节气单独查询。特殊周不假装属于上一月，也不多走一次月相。选择空值而非延续大寒或立春，是为了让未来玩法区分“节日特殊周”和“普通节气周”。这属于本提案可供审阅的默认设计。

### 4. 推进接口只提交时间，通知只用于观察

`AdvanceWeek()` 计算并验证下一周日期，保存新周数，生成不可变的 `WorldCalendarTransition(Before, After, SolarTermChanged)`，然后依次发送 `WeekAdvanced` 和有条件的 `SolarTermChanged` 通知并返回结果。每次只推进一周，先不提供跳过中间边界的快速批量推进。

节气变化按可空的前后节气身份比较。例如大寒到除夕为空会触发变化；除夕到新年两者都为空，不触发节气变化；新年到立春再次触发。每个普通节气在进入时出现一次，第二周不重复进入。

通知发送期间设重入保护，观察者再次推进应明确拒绝。每个观察者异常分别捕获、记录并继续分发，异常不回退已提交时间，也不把成功推进变成可重试的失败。无世界日志实例的独立使用场景可用标准诊断输出兜底。通知不是事务性的玩法执行器，未来天气或产出结算不得作为本轮观察者暗中接入。

周历按单线程调用设计，与现有核心一致；分批执行或多线程不会自动变成时间跨度。未来结算器可以在整周世界结果完成后调用此入口提交周历，但本次没有结算器，也不宣称已经实现世界事务。

### 5. 在现有入口增量接入，保留旧时钟语义

`WorldTime` 保留 `CurrentTick`、`DeltaTime`、`TotalTime`、`RandomSeed`、`Advance(float)`。新增当前周历查询和显式 `AdvanceWeek()`；旧 `Advance(float)` 不调用周推进，周推进也不反过来调用 `WorldMgr.Tick`。需要文档明确“周历是游戏日期；旧秒时钟是待迁移系统的旧计时”，它们之间没有默认换算关系。

`WorldTime.Initialize(seed)` 建立新的初始周历实例，旧观察者不挂到新实例。沿用 `WorldMgr` 已有的成功初始化末尾调用，不提前清空旧时间；`WorldMgr.End()` 仍不擅自重置最后日期。失败初始化、创建额外位面、地图候选生成都不改变周历。

不修改 Godot 物理帧驱动和既有管理器 Tick，因此旧世界系统仍按当前方式运行，但不会带动新周历。停止旧自动 Tick、迁移故事和元气单位是后续完整周结算变更的工作。本提案没有用两个会自动互相换算的时钟维护同一份日期。

### 6. 必要注释与验证入口

在新增值类型写明单位、索引和特殊周空值语义；修改 `WorldTime` 时注明旧秒接口与周接口的边界。在 `Program.cs` 增加 `--world-calendar-tests` 的早期分派，放在整体世界初始化之前；现有项目文件已经包含测试文件，无需仅为纳入文件修改 csproj。

测试重心是独立可观察规则：年界、所有月份和节气、天干锚点、通知次数和异常、范围错误、秒周隔离。已有地图生命周期测试只增加与周历有关的断言，不扩展水文或批量地图基准。

## Risks / Trade-offs

- [新旧时间并存容易被误用] → 命名、注释和独立测试明确单位；后续系统接入周历时单独迁移，禁止乘 604800 后调用旧 Tick。
- [特殊周的空值被前端当成普通枚举零值] → 值类型显式区分特殊周，可空字段配合独立格式化；当前不做前端。
- [观察者被误用为世界结算事务] → 文档限定为已提交时间的只读通知，不在回调中加入 NPC 行动、购物或环境收益。
- [旧字段仍是 int/float] → 保持兼容，本轮新增周数独立使用 long；不顺手改变战斗快照或旧 API。
- [开局和特殊周规则与探索预览不同] → 保持相邻变更不动；真实周历后续接入时再更新对应预览规范和画面。

## Migration Plan

1. 增加纯数据、换算、格式化、节气和推进模型，先独立验证。
2. 给 `WorldTime` 增加兼容门面并沿用初始化位置，接入控制台短测试和必要的生命周期断言。
3. 后端验证通过后交付 API 说明，供后续前端和调度变更使用；本次不自动启动任何新世界循环。
4. 回退仅撤销新增模型和门面，不涉及玩法数据或存档格式迁移。当前没有已发布周历存档需要转换。
