# Main Keyword 的运行与迁移设计

## Context

[方案](proposal.md)确定了唯一 Main、共用行额度和装备自带招式。[增量规格](specs/keyword-system/spec.md)定义四类卡的行为。本设计解决如何在装配前获得可靠的 Main、如何按末格提交发动，以及如何让现有内容通过新校验。

本次按 `Data/Card` 的 268 条 JSON 定义核对。241 条恰好显式配置 `FaShu`、`FaBao`、`Passive`、`ZhaoShi` 中的一个，25 条缺失，2 条冲突。战斗加载 Lua 后还会追加 `Keywords`、旧 `CardData.CardType` 和派生 Keyword。现有 15 张招式都是 1 格、空灵元需求且标为 `Unmigrated`。补齐 Main 和完成效果迁移是两项独立的验收结果。

## Goals / Non-Goals

**Goals**

- 在卡定义、世界卡、模板预检和战斗快照之间共用 Main 判定。含旧内容的卡按确定的规则迁移后才能创建。
- 把发动和资源提交收回到扫描末格，保留现有灵元分配、冻结解除及拼点调度。
- 保留现有卡牌 ID 和装备实例绑定。先用可追踪的长剑、剑斩、剑刺链验证规则，再用可引用的招式覆盖现有装备清单。

**Non-Goals**

- 范围限于当前内容和需要的兼容检查。完整世界存档功能、旧招式串行 CD、角色习得招式、自动排包和未确认的平衡重做各自留在原有范围。

## Decisions

### 在装配前解析唯一 Main

保留卡定义的 `Keywords` 列表。用 Keyword 注册定义保存 `Main` 标记，由一处公共解析和校验提供结果。卡库和模板预检读同一份可只读查询的角色元数据，战斗初始化使用已校验的 Main 及卡的独立 Keyword 快照。这让定义校验可以在创建运行时实体和执行战斗效果之前完成。

卡的 Main 以迁移后的定义或明确的旧输入转换结果为准。战斗 Lua 的普通 Keyword 附加和 `CheckCondition` 仍可工作，追加结果经过唯一 Main 校验。迁移已有的 Lua 主词声明到 JSON，避免同一张卡在装配时和战斗里得到不同答案。`ScanActivatable` 只作为识别旧扫描夹具的证据，使用入口按解析出的 Main 决定。主功法实例的 `IsMain` 仍表示主功法位置和身份，与 Keyword 的角色声明分别处理。

解析失败须给出卡定义 ID、相关 Keyword 和输入位置。预检、导入及正式装配共用该诊断。保留草稿的原条目，以便用户修正配置。卡牌生成路径也显式给出 Main，尤其是测试夹具和战斗中动态插入的伤口。即使卡没有效果脚本，系统也能从 `Passive` 确定它的运行方式。

### 在末格一次提交发动，并处理法宝到期

每一方的扫描行持有一份发动额度。到卡的末格先判断是否到期、是否冻结和该卡能否提交。只有资格齐全才同时提交蓄灵消耗、行额度，以及适用的招式本轮次数。发布发动事件和执行卡脚本发生在提交之后，避免同步派生事件重复占用本行。失败保留原蓄灵和剩余额度，扫描仍继续。需要拼点的法术或招式沿用待发槽和后续结算。

法宝在战斗实例上记录被动是否激活。首次发动打开被动，下一次真实扫到本卡末格时续上或关闭。续期复用当前激活状态，避免重复注册监听。激活期间可以为下一次续期蓄灵。即使行额度已经用完、法宝缺灵或冻结，末格也要处理到期。冻结在本次跳过发动后解除。激活窗口按实际末格访问推进，速度变化和移位直接反映到窗口长度。法宝离场时停止其在场被动。

常驻 `Passive` 使卡入场就处于激活状态。旧卡若有明确的开场效果，保留其预期的一次执行，例如兽皮的斩击抗性。空被动只建立激活状态，不额外发出 `Apply` 或 `OnApply`。这保留了原本只占格伤口和无效果材料的事件行为。

### 用父装备实例供给招式和攻防

从已装备实例的生效 `FormList` 枚举应装配的招式。每个条目对应一张招式卡，按父装备实例归属。模板继续用显式位置和 `ParentPlacementIndex`，编辑器内部继续用稳定条目 ID。装配或预检应比较每件装备所需招式与实际位置条目，检查定义、归属、数量、占格和 SP。缺少位置或超出容量时报告问题，由配置显式补齐。

普通获得链通过装备清单建立来源明确的招式卡。重复排包和加载要按这一绑定复用已对应的实例，避免每次检查再发一次卡。模板的显式条目直接生成绑定实例，按同一规则检查缺失和多余。卸下或更换装备后重新校验其招式和位置。装备及招式可在战斗中有各自的实例状态。招式对拼每次读取自己的父装备，不按同名卡推测归属，也不以父法宝的被动开关作为使用资格。

招式成功次数按「本方背包轮次 + 招式实例」记录，默认一轮一次。以本方扫到底进入下一轮为界。移动位置或同名招式在别的装备上发动，都不会刷新原实例的本轮记录。保留公共装备属性读取能力，迁移 `UseFabao` 时把仍被招式调用的 `GetEquip` 与法宝旧发动入口分开。

## Migration Plan

### 1. 显式补齐 268 张现有定义的 Main

先按原始 JSON 和实际匹配的 Lua 脚本列出每张卡的归类，再把结果写回定义。保留普通 Keyword、卡牌 ID 和原有有效效果。兼容状态继续独立判断。

| 旧定义 | 迁移规则 | 当前数量或例子 |
|---|---|---|
| 四种 Main 中恰好一个 | 沿用该词。将 Lua 针对同一 Main 的重复声明并回定义。 | 241 张，包括剑斩和长剑。 |
| 只有 `Wound` | 加 `Passive`，保留 `Wound`。已配置的伤口效果仍按自身实现。 | 12 张，含 2 张占格测试卡和 10 张未迁移的旧伤势。 |
| 只有 `Item` | 加 `Passive`，保留 `Item`。兽皮保留 Lua 原有开场效果，其余素材按已有状态处理。 | 7 张，其中兽皮已迁移。丹药类内容同样由实际运行方式归入 Main，丹药身份保留为普通 Keyword。 |
| 无 Keyword 的主功法测试卡 | 显式加 `Passive`。 | `bp_main_6x5`、`bp_main_8x3`。 |
| 只靠 `ScanActivatable` 打开扫描的测试卡 | 显式加 `FaShu`，继承原费用和测试用途。 | `bp_attack`、`bp_charge`、`bp_guard`、`bp_focus`。已带 `FaShu` 的纳音卡继续用原 Main。 |
| 同时有 `FaBao` 和 `Passive` | 按原运行时走主动法宝的归类，显式保留 `FaBao` 为唯一 Main。 | 铠甲、利爪共 2 张。保持未迁移。 |

按这份清单迁移后，当前目录应为 `FaShu` 183 张、`FaBao` 3 张、`Passive` 67 张、`ZhaoShi` 15 张，合计 268 张。

兼容导入先按已知定义 ID 和迁移映射修复旧结构，再执行正常校验，保留普通 Keyword、装备归属和实例位置。遇到无法唯一确定的输入，指出具体卡及原因，由数据显式选择。现有世界 `SaveMgr` 及卡牌的 Save/Load 是占位实现。本次实现围绕实际在用的卡定义、项目与个人模板导入，以及程序构造入口，复用同一套校验供未来世界读入使用。

### 2. 迁移三张现有法宝

| 现有内容 | 迁移办法 |
|---|---|
| 长剑 `card_fabao_jian` | 保留 ID、标签、2 格、2 金灵元及长剑装备数据、招式清单。移除 `OnBaseManaDraw` → `UseFabao` → 射击拼点的旧链路，将 `ProducesContest` 改为 `false`，卡面说明改为新的胜利触发被动。 |
| 铠甲 `card_fabao_kaijia` | 保留 `FaBao`、普通词 `Armor`、1 格和 1 土灵元。删除冲突的 `Passive`，保留 `Unmigrated`、旧说明和缺失效果原因，直至有对应被动和验收。 |
| 利爪 `card_monster_lizhao` | 保留 `FaBao`、1 格和 1 金灵元。删除冲突的 `Passive`，保留 `Unmigrated` 和缺失效果原因。装备清单里的抓击单独按招式迁移。 |

长剑被动沿用已定的「斩击对拼胜利后，下次招式对拼点数 +1」。以真实对拼胜利事件 `OnContestOverflow` 的胜者、来源卡和 `WinnerType=Zhan` 判断，效果来源归激活的长剑实例。对拼双方比较点数前消费有效加成。这个时点让已经失败的扫描、待发槽拒绝、轮末直击以及当前已结束的对拼各自保留原义。

首版内容口径按同一参战者的斩击获胜触发，下一次其招式参加双方对拼时使用。每个长剑实例只存一份待用 +1，连续胜利刷新它，连续续期保留它，激活结束时清除尚未使用的加成。这是长剑单卡的迁移口径，Main 只负责开关被动和续期。攻击 4、防御 3 等装备基础属性照常给绑定招式读取。

### 3. 迁移招式和装备装配数据

15 张旧招式全部保留唯一 `ZhaoShi` 和现有 ID。以 JSON 的 1 格为准，清掉 Lua 中旧的零格、空费用、`CardType` 和独立 CD 等过时声明，保留卡自身的 `Contest` 或 `Apply` 效果。招式的匹配灵元在招式定义中明确配置，同定义复用同一费用。攻防底值与元素读取来自实际绑定的装备及其卡实例。

| 现有装备 | 生效招式 | 迁移验证 |
|---|---|---|
| 短剑 `short_sword` | 剑刺 `card_form_jian_ci` | 复用剑刺定义，读取短剑攻防。 |
| 长剑 `long_sword` | 剑刺、剑斩 `card_form_jian_zhan` | `test_npc_a` 保留第 3 条长剑绑定，显式补两张单格招式及合法坐标，父条目设为 3。用正式预检核对容量和 SP。 |
| 巨剑 `great_sword` | 剑刺、剑斩、剑气 `card_form_jian_qi` | 同名招式读巨剑数据，各自有实例和每轮次数。 |
| 利爪 `monster_claw` | 抓击 `card_form_strike` | 保留抓击的刺击效果，验证招式和父装备读取。利爪法宝另按上表评估装配状态。 |

首批给装备已经引用的四张招式配置验证费用，建议每张 **1 格、1 金灵元**，采用当前长剑和利爪的金系配置作为迁移基准。确认其真实效果和装配链通过后再调整各自的兼容状态。其余 11 张未被现有装备列表引用的招式先完成结构清理，保留 `Unmigrated`，待有对应装备、费用与效果验收再开放。孤立的旧脚本 `card_form__strike.lua` 需与实际匹配定义的 `card_form_strike.lua` 区分，迁移按定义 ID 生效。

`test_npc_a` 的原布局使用 10 SP，上限是 11。剑斩和剑刺各占 1 SP，补齐会达到 12 SP。建议在这份测试模板中把神识从 **11 调到 12**，保留原七张卡，并把剑斩放在当前空格 **(5,3)**、剑刺放在 **(1,5)**。这两张卡的 `ParentPlacementIndex` 都设为 **3**。验收时同时检查实际占格、SP 和两条装备绑定。

### 4. 同步切换并验收

按「登记及校验 → 数据补 Main → 扫描和装备规则 → 内容迁移 → 验收」实施。在启用严格校验前让正式目录和测试样本都具有明确 Main。兼容判断与效果迁移后的数据一起交付，避免只切运行时导致现有合法模板无法加载。用正式模板验证长剑和两张招式，用定向样本验证同名绑定、续期失败与冻结。回滚时将代码和对应配置作为一组恢复，保留模板草稿的旧版源数据供重新导入。

## Risks / Trade-offs

- 未迁移内容加了 Main 后看起来更完整。仍由兼容状态阻止装配，旧卡报告分别列出 Main 校验和效果可用性。
- 装备关联按卡定义 ID 会误把两件武器的同名招式算成一张。预检、导入和战斗均以装备实例和位置条目为绑定依据。
- 旧法宝事件测试、扫描夹具和真实模板依赖原有行为。先建立替换断言，再移除旧事件入口，保留原事件上下文及对拼调度的回归覆盖。
