# Design

## Context

动机和能力范围见 proposal.md。以下是当前源代码的只读检查结果，不代表已实现本设计。

| 位置（相对仓库外层） | 当前行为与设计影响 |
| --- | --- |
| `Xianxia.Client.csproj` | 同进程引用纯 C# 核心 DLL；本轮的“包”是内存值对象，不涉及网络 |
| `scripts/client/battle/BattleObserverSession.cs` | 324 行，控制 Tick、采集快照及订阅玩法事件；每步有 FrameCommitted，但视图在 Update 后只刷新最后快照 |

既有 `battle-ui-observer` 的三份能力仍在未归档 change 中，主规格尚未包含它们。本设计追加 stream/playback/projection 三项能力，不覆盖其全部 UI、素材或会话规格。旧变更关于“核心不改”的历史验收保留；本次允许观察数据及纯查询所需的 C# 修改，规则和数据保护仍成立。旧暂停“取消瞬态”由本次“逻辑停、已提交短动画收尾”替代。

## Goals / Non-Goals

**Goals:**

- 以一次成功 Tick 为交付边界，保留中间事实、顺序和关联；UI 不重新算分配、伤害或对拼。
- 核心只输出引擎无关值，客户端独立决定曲线、时长、颜色和锚点。
- 每个动画都能中断、收尾或从快照恢复，记录读取不会改变规则和随机状态。
- 拆分真实职责，使新增动画不会继续扩大主视图及会话类。

**Non-Goals:**

- 网络服务器、RPC、线程并行模拟、完整事件溯源、任意时间回滚及同进程确定性重开。
- 修改资源支付、扫描排序、对拼公式、卡牌资格、伤口布局或 JSON/内嵌 Lua 内容。
- 引入核心 Godot 类型、反射修改私有状态、新图片生成或角色骨骼动画。

## Decisions

### 1. Tick 快照加有序事实，采用批量拉取

计划新增纯 C# `CombatPresentationEvent` 家族及战斗场景持有的观察缓冲。事件为不可变值记录/只读深复制集合，公共头包括 Tick、场景内 Sequence、Kind、可空的 ActionId/ParentActionId/ContestId 和实体 ID。会话包装成 `BattlePresentationFrame`，包含 SchemaVersion、SessionId、Tick、Snapshot、Events 及序号范围；具体名字允许实施时调整。

```text
CombatScene.Tick()
    --> append facts to scene-local buffer
    --> return successfully
BattleObserverSession
    --> take copied facts + capture end snapshot
    --> commit one immutable frame
BattlePresentationPlayer
    --> schedule visual transitions
    --> settle to committed snapshot
```

- Scene 只追加记录，Tick 结束后由会话拉取；不在结算栈中同步回调 UI，不接入玩法 EventMgr，也不使用全局静态事件。
- 初始化作为 Tick 0 批次，带初始化标记；初始已有卡直接显示。每次 Advance 都提交一批，即使事件为空；视图订阅每次提交，不能继续只看 Update 后的最后快照。
- SessionId 来自客户端会话生命周期，不能消耗核心 Rng。重复刷新按 SessionId + Sequence 去重；Tick 连续性及版本不符有诊断。
- 正常 Tick 返回后完成事件复制和快照才提交。若 Tick/采集失败，保留最后完整批次，未完成记录只写明确标记的诊断；不假装能够回滚核心部分操作，也不发布成功帧。
- 核心缓冲在转交后释放，旧完整事实可流式写现有会话日志。未启用观察时不积攒事件；客户端待播队列独立设上限。新字段不写入 JSON 定义。

选择依据：当前状态差值无法可靠重建中间过程；直接 C# 回调容易把 UI 失败带进规则执行；完整事件溯源需要重写状态来源，超出本轮需求。

### 2. 事实记录与插入位置

| 计划记录 | 必要数据 | 插入位置与注意事项 |
| --- | --- | --- |
| ManaAssigned | 角色、源格、元素、卡实例及定义、分配前后元素/计数 | 实际 TryAssign 成功后的事实点；不对 Convert、Reduce 或伤口覆盖假装分配 |
| CardUsed | 卡身份、独立使用 ID、资源前后值 | TryCommitUse 的资格提交与 BeginNextActivation 复位处；失败不发，不能等 Apply 才复位 |
| PendingChanged | 槽所属角色、入/出、使用 ID、卡身份、拼点类型/值/元素 | 实际入槽及取走位置；同 Tick 出入仍完整保留 |
| ContestResolved | 唯一对拼 ID、双角色/双卡/双使用 ID、双方数值、结果/差值 | ResolveContest 对双方与结果已明确的位置，覆盖平局早返回；不能只订阅 OnContestOverflow |
| DamageResolved | 来源 ID/卡及关联、目标、HP before/after、扣血量、盾吸收量 | DamageIn 与护盾后，在 OnDamage 可能派生效果以及 HandleHpZero 回血前保存本次事实 |
| CardAddedToBackpack | 角色、卡身份/名称/需求/形状值、实际 cells、被替代灵元 | DealFieldChange 完成实际放置及入场流程后；AddCombatCard 请求不发成功记录 |
| CardApplied | 卡所属角色、实例/名称、独立生效 ID、使用/对拼或被动来源关联 | 成功完成 Apply 的一次语义生效；被动实际效果按下一节记录 |

记录在操作对应的事实点取值，不在 Tick 末再读已被清空或覆盖的数据。卡牌身份包含实例 ID 与定义 ID，名字在记录时复制。需要延迟处理的伤害/入包在队列项上保存纯观察关联元数据，不替换伤害的玩法来源、目标或基础数值。

对拼记录表示已经决定的双方和结果，发布顺序位于相关后续效果前。伤害队列可能稍后结算，须携带 ContestId/ActionId；不能用同 Tick、同名卡或原始日志进行配对。现有 OnUse/OnApply 继续用于玩法和原始记录，UI 特效只消费新的 typed records，避免双重提示。

### 3. 生效提示覆盖主动与实际被动效果

正常 Apply 以其独立 invocation 为一次生效，守卫提前返回不记录；成功流程即使没有额外 Lua 数值变化，仍保留核心认定的生效。赢家、输家和平局的 Apply 均按实际执行记录。

被动 Hook 的调用不等于生效。对 `InvokeOwnHook`、关键词 Hook、直接卡牌事件回调的 C# 边界建立场景内观察作用域，保存“当前实际执行卡”，不得把传入 ctx.SourceCard（可能是引发事件的攻击卡）错当被动效果所属卡。在现有 C# 战斗动作的实际提交处标记 effect committed：如治疗实际恢复、护盾变化、成功 Buff/属性修正、资源或扫描状态变化、有效伤害/入包请求入队等。零变化、无目标、仅条件检查或失败请求不标记。

同一被动 invocation 首次有效提交关联一个 EffectId，成功退出时产生一次 CardApplied；后续实际结果继续携带关联。主动 Apply 内的多次动作归入同一生效，不每个 API 再弹一次名字。嵌套的其他卡效果使用栈保存各自 ID，finally 清理，不能修改玩法调度或阻止原回调。修改仅限必要 C# 边界及动作提交标记，不修改 Lua 数据。

实施第一组具体核查需形成当前运行卡/关键词到这些 C# 路径的覆盖表，特别验证绕过 API 直接操作实体的路径；该核查是确定剩余标记位置，不重新决定架构。无法归属的效果必须报告缺口，不以“所有 Hook 都生效”代替；所有当前可执行的实际卡效果通过验收后才可声称“任何卡生效均提示”。

### 4. 上限读取复用规则并隔离计算状态

在核心 Stat 层提供只读读取/批量投影入口，向会话返回当前 HpMax、MpMax、SpMax 整数值。它与正常 Get 采用同一套修正、Override、Clamp 和定义边界规则，不能在客户端写 QiXue×2 等公式。

计划抽取纯求值内核：输入为属性条目的值副本、修正值集合、对应定义及必要缓存参数；输出为数值。常规查询保留原脏检查和写回行为，只读查询保留当前缓存有效性语义，脏条目在隔离上下文中求值，不清除原 dirty 标记、不写原 final cache。公式求值使用本次查询独有的表达式/参数对象，不借用会修改 Parameters 的静态 Expression 实例。不会借此次优化重排全部派生属性依赖或修正历史缓存失效规则。

先以两个等价属性状态对照：一个只读投影，一个正常 Get；再验证只读前后的原条目、脏标记、最终缓存、共享表达式参数完全一致。覆盖修正移除、夹紧、浮点转 int、缺失条目、同公式双角色交替读取及连续战斗。已有 Snapshot().Get 路线因共享表达式和重建脏状态，不直接当成正确实现。

面板按快照展示三个当前值/当前上限，SP 使用角色 SpMax；护盾不新增虚构上限。真正零上限可显示，异常明确标记并诊断；不能用初始参考值冒充完成。

### 5. 播放队列及逻辑时间

播放器维护最新提交快照、按序排队的事件及受影响对象的短暂显示状态。普通属性可按当前批次更新；存在待播过渡的卡/待发槽由相应事件暂时驱动，完成后对齐该对象已处理到的快照边界，不能用一个较旧动画回调覆盖更新后的视图。事件不触及的状态仍来自快照。

同一张卡的资源过渡和同一待发槽的短位移保持必要顺序；无关角色/资源飞行以及不同 Tick 可并行。名称与伤害数字只等待触发它们的必要前置，不把整个淡出寿命作为卡、角色或对拼链的排他锁。若事件在新卡入包后立即作用于该卡，先完成/压缩入包再显示其后续效果。所有动画使用客户端显示时钟，不等待动画结束才调用正常战斗逻辑。

2026-10-31 用户实测修正：禁止整 Tick 播放屏障。提交下一批时立即更新最新快照并安排新事件，只对仍在过渡的卡资源或待发局部覆盖；旧 cue 完成只释放对应覆盖，不能写回旧整帧。扫描线及其行进度直接消费 session 最新快照，与播放器收尾完全分离。同一人物的多次名称/伤害提示同时存在，使用存活期固定的文字槽位避免覆盖或跳动。

以下是本提案的可调默认值，不是已验证的最终美术参数：灵元飞行约 0.18 秒，卡牌入包约 0.40 秒，对撞约 0.25 秒，名称约 0.70 秒，伤害约 0.80 秒。预计积压超过 0.8 秒时压缩飞行/等待/淡出，保留基本碰撞与点亮顺序；硬队列默认最多 2048 个事件。超过容量保留日志并提示“已跳过部分动画”，取消旧表现、对齐最新完整快照，从新的消费游标继续，不能静默漏事件后假装完整回放。

暂停停止逻辑累加并让已提交表现收尾；此后静止。单步只 Advance 一次，其表现可继续使用显示时钟；连续点击每次只增一 Tick，队列按序承接。正常结束同样允许末步收尾；重开、退出或场景销毁立即取消并递增显示 generation，旧回调检查 generation 后失效。低帧率/缩放不能改变核心速度或结果。

### 6. 具体视觉与通用组件

- **灵元/点亮**：复用五行图标，从记录的源格到目标卡锚点。卡面底层绘制暗色，再按实际需求份额裁切亮色；默认从左到右，混色采用稳定的元素需求排序，匹配元素点亮其未亮份额。Size 2 水卡严格半蓝；非矩形卡裁切于实际 cells，保持名称和卡图可读。卡面删除 x/x，悬停保留。冻结独立覆盖，满亮等待持续亮，成功 Use 短闪复位；无需求卡不生成虚假进度。
- **卡牌入包**：所属人物附近浮现，再缩小飞入实际占格；背包视图在飞行期间隐藏该实例的静态卡面，避免双份，其他格及真实占用不变。被伤口替代的灵元按入包事实处理，不假装被卡吸收。初始布局直接显示；新卡后续移除按事件顺序处理。
- **待发槽对撞（用户最终明确）**：把当前左右待发槽组件各自拆成固定底框及可移动的内容容器。图、卡名、类型等属于内容容器；两容器向两槽中点短距离运动，碰撞闪光及局部震动，再回到原锚点并按待播状态显示新卡或空槽。空槽字样不参与碰撞。绝不另做一组自由漂浮的副本，也不移动背包卡。即使终态空槽，也使用本批事件在这两个内容容器中短暂重现本次待发身份。胜负只做轻量区别，平局保留碰撞，直击不生成对方。
- **人物头顶**：名称与伤害采用上下两条提示通道，伤害数字更大、有描边；每次伤害错位显示。名称显示所属人物的“卡名 · 生效”，不是受益/受击目标，避免治疗对方时归属混淆。全盾吸收显示“吸收”；扣血使用核心实际减少金额，含负 HP 所体现的溢出，之后回血不抵消数字。
- **缩放/缺图**：锚点取组件坐标并转统一画布空间，窗口变动重算路径。复用现有资源，缺图显示卡名占位，不能阻止事件消费或战斗。
- **连续多格卡面**：根据真实占格四邻接合并同卡内部格缝，图片与底色在该并集上连续绘制，只描外露边界；不同卡的外间距及 L 形空洞保留。长剑图片不再被每格缩进与边框切断。

### 7. 按职责拆文件

计划结构如下，命名可调整但职责必须独立；不为了凑行数机械切 partial。

| 区域 | 计划职责 |
| --- | --- |
| 核心 Combat 观察文件 | 事件值类型、场景缓冲、序号/作用域/来源关联；规则调用点仅追加事实 |
| `battle/BattleObserverSession` | 核心宿主、生命周期、逻辑时钟、批次提交 |
| `battle/BattleSnapshotProjector`、记录适配 | 安全读取、深复制、旧战报记录；无 Godot 依赖 |
| `battle/` 下播放契约/调度数据 | 会话与事件游标、对象依赖、纯值计划，供无画面验证 |
| `ui/BattleObserverView` | 组合组件和连接命令，不再放自动截图和所有绘制 |
| 背包/卡牌视图及效果层 | 格子、tooltip、底色点亮、灵元移动和卡牌入包 |
| 待发槽面板 | 双槽数据、固定框、内容容器、原位对撞与恢复 |
| 角色面板/头顶提示 | 当前/上限、伤害、生效名称布局 |
| 日志面板/会话输出/验证驱动 | 战报展开、文件输出、截图与自动操作，分别脱离主视图 |

公开边界与关键时序补简短中文注释：来源、坐标口径、提交时点、取消条件。实际格坐标沿用核心零基，只有 UI 说明转为 1 起始。不随意删除原脚本，不修改旧预览资源；搬迁须同步现有编译包含与验证入口。

## Risks / Trade-offs

- [生效来源被误归到触发者] → 观察作用域记录执行卡，保留关联 ID；补被动/嵌套与空检查测试，不只依赖 ctx.SourceCard。
- [增加记录改变事件或随机顺序] → 只追加值、独立计数、不调用 UI/玩法总线；观察启停逐 Tick 对照。
- [只读属性重算改变旧缓存语义] → 保留当前 clean/dirty 行为，共用计算规则但隔离表达式状态；不顺带修正属性依赖机制。
- [短动画超过 0.1 秒 Tick 间隔] → 对象级并行、因果约束、时长压缩、有界队列及明确跳过恢复。
- [使用旧回调覆盖新槽/新卡] → 每对象消费位置与会话 generation 校验，快照对齐不倒退。
- [新字段让旧比较器误报] → 分开比较旧玩法字段投影和新表现契约，不删除原校验、不用最终赢家一致代替轨迹一致。
- [未归档旧变更将来引入相反规定] → 本变更明确覆盖点；后续同步时协调核心边界和暂停收尾条款，不在此规划轮暗改旧文件。

## Migration Plan

1. 实施起点记录工作区变更范围、数据/核心版本，取得原控制台和观察器的新进程基线；现有历史 740 Tick 等结果仅作参考，重新运行确认。
2. 先添加可关闭的核心观察及只读投影，再接入会话批次；保留旧玩法事件与原始战报接口。新表现日志使用版本化文件/记录，不强求旧日志自动生成缺失事件。
3. 在既有 UI 外观与场景入口下完成组件拆分和绑定，逐项接入动画；保留独立禁用动画/观察的验证开关，不引入额外生产数据。
4. 完成 V1—V9 和 Godot 实机画面验收后更新 README 与接入说明；所有任务仅在证据齐全后勾选。
5. 回退时可先关闭新表现、以快照恢复静态观察；若撤销核心接口，需同时回退依赖这些接口的客户端构建。保留用户已有修改，不能清空工作区或回退数据。

本轮只写规划，不实施、不同步主规格、不归档旧变更。没有阻止进入实施的产品问题；时长、亮色强度、字距等集中配置并在视觉验收调整。
