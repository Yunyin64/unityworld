# 战斗 TCA 拓展设计

## Context

战斗事件已有场景队列。扫描转移和供能都能往战斗卡充入灵元，但提交点不同。伤势增删通过延迟队列提交。法宝的旧被动回调负责卡自身生命周期。进阶内容沿用已有 Lua 动作、条件与 Aura 注册方式。

## Goals / Non-Goals

完成讨论中的七个基础触发与十项进阶能力。实现复用战斗卡、战斗角色、背包和 Modifier。保留冻结扫描、灵元支付、入槽、位置、伤势和战斗结果现有流程。

## Decisions

- 事件从真实结算点广播。平局按修正后的点数计算。法宝激活和失活取状态边沿，续期取成功发动的原状态。全场监听与本卡原 Hook 独立。
- 灵元充入保留元素、卡、是否充满，扫描在源格释放后发。灵元使用保留成功支付的数量快照，并与发动事件同批提交。
- 伤势获得取实际落格。治愈在移除请求携带原因，实际移除后发，普通离场继续由 OnCardLeave 处理。
- 五行只按 BaseElementBuff 对应的十个确切定义 ID 处理。层数变化取提交前后。免疫在创建或叠层前按施加次数消费。
- 解冻只改卡的冻结状态。冻结 Aura 在尝试冻结时按场上激活来源和共边判断。定身用目标方扫描轮。剥离只操作卡上已收灵元，先进先出。
- 灵盾耗尽带原因。以盾蓄力用实际吸收量汇总，同一供能状态每本方轮最多兑现一次，达标事件供配置动作监听。
- 入阵用位移提交时的方位快照，区分发起卡、被移动卡和参照卡。使用现有占格与共边算法。
- 进阶的触发、动作和条件模板设零权重并在描述标记调整可能。测试覆盖手动调用和抽样池。

## Risks / Trade-offs

触发可在同步分派期间派生更多事件。事件数据取结算快照，关键资源提交完成后再发。位移和冻结等动作在候选选择时验证资格，在实际操作入口复核。
