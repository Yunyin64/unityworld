# 弹药与消耗的结算设计

## Context

`CombatCard` 在 `CombatCardScan.cs` 的 `CommitScanUse` 中提交法术发动、法宝激活和续期。`FaBao.lua` 已经知道一次激活期何时开始、续期和结束。今天 C# 在提交时直接判断消耗、扣份，场景、角色和卡还分别处理灵活离场。弹药上限已从定义复制到战斗卡的 `BaseData`，现有战斗访问器却读另一份初值为 -1 的上限。

## Goals / Non-Goals

让 Mod 作者能从 `Amount.Lua`、`Consume.lua`、`Flexible.lua` 看清什么时候支付、什么情况耗尽后应离场。卡的基础资源和操作保留在 C#，由 Lua 调用。旧分支在原文件重构，保持已有公共入口可用。遇到现有接口无法覆盖的时机或原因，停止实施并报告。符箓与各张法宝的弹量留给各自的内容设计。

## Decisions

### 余弹归战斗卡，物品份数归世界卡

| 数据 | 读取与提交 |
|---|---|
| 弹量上限 | 以 `CardBaseData.AmountMax` 为底值，保留既有有效上限修正入口。统一世界卡与战斗卡对底值的读取，移除战斗卡重复保存的私有上限。 |
| 当前余弹 | 沿用战斗卡实例的 `CurrentAmount`，在本场创建时初始化一次。同场再部署沿用该实例，另开一场从上限开始。耗尽状态直接由余弹得出。 |
| 物品份数 | 沿用世界卡的 `Stack/StackMax` 及它们的战斗快照。保留开战份数用于战果核对，正式战斗按卡 ID 提交剩余份数一次。已离场的消耗卡也参与提交。 |

配置与战前、战中使用同一关键词判定。尤其要消除只配正数 `StackMax` 就在开战后派生出零份消耗卡的差异。弹药随每场战斗恢复。旧丹药移除已退役的 `Preparation` 词名后沿用当前库存。

沿用 `GetAmountMax()`、`IsAmount`、`HasAmount` 和 `ConsumeAmount(int)`。上限从已有定义底值与修正量得出；`HasAmount` 表示至少剩一发。扣弹方法保护下界，并处理无弹药卡和非正扣量。更新文件中关于旧 CD 与“弹药空余”的注释，使其反映背包战斗规则。

`StackMax`、`ConsumeStack` 和 `TryConsume` 同样保留。一次扣多少、实际能扣多少、是否从正数降为零，都在真正修改资源的方法中算清楚，再按该次变更发出事实事件。`TryConsume` 中的灵活判断、离场标记和排队调用移回关键词规则。现有 `CanAcceptMana` 可以继续读取消耗卡的真实存量：零份丹药拒收，空弹法宝仍可收灵。去掉对灵活私有标记的依赖即可，此处无需为 Lua 增设收灵前回调。

### 一次成功提交支付一发

1. 在本卡末格先检查原有发动条件和普通关键词的资源资格。失败沿用主关键词的失败处理。弹药为零只阻止发动；弹药规则不拦截收灵。
2. 复用主词 Lua 现有的 `CanCommitScan` 和 `OnScanCommitted`。前者可通过已注册的普通关键词查询资格，后者可将已成功的提交交给本卡关键词处理。`Amount.Lua` 或 `Consume.lua` 在这个时刻调用 C# 的扣弹或扣份方法。成功发动只支付一次，监听者读到已提交的余量。全场广播可能排队，不适合充当支付入口。
3. 主关键词仍按原有末格结果控制阶段。法术即刻结算或进入待发；法宝开启或延长一次激活期。`FaBao.CanRespond` 继续按激活状态决定是否响应。最后一发覆盖完整的一期，期间获胜三次即可兑现三次对应卡面效果。

例如 3 发法宝的首次激活、两次成功续期依次把余弹变为 2、1、0。下一次末格检查仍空弹时，法宝失活，留场卡保留已蓄灵元，未用的行额度可给右侧卡。此前若补回一发，下次末格照常检查全部条件。

### 灵活在最后一次效果结束后请求离场

扣至零时发布资源耗尽。离场另有合适的时机：即发法术在本次结算结束后，待发法术在直击、对拼完成或待发取消后，法宝在最后一个激活期结束后。`Flexible.lua` 在相应的本卡回调检查余量与阶段，仍耗尽才请求通用移除。若已补弹，则按当前余量继续在场。

普通主动卡由 `Flexible.OnApply` 检查事件来源是否本卡，法宝通过本卡的 `OnPassiveDeactivated` 收尾。灵活使用卡牌 Action `RemoveCard(ctx, "Self", "Flexible")`。场地释放格子、重算在场 SP 后，实际生效的请求把原因交给既有 `OnLeave`；由关键词发出 `OnFlexible`。耗尽和等待离场均不另存卡牌标记。

### TCA 读卡实例，触发跟随实际发生的变化

| 策划入口 | 数据与时机 |
|---|---|
| 补充弹药 A、是否空弹 C、弹药耗尽 T | 补弹沿用已有目标选择。条件读取指定卡的余弹。C# 扣弹操作在弹药实际由正数降至零时报告耗尽，主体为该卡及持有者。 |
| 消耗时 T、消耗耗尽 T | `TryConsume` 按实际扣份提交报告“消耗时”，保存扣除量和扣后存量。最后一份同时满足原有 `OnExhausted`。关键词、其他 Lua 脚本及既有批量扣除入口走同一次资源提交，避免扫描或战后提交重复广播。 |
| 是否还有消耗存量 C | 用现有 `CheckConsumeCount(ctx, card, "AtLeast", 1)` 配出直接可选的条件。份数大于零才成立，给普通法宝补弹不会增加物品份数。物品补货放在战斗外，本次不设计补货方式。 |
| 触发灵活时 T | 等场地确认**此卡因灵活**被移除后通知订阅者。来源取该卡，监听者看到腾出的格子与 SP。待发期间、仅请求移除、被其他效果移除均不触发。 |
| 有某关键词 C | 在模板中传关键词名与要检查的卡，Lua 复用现有 `card:HasKeyword(name)`。模板提供各词的策划变体，分类沿用 JSON 的 `APIType`。已有 `IsFabao`、`IsFaShu` 等入口继续可用。 |

内置关键词变体按现有注册名配置。主词有 `FaBao`、`FaShu`、`ZhaoShi`、`Passive`；附加词有 `Amount`、`Consume`、`Flexible`、`GongFa`、`Item`、`Wound`、`Armor`、`Shield`、`Shoes`。Mod 可把新词名传给同一个判断。保留既有脚本对字面关键词的检查语义，例如 `IsEquip` 检查 `Equip`，装备绑定关系继续由已有装备查询负责。

## Risks / Trade-offs

- **最后一发使法宝立即退场。** 在场、有效的法宝可能余弹已经为零。用“最后一发续期后响应效果，再到下一次末格失活”的跨扫描用例检查阶段与灵活规则。
- **补弹覆盖失败扫描，或同场部署免费装满。** 分别检查补弹前后点亮、该行右侧卡的发动和同一实例撤回再上场的余弹。
- **同步回调触发重复扣费或离场。** 让最终资源值在公开通知前可读，测试耗尽中补弹、待发取消和重复清理；每次真实耗尽只报一次，每次实际离场只报一次。

## 待发取消与移除原因

超时和败退都先清除原待发槽，再向该卡分派局部 `OnPendingCancelled`，取消本身不执行 Apply。整场结束时，在场卡的局部 `OnCombatEnd` 允许灵活法宝结束最后一个未到末格的激活期。通用离场请求将原因保存在场地队列中；重复请求由实际出队时的场地归属决定是否有效。外部效果先移除灵活卡，仅报告普通离场。伤势治疗沿用专用 Action 和原有治疗事件。

## Migration Plan

先调整现有消耗回归中“准备丹药战后补满”的预期，保留其耗尽、最后一击、实战回写和试战隔离断言。需要每场恢复的卡或 Mod 改配 `Amount` 和弹量上限，丹药、食物沿用 `Consume` 及已有库存。保留现有消耗事件和检查条件的语义。验证新弹药 TCA 以及无次数关键词卡的原有表现后，再同步玩法接口索引与主规格。
