# Design

## Context

`AssetMgr` 位于 Core，现有代码提供领域生命周期和路径辅助方法。Game 的 `NpcAppearanceData` 挂在 `NpcBioData` 下，目前保存出生时生成的身高。Godot 现有换装把前发 `hairFront`、后发 `hairRear` 等插槽归为一个部位。此次定义和实例采用逐插槽选择。仓库目前没有 `ModMgr` 实现。

## Decisions

### Core 按内容包加载 src

```text
[引擎随包资源] ------+
[游戏安装根/src] ----+--> [AssetMgr 索引和预载] --> [Game 外观目录] --> [NPC 实例选择]
[已启用 Mod/src] ----+                              ^
                                                    |
[包的 Data 配置] ------------------------------ [Game 读部件声明]
```

- 三种来源向 `AssetMgr` 提供相同的包 ID、读取入口和挂载顺序。游戏随包资源由引擎宿主适配，例如 Godot 提供项目打包资源，安装根 `src` 和 Mod 的 `src` 使用文件系统读取。安装根是可选的本地内容包，路径基于实际游戏安装目录。控制台可以使用文件读取入口或验证用的资源源。
- `ModMgr` 提供有序的启用包列表。一个 Mod 可以含 `src`、`Data`、`script`，分别放美术资源、JSON 配置和 Lua／C# DLL 扩展。Core 的 `AssetMgr` 只接收其中 `src` 的资源入口。此次先定义资源包列表的接入契约，由宿主提供显式的启用包列表验证挂载。完整 Mod 管理、玩法 Define 合并与 Lua／DLL 执行分别立项。
- 启动先确定资源源，`AssetMgr` 枚举各包 `src`，预载宿主已注册支持的资源类型。预载和缓存不需要 NPC Define 或插槽配置。资源按包 ID 和规范相对路径存储，同一份资源只读取一次。有序源和缓存按代切换，世界结束时释放；模板编辑器可独立准备同一组源。
- 默认挂载顺序是游戏随包资源、安装根 `src`、按启用顺序加载的 Mod。同一逻辑路径按后挂载的可用资源生效，未覆盖的资源继续来自前面的包。诊断保留命中的包及被覆盖的来源。挂载完成后 Game 再加载部件配置并建立索引，Godot 在展示开始前预先准备骨架、图集和所用的纹理。
- 逻辑引用从 `src` 根算起，`faces/ashen` 和 `src/faces/ashen` 统一为 `faces/ashen`。定义和导出都可直接写 `hair/jade`，不附带来源前缀。核心索引记录来源，使内容包的物理位置与资源引用解耦。对绝对路径、越界路径、同包内规范化后冲突的地址提供来源诊断。

### 卡图走外部 src，显示实例按需复用

- 开发时从仓库根读取 `src/cards/`，发布时从可执行文件旁的 `src/cards/` 读取，两处都通过文件系统加载。资源随发布目录分发。迁移 10 张独立 PNG，长剑卡在外部目录使用玉剑副本并保持原裁切和转置，原图继续用于旧素材预览。
- `card_visuals.json` 按既有卡牌定义 ID 关联 `cards/card_jin_slash.png` 等短地址。Core 管理已解析来源和预载内容，Godot 按来源和内容版本共享解码纹理。卡库、背包、待发、对拼和详情通过统一的卡图映射取图。移除对拼场景对旧位置 PNG 的直接运行时引用，保留缺图时的卡名和路径诊断。
- 复用现有 Godot Autoload 宿主保存一个客户端实例池，场景持有借用实例并在卡面移除、列表重建或退出时归还。池按资源或控件模板及实例类型分组。每组从 0 个开始按需创建，自动保留上限取同时借用的历史峰值。可设置每组硬上限，下降时立即裁减空闲实例，0 表示归还即释放。池在进程退出时释放空闲实例。
- 卡库的卡面控件进入池，归还时解绑旧卡号、纹理和交互状态，再由下一次借用重新绑定。Spine 演员归还时清理衣装、染色和姿态。卡面已由画布直接绘制的入口使用共享纹理。切换内容版本时按新版本解析纹理，旧实例归还后能解绑过期纹理。

### Game 每个组件对应一个插槽

```json
"Appearance": {
  "Face": "src/faces/ashen[#555555]",
  "HairFront": "hair/front/jade",
  "HairRear": "hair/rear/jade"
}
```

- `NpcDefine.Appearance` 是可选的字符串映射。键使用目标骨架的插槽 ID，输入匹配时忽略插槽名大小写，内部保存骨架中的实际 ID。每条部件声明明确一个目标插槽，使用它只替换这一槽。同一槽可有多款可选组件，同一款式若有前发和后发，则各自登记为独立组件、各自可配置。
- 继续用现有 `wardrobe.json` 提供内置款式信息。由 Game 的外观加载层把旧分组选项展开为逐槽部件，Godot 只应用对应插槽的附件。例如旧 `hair/jade` 的前发和后发分别迁为 `hair/front/jade`、`hair/rear/jade`。同一插槽内由动画选择的多个附件状态可随该组件保留。原来含 `none` 的插槽支持明确选空。既有 `Stance` 沿用单独的待机动作选择语义。
- 外部部件声明由 Game 从启用包的 `Data/Appearance` 读取。它声明逻辑部件地址、标签、目标插槽、适用骨架以及指向 `src` 资源的图像引用。附件的尺寸、坐标和旋转使用该骨架的局部单位。若有同槽动作状态，可为各状态附各自的资源地址。外部 PNG 用 Core 的资源索引解析；Godot 负责图像解码、按声明挂到目标槽和绘制染色。只有当前包提供 `src` 时，也可以通过同路径图片替换已有组件的美术。
- 显式地址末尾可附六位 RGB `[#RRGGBB]`。省略色值或写空括号时使用原色。编辑器对未知插槽、重复插槽、非法语法提示字段错误。合法地址指向缺失或不兼容的资源时保留原始配置并报告，角色装配使用该槽的可用候选或既有展示回退。

### 实例保存选中的插槽值

- `NpcDefineMgr.ToBirthContext` 传入外观选择和模板身份，由 `NpcSystemBio.OnEntityBorn` 统一装配。性别与未知性别的现有规则用于选骨架。指定有效组件直接使用，缺项用独立于玩法的 `Rng` 在匹配该槽和骨架的预载候选中等概率抽一次。按固定顺序遍历插槽和候选。两名演示人物的旧预设写成明确的插槽配置。
- `NpcAppearanceData` 保存身高、骨架 ID、每个已选插槽的逻辑地址、解析到的部件来源和可选染色。来源用于复用同一份结果，缓存中的纹理和字节随宿主维护。沿用 `NpcBioData.Clone()` 并深拷贝插槽集合。

### 编辑器和试战复用装配规则

- 标准 JSON 进出 `NpcDefine.Appearance`。单槽编辑只写对应槽；预览缺项使用稳定的草稿种子，导出仍保持缺项。读取旧草稿和旧试战输入时，将 `hair` 等分组按旧款式及染色展开为对应槽；映射旧 `flame` 别名。已存在的新槽值优先。
- 开启试战时冻结双方预览外观，现有 `BattleParticipant.Appearance` 负责传值。普通案例由角色装配决定外观。在首帧发布前把实例结果复制到会话输入，观察器和重开使用同一份结果。
- 外部组件声明、参与的资源内容和启用包顺序纳入现有试战版本核查。相同路径被其他包覆盖时，即使定义未改也能识别版本差异。缺少素材时沿用已有展示回退，非人形仍走现有展示。

## Risks / Trade-offs

- 安装根或 Mod 可以提供同路径替换。稳定挂载顺序和来源诊断让内容作者可查清实际生效的文件。
- 独立插槽允许混搭前后发。已有演示角色通过逐槽写明原款式保留原组合，普通生成使用各自的候选池。
- 启动预载有时间和内存成本。共用同一来源的资源和基础纹理，染色变体按需准备，目录结束时释放资源批次。

## Migration Plan

1. 建立 Core 资源源和预载契约，验证三个来源及覆盖顺序。
2. 迁移正式卡图，接通 Godot 共享纹理和全局实例池，验证卡库刷新和跨场景归还。
3. 把 NPC 规则接到已准备的资源索引，展开内置部件和演示模板，兼容旧草稿及案例输入。
4. 让模板编辑器和观察器使用逐槽结果，验证外部资源替换、正式导出和试战重开。
