# Proposal

## Why

现有战斗由卡牌独立冷却与集中灵元池驱动，卡组位置不能表达二维布局带来的出招节奏和资源分配。改为功法背包逐行扫描，使卡牌形状、摆放位置和灵元随机落点共同影响发动机会，同时保留待发槽与现有拼点关系。

本变更为讨论草案，已纳入 2026-10-14 用户对 A–I 的反馈。已确认的骨干规则写入 specs，算法预留、少量边界及后续卡牌设计见 `design.md`；本次只更新规划文件。

## What Changes

- **BREAKING**：卡牌 Size = 占用 SP 数量 = 实际占用背包格数 = 激活所需灵元总数；元素种类要求及特殊效果交由后续卡牌设计细化。
- 角色一定有一个主功法。主功法本身也是 Card，固定占格；其配置及等级决定背包大小、有效格排布和自身固定位置，形成流派差异。副功法按普通 Card 处理，不自动增加第二个背包。
- **BREAKING**：灵元离开集中池，每个未分配灵元占一格；扫描时在需要且能接收该灵元的卡中选最近者，等距优先下左方，无可接收卡则原地保留。距离/平距的具体算法留独立函数接口。
- **BREAKING**：用自上而下逐行扫描替代每卡独立 CD，例如 10 Tick 一行；行内从左向右逐格处理，扫到卡的最后一个占用格时按当时资源判断。缺灵不消耗本行机会，继续向右；只有成功使用才占用机会，每行最多一张卡生效。
- 扫描使用产生的拼点数据进入原有待发槽；每次行切换尝试双方对拼，单方待发数据不能在该阶段转为直击。
- 每轮扫描完成只触发本方待发槽的强制结算，此时才考虑直击；不能强制清算对方队列或同步对方轮次。不同背包行数造成不同节奏，是有意设计。
- 剩余灵元跨轮保留，下一轮继续抽取并随机填入空格。空间不足按实际可生成数结算：计划 5 个、只有 2 空格时生成 2 个，也只扣对应 2 个的 MP。空格足够时，疏密主要改变随机分布；更多卡牌增加激活需求。
- 保留 SP 决定输赢；伤口不能放进空格时占用灵元所在格。设计保证 SP 容量不超过背包有效空间，不另设“背包满即失败”，也不改成 HP 清零即失败。

## Capabilities

### New Capabilities

- `combat-backpack`: 主功法固定布局、卡牌占格与 SP、位置灵元及跨轮/补充规则、伤势占用灵元格。
- `combat-backpack-scan`: 逐行扫描、完整扫描条件、资源分配和每行一次发动额度。
- `combat-contest-scheduling`: 待发槽入队、行切换对拼及轮末强制结算时机，复用现有胜负与伤害规则。

### Modified Capabilities

- `passive-card`: 移除规格中“主动卡继续走旧 CD 流程”的要求，接入扫描调度；具体被动与特殊卡效果纳入后续卡牌设计。

## Impact

- 数据层：`CardDefine` / `CardBaseData` 只有 Size、Cooldown、ManaCost，没有形状；`CultivationDefine` 没有背包；`NpcCardData.Field/Reserve` 只有卡牌 ID 列表，没有坐标。
- 战斗层：`CombatScene.Tick`、`CombatNpc` 的卡组/灵元/待发槽方法、`CombatCard` 生命周期需要改造；新扫描状态、灵元位置与卡牌已接收资源须归战斗实例持有。
- Lua 与内容：`FaShu`、`ZhaoShi`、`FaBao` 的旧计时/扣费/Ready 出手路径需隔离；核心先用最小测试卡验证。依赖 ManaPool、CD、线性索引的旧卡效果列出影响，具体替代玩法由后续卡牌设计调整，不要求本次全部等价迁移。
- 兼容：现有 `zhaoshi-rotation` 变更定义独立串行 CD，与新扫描调度冲突；本草案指出替代方向，不修改或归档他人的变更。多数战斗历史规格仅在 archive 内，不能伪造同名主规格的 MODIFIED delta；现有 `action-card` 主规格描述大世界行为卡，不属于此次战斗卡改造。
- 测试：扩展现有 `CombatTestRunner` 或同级可断言测试入口，覆盖二维占格、资源分配、扫描额度、拼点时机与 Lua 生命周期。
- 不包含 Godot 静态预览接线、拖拽 UI、美术、全量卡牌重设计和此次代码实施；后续卡牌内容调整不作为骨干方案定案的前置条件。伤势与固定布局的几何边界继续列在关注点中。
