# 防御拼点与卡牌形状设计

## Context

范围来自[提案](proposal.md)。`CombatNpc.ResolveContest` 在双方拼点值修正后比较点数，构造并入队伤害，然后广播 `OnContestOverflow`。`CardDefine.GetShape()` 只有专用测试可以取得非横条形状。模板编辑器从自己的数据目录读取定义，战斗装配从 `GameDataMgr` 读取定义。两条入口都会解析形状。

## Goals / Non-Goals

**目标**是让卡脚本继续使用现有出招接口，让特殊拼点规则由参与配对的卡牌 Keyword 各自处理。形状数据应从模板拖放一直传到战斗占格和扫描，沿用实例锚点作为位置来源。

**本期范围**是工程能力与独立验证样例。首版以固定朝向摆放。首批正式卡牌、同费用下格挡闪的点数量级及正式形状组合交给配表。费用与体积拆分、战斗部署和召回延续各自的设计进度。

## Decisions

### 卡牌 Lua 提交拼点，卡牌 Keyword 处理特殊结果

卡牌的 `Contest` 回调调用 `Attack` 或 `Defend` 决定本次拼点。装备招式通过现有读取入口取得绑定装备的战斗生效防御，作为格、挡、闪的点数。普通 Keyword 在卡定义的 `Keywords` 中声明，按照既有 Lua Keyword 注册入口挂接结算。例如招式卡配置 `["ZhaoShi", "Zhan"]`，卡脚本提交 `Zhan`，`Zhan` Keyword 在实际配对时处理斩对斩通吃。

```text
Card Lua --> Attack / Defend --> ContestData
                                       |
                                       v
                             Compare and compute base damage
                                       |
                                       v
                          Winner card Keyword --> Loser card Keyword
                                                           |
                                                           v
                                   Damage pipeline <-- Final damage
```

C# 在 `CombatNpc.ResolveContest` 保持既有待发、点数修正、比较和调度。攻击获胜时的初始伤害等于最终点数之差，防御获胜时为 0。非平局时，伤害入队前依次只向胜方、败方两张来源卡派发同一次配对结果。优先复用 `CombatCard.RunKeywordHooks` 的单卡派发机制。上下文提供本次双方来源、实际类型、最终点数、胜负和差值，另提供可修正的基础伤害。Keyword 负责自己的条件、伤害修正或奖励，C# 使用最终结果至多提交一次基础伤害，维持既有事件和 `Apply` 顺序。`OnContestOverflow` 仍在伤害入队后广播。

| Keyword 拟用 ID | 生效条件 | 结算 |
| --- | --- | --- |
| 斩 `Zhan`、刺 `Ci`、打 `Da` | 胜方实际使用该词对应的攻击类型，败方实际使用同一类型 | 基础伤害改为胜方最终点数 |
| 格 `Block` | 来源卡以格赢过敌方攻击 | 给自己添加等于胜出差值的单次全攻击拼点强化 |
| 闪 `Dodge` | 来源卡以闪赢过敌方攻击，或以闪输给敌方攻击 | 胜时调用 `Charge` 给自己整包充能胜出差值的基准 Tick，败时基础伤害改为对手的最终攻击点数 |

挡和射击使用基础结算。`Shield` 已是装备分类 Keyword。射击参与攻击对攻击时取差值，射击赢过闪时由败方的闪修改基础伤害。以攻击 6、对方 4 为例，射对斩是 2 点，射对闪是 6 点。平局、轮末单方待发以及两项防御配对都不产生格、闪奖励。充能后的扫描由原调度器处理。

格通过 `AddNpcBuff` 施加单次全攻击强化。该状态自己的 `ModifyContest` 匹配攻击拼点、增加点数并消费自身。通用的 `Attack_Changed_Once` 当前最多 99 层。为保留完整胜出差值，给格配置单独的单次数值状态，使用点数类型能表示的范围，保留通用 Buff 的既有上限。背包充能沿用现有基准 Tick 语义。

### 功法定义矩形，卡形由独立定义解析

正式功法在 `CultivationDefine.GetBackpackDefinition()` 的既有宽高、等级布局和主功法固定格入口上校验完整矩形。空 `ValidCells` 生成全部格子，显式列举时须与整个矩形一致。默认 5×5 与 (3,3) 继续有效。其他尺寸的主功法固定格以现有显式布局配置为准。

新增 `ShapeDefine`，通过 `Data/Shape` 加载 ID 和相对坐标 `Cells`，运行时沿用 `DefineMgrBase` 与 `GameDataMgr` 的定义加载方式。编辑器的 `TemplateCatalog` 同样加载此目录。两条路径共用形状解析和校验，向解析入口传入各自目录的查询来源。这样预检可以保持只读，也能同时支持不同数据目录。正式配表从卡定义独立引用形状，示例中的多个卡定义可共享一个 `L3`。

```json
{ "ID": "L3", "Cells": [{ "X": 0, "Y": 0 }, { "X": 0, "Y": 1 }, { "X": 1, "Y": 1 }] }
```

`CardDefine.GetShape()` 的正式分支解析必填的正数 `Size` 和可选的 `SizeShape`，`SizeShape` 缺省或为空字符串时生成横条。卡实例继续用 `CardBaseData.Shape` 保存解析结果的独立副本。实例公开位置映射到形状外接框左上角，校验、显示与摆放使用实际格集合。战斗按实际占格的行列顺序确定末格。程序生成卡和专用几何回归沿用现有内部几何入口。

### 编辑与运行使用同一份占格规则

`TemplateCatalog` 提供形状查询，模板预检、拖放草稿和卡片预览共同使用解析结果。预检定位卡定义 ID、形状 ID 或模板坐标。装配写入的实例占格与编辑器预览一致，战斗观察器继续使用快照中的实际占格。L 形卡放在 (2,4) 时占 (2,4)、(2,5)、(3,5)，(3,4) 可留给别的卡或灵元。

## Risks / Trade-offs

- **扫描时机随形状变化** → 以实际末格为准验证行额度，避免跨行卡提前发动。
- **空格碎片仍可能卡住两格伤口** → 沿用整张伤口寻找合法位置及失败诊断。验收样例用可容纳伤口的布局，并覆盖碎片导致放置失败的路径。
- **编辑器和战斗会分别加载定义** → 共用解析和错误条件，使用同一份数据同时验证编辑预检、正式装配与战斗快照。验证缺失或重复形状 ID 的诊断一致。

## Migration Plan

1. 将 C# 的同类全额分支切换为各 Keyword 时，给依赖旧通吃行为的正式卡补齐斩、刺、打对应的词，原卡脚本沿用。外部内容沿用原 `Attack`、`Defend` 调用，通过补词保留通吃行为。工程验收使用独立样例，旧轮测卡不作为本次配表来源。
2. 接通新的形状加载和解析入口，与后端和编辑器一起交付。旧卡保留 `size` 的已有拼写和默认横条。欠缺 `Size` 的外部卡定义须补上明确的正数。旧数据目录没有采用 `SizeShape` 时可按空形状目录读取。
3. 正式主功法如显式列出了有效格，需符合完整矩形。原有非矩形的专用几何回归保留独立入口，既有数据和测试文件按原用途保留。
4. 使用新的独立工程样例经真实模板生成链验收拼点 Keyword 与 3 至 5 格卡形。上线前先验收规则与接口，再安排首批正式卡牌和形状配表。回退到旧版本时，使用 `SizeShape` 的内容应一起回退，避免旧版本将异形按横条装配。
