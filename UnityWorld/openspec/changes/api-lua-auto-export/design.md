## Context

当前 `APIMgr` 通过反射扫描 `[APIFunc]` Attribute 注册所有 API 函数签名和执行委托。Lua 侧的包装函数（Action.lua、Condition.lua 等）是手写的，本质上是对同一份签名的冗余翻译。已有 `ExportDoc()` 方法证明运行时反射导出的可行性。

## Goals / Non-Goals

**Goals:**
- APIMgr 运行时自动生成 Lua 包装函数文件，按 APIType 分文件
- 新增 API 时只需写 C# `[APIFunc]`，Lua 侧零手动维护
- 生成的 Lua 可被 Init.lua require，与现有卡牌脚本兼容

**Non-Goals:**
- 不自动生成卡牌脚本（card_xxx.lua）—— Layer 2 不做
- 不改变 [APIFunc] Attribute 的定义格式
- 不处理 Keywords/ 目录下的手写 Lua

## Decisions

### 1. 生成触发时机：APIMgr.Init() 末尾

**选择**：在 `ScanHandlers()` 完成后调用 `ExportLua()`

**理由**：此时 `_apis` 字典已完整填充，反射数据 100% 准确，无需额外工具链。与现有 `ExportDoc()` 方案一致。

**替代方案**：
- Python 正则扫描 C#（脆性高，正则难处理多行 Attribute）
- Editor 菜单按钮（需跑 Unity 编辑器，CI 不友好）

### 2. 分文件策略：按 APIType 枚举值分

每个非 None 的 APIType 生成独立 `.lua` 文件：
- `Action.lua` ← APIType.Action
- `Condition.lua` ← APIType.Condition
- `Contest.lua` ← APIType.Contest
- `Aura.lua` ← APIType.Aura

APIType.None 和 APIType.Scale / Scope 如果存在则归入 `Other.lua`。

### 3. 生成模板区分

| APIType | 模板 |
|---------|------|
| Action / Contest / Aura | 设参 → Execute，无返回 |
| Condition | 设参 → Execute → return ctx:GetObject("Result")，且剔除名为 "Result" 的输出参数 |

### 4. 类型转换规则

| ParamDef Type | Lua 包装 |
|---------------|----------|
| Int / Float | `tonumber(x)` |
| String / Bool / CombatNpc / CombatCard / 其他 | 直接传 |

### 5. 可选参数处理

`?` 前缀的参数生成 `if x ~= nil then ctx:Set(...) end` 守卫。

### 6. 文件头标记

生成文件首行加 `-- AUTO-GENERATED by APIMgr.ExportLua(), DO NOT EDIT`，防止误改。

## Risks / Trade-offs

- **[风险] 启动时写磁盘** → 只在 Debug/Editor 模式下执行 ExportLua()，Release 构建跳过（或加 #if 条件编译）
- **[风险] 现有 Init.lua require 列表不匹配** → ExportLua() 执行后需确认 Init.lua 中 require 了新文件（如 Contest.lua），首次需手动加一次
- **[取舍] 参数命名不再 "友好化"** → 手写版用 `value` 替代 `HealValue`，自动版直接用 ParamDef Name。卡牌脚本调用方需适配（实际影响极小，模板已对齐）
