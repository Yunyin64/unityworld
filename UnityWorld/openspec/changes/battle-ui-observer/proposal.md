# Proposal

## Why

Godot 已引用真实 C# 模拟器，但当前战斗场景仍显示写死的背包、属性、拼招与战报，无法观察和验证实际战斗。需要在保持核心与引擎独立的前提下，接通可暂停、单步和重开的观察界面，并建立客户端卡牌素材库。

## What Changes

- 分成可并行的三条工作线：现有接口核对与接入验证、独立客户端控制与 UI、图片及动画素材补齐；只对真实依赖规定先后。
- 以现有控制台 `CombatTestRunner.RunBasicTest` 为首个真实案例：共享 `test_npc_a`、`test_npc_b` 源数据、世界/战斗种子 12345、阵营及装配顺序、5000 Tick 上限。Godot 与新增无画面验证入口共用引擎无关案例描述和装配逻辑，原控制台保留作兼容对照；核对实际加载数据哈希，避免输出目录旧数据造成差异。
- 提供案例信息、播放、暂停、单 Tick、重开当前案例和结算反馈；重开保留完整案例输入，不只保留种子。其他现有回归先区分可播放案例和仅控制台断言，不复制近似的客户端测试数据。
- 客户端以值快照绑定双背包、灵元、点亮、扫描行与独立轮次、HP/MP/SP/护盾、状态、待发及战报。已有事件不能完整描述的过程明确降级为原始日志，不伪造精确动画或重算战斗规则。
- 扫描采用参考图中横贯背包宽度的光线形式：蓝白色细亮芯与柔光从上向下随真实行进度扫过，双方独立运动，扫过时呈现物品受光与灵元激活反馈；实际资源转移、点亮和出招由核心状态/事件决定，光线不反向触发规则。
- 后端源码、JSON、Lua、工程和规则不变；图片路径、裁切、动画、UI 缓存、读取适配与验证代码都位于客户端。运行时只由会话控制器调用现有模拟生命周期，展示层不直接写入核心实体。
- 按 Card 定义 ID 建立外置图片映射和缺图台账，按实例 ID 区分战斗卡片。记录全部 88 种静态定义的状态和覆盖，避免重复生成同定义实例的图片。
- 首批范围已确认：10 张透明无文字卡图、5 张金木水火土灵元图标，共 15 张新增图片，复用现有玉剑图表示长剑。扫描光线及激活亮度由客户端表现脚本实现；其余卡图、UI 贴图、动作帧和特效图先列清单再逐批确认，本轮只更新规划，不生成素材。
- 实施时优先使用已连接的 Godot MCP 辅助场景操作、启动和读取调试输出，并单独取得实际画面及交互验证证据。

## Capabilities

### New Capabilities

- `battle-observer-session`: 与控制台案例输入对齐的会话、独立时钟、只读投影、事件记录、当前案例重开和清理。
- `battle-observer-ui`: 真实背包扫描战斗的观察界面、蓝白扫描光线、物品/灵元反馈、播放操作和可验证降级。
- `client-card-assets`: 客户端 Card 与配套灵元图标映射、素材覆盖清单、确认后生成与落盘、缺图回退。

### Modified Capabilities

无。现有 `combat-backpack`、`combat-backpack-scan`、`combat-contest-scheduling`、`combat-status-effects`、`npc-template-backpack` 的玩法要求保持原样；本变更仅消费这些能力。

## Impact

- OpenSpec 文档位于 `C:\Unity\Game\unityworld\UnityWorld\openspec\changes\battle-ui-observer`；实际目标客户端位于同一仓库外层 `C:\Unity\Game\unityworld`，不是另一个后端工程。
- 实施涉及外层 `scripts/client/`、`scenes/`、`assets/`、`docs/art/`、客户端验证目录，以及必要的 `project.godot`、`Xianxia.Client.csproj`、`README_GODOT.md`。
- `UnityWorld/Scripts/`、`UnityWorld/Data/`、核心/控制台工程及主规格均不在实施修改范围。核心接口缺口或已存在错误另行汇报，不借 UI 接入修后端。
- 复用 .NET 项目引用、现有贴图与 Godot 控件；不引入前端专用战斗规则、后端 Godot 依赖或资源字段。
- 首版完成口径：现有控制台默认案例与客户端输入及结果对齐、暂停/单步/当前案例重开可验证、蓝白扫描线与真实状态协调、后端受保护文件无改动、11 种卡定义和 5 种灵元均有可加载映射，其余素材有明确状态。全库图片全部生成不是首版完成的隐含条件。
