# 背包战斗旧机制迁移与模板装配设计

## Context

动机见 proposal.md。本文件基于 2026-10-25 工作区代码和本轮用户决策；下文的目标行为尚未实现，不把上一变更的测试结果当成本变更验收。

### 与现有规格的关系

- combat-backpack-scan 中“主动只能扫描”的表述改成扫描路径条件；法宝事件是明确的新机会来源。
- combat-backpack 的 Size 统一扩展至所有需要点亮的主动卡；形状由正式内容的 Size 自动派生。
- combat-contest-scheduling 的唯一槽、行边界对拼、本方轮末强制规则不变，扩展允许条件 Use 入槽。
- passive-card 的纯被动生命周期保留，调整混合卡互斥假设。
- keyword-system 新增组合机会契约。其旧主规格格式为 delta 头，且旧文档 hook 名称/调用先后与实际代码不完全一致；本次实现要统一适配已有约定并验证回调恰好一次，不能复制两套回调。同步前修整结构，禁止顺手重写无关主规格。
- zhaoshi-rotation 的旧串行 CD 方案仍与新扫描冲突，保留待重设计状态，不套用其未完成任务。

## Goals / Non-Goals

**Goals**

- 一份点亮真值、一份 Card 实例位置、一处受控主动 Use 入口。
- 准确区分真实时间、扫描进度、扫描机会和条件事件机会。
- 迁移现有数据与真实模板生成，测试能覆盖数据加载、实例绑定、Lua 条件、事件、拼点和伤口全过程。
- 将每项被拒绝的旧行为说明为废弃或待定，避免“能加载”被误认为“能运行”。

**Non-Goals**

- 不实现神修的移动、交换、部署、召回；不禁止未来玩家战斗外摆放。
- 不实现玩家配置 UI、生成 NPC 组牌算法、功法升级换布局政策、普通卡旋转、距离函数最终算法。
- 不扩大为所有历史卡效果重新设计；使用禁用机制的旧卡保留内容并阻止作为已迁移卡上场。
- 法宝弹药/次数没有在最终讨论中定案，本次不擅自启用、废弃或重新设计它们；依赖未支持次数行为的内容仍需独立处理。
- ApplyHeal、既有告警、Godot、美术保持后续事项。

## Decisions

### 1. 决策来源与实施默认值

用户已确认的规则见各 delta spec。特别保留以下纠正，避免重新回到曾讨论但被否决的方案：

| 主题 | 最终确认 | 不能采用的旧提议 |
| --- | --- | --- |
| 冻结 | 下次完整扫过即解除，无论满灵与否；不叠加，优先未冻结 | 轮末统一解冻、计时冻、必须拦下一次本来成功的出手才解冻 |
| 加速 | 整包双倍速，按时间，同类延时 | 对单卡加速、把加速等同一次性推进 |
| 充能 | 基准进度增加，不被加减速缩放，不扣速度持续时间 | 双倍速使充能翻倍、充能扫描行消耗速度时间 |
| 法宝 | 条件主动，可与法术 Keyword 并列 | 法宝全部改成普通扫描卡或免费被动 |
| Min/Max/ManaAdj | 废弃、保留、禁用 | 删除数据，或自动改造成新玩法 |
| 神修相关操作 | 待定、保留、禁用 | 标记废弃，或本次实现背包换装 |
| 坐标 | 1 起始、主功法 (3,3)、实例持有位置 | 主卡左上角、模板永久控制位置、用一维 index 判断空间 |
| 模板 | 可重复 key/value 列表，显式生成实例 | 字典去重、靠未配置卡自动找空位或进入候补 |
| 自动发牌 | 玩家/生成 NPC 的能力，模板禁用 | 全局删除功法解锁或装备附带卡机制 |

下文涉及 Tick 边界、事件队列、字段拼写和错误表现的选择为**实施默认值**，不是额外向用户宣称已经逐条确认的玩法。执行时如发现影响已确认规则的冲突，记录具体例子并处理，不再为等价命名或微小内部实现反复讨论。

### 2. 单卡冻结是独立标记

- 使用战斗实例上的冻结标记，不依赖 CDSpeed、旧 Phase 或持续时间。
- 所有主动 Use 入口查询同一个标记；被动和接收灵元不查询它。
- 扫描到卡最后占格时，先读取并处理冻结，再处理资源、行机会、待发检查。若进入此格时冻结，本次扫描必定不使用，随后解除；不能解冻后在同一格继续尝试扫描 Use。
- 已入槽卡受到冻结后，Apply 不因冻结失败，也不清除冻结。其下次完整扫描依然跳过并解冻。
- 目标选择先保持原效果候选范围，再优先未冻结卡；范围内全已冻结时无新增效果。不能把“优先未冻结”变成跨阵营或跨范围搜索。
- 多格回归保留“末格”语义，虽然正式卡本次全部横向。

**默认顺序**：冻结在某卡末格之前施加，则该次末格访问就消费冻结；末格之后施加，则等下一次完整扫描。解冻之后发生的新独立条件事件可重新检查主动资格；只禁止追补被跳过的扫描机会。

### 3. 扫描进度与真实时间分开

以当前基准 10 Tick/行、10 Tick/秒作为示例，保持基准行间隔配置可测试：

- 每个真实 Tick 按当前速度增加基准进度：正常 1、加速 2、减速 0.5、同时存在 1。
- 每行消耗 10 基准进度；采用可精确表示半速的整数细分单位或等价确定性表示，不截断 0.5，也不每行清空余量。
- 加速、减速在 CombatNpc/背包时间状态分别保存剩余真实 Tick，重复施加加时，不叠倍率。
- 充能只向基准进度增加数值，旧 Lua 参数若以 Tick 表达，10 Tick 充能仍等于基准一行。接口文档同时标明单位，避免把旧名称里的秒直接当 Tick。
- 每个真实 Tick 每种速度时长只扣一次；处理额外行和额外轮末不重复扣时。

示例：已积累 4/10 进度，半速下获得 10 进度充能，立刻可完成一行，仍剩 4/10；下一行按半速继续。获得充能的瞬间不减少加速/减速剩余时间。

**默认 Tick 边界**：Tick 开始时已有的速度效果作用于本 Tick 的自然进度，并消费一 Tick 持续时间；本 Tick 行内新施加的速度效果从后续自然 Tick 开始计时。避免同 Tick 下方卡施加 1 Tick 加速却还没产生进度就到期。充能则在当前扫描工作安全边界追加处理。

### 4. 多行推进不重入扫描

现有 CombatScene 的“先所有到点者扫描，再配对，再各自轮末”顺序需要保留，同时支持同 Tick 多行。

建议将一次完成行作为调度单位：

1. 真实 Tick 只更新一次角色、持续时间与自然进度。
2. 收集此时达到行阈值的存活参战者，按稳定角色 ID 顺序逐格扫描各一行。
3. 完成这批行后尝试对拼，再只强制这批中到轮末的角色自身剩余待发。
4. 统一处理本批伤害、伤口与败退，再换行；轮末所属存活者补灵。
5. 对仍有足够进度的角色继续下一批；没有足够进度则结束此 Tick。

充能事件只累加进度/排入扫描工作，不能在某卡 Apply 内递归调用 ScanRow。当前行必须扫完右侧剩余格子。两位同时到点者先完成各自这次扫描，防止注册顺序让一方抢先单独轮末直击。

**新组合风险**：条件法宝可能在抽灵、Use、伤害事件中触发并再次充能。为每个事件链记录来源，做重入与循环检测；异常循环应明确给出链路并中止该异常战斗，不能静默丢弃合法行、永远卡住进程或凭空添加玩法冷却。安全预算是诊断保护，具体阈值与数据压力测试一起确定。

### 5. Keyword 提供机会，统一入口决定能否 Use

不再将 FaShu/FaBao/Passive 作为排他卡类型，也不允许多个 Keyword 分别直接维护卡 Phase。

```text
Scan opportunity ----+
                     +--> Eligibility --> Commit one Use --> Pending / Apply
Event opportunity ---+
```

建议区分：

| 能力/状态 | 来源或职责 |
| --- | --- |
| 能否扫描主动 | 迁移后的扫描 Keyword；法术已确认，现有招式迁移按扫描路径处理而不恢复串行 CD |
| 条件主动机会 | 法宝 Keyword 与卡的事件条件定义 |
| 能否蓄灵 | 是否具有需要点亮的主动能力，而非 ScanActivatable 一个布尔值 |
| 被动回调 | 独立监听和生命周期能力，不与前两项互斥 |
| Use 资格 | 存活、满灵、未冻结、无本卡待发、如有拼点则槽为空 |

`ScanActivatable` 可作为迁移适配字段保留，但不能与 Keyword 长期形成两套可矛盾配置。旧测试内容通过适配或迁移到显式 Keyword 回归；正式内容由 Keyword 表达机会。Cooldown<=0 不再自动代表只有 Passive。

一次成功提交：先锁定资格和使用状态、结束本次点亮，再执行该卡的 Use 链；无拼点 Apply 一次，有拼点等结算 Apply 一次。失败不清点亮，不触发 OnUse，不占扫描额度。继续保留直接调用 Use/Contest 的保护，统一受控入口分别授权两种机会。

**拼点预判**：当前实现仅用存在 Contest hook 推断拼点，但旧法宝和辅助卡常有空 Contest 函数。不能因此让无拼点法宝被满槽挡住。实施时为迁移卡定义明确的拼点能力声明或等价可验证描述，不能执行一次有副作用的 Contest 来“试探”再回滚。字段名可实施时决定；必须测试空 Contest 的无拼点卡。

### 6. 事件上下文、去重与被动

- 原始事件上下文不可被监听卡的 CreateCtx 覆盖。事件携带事件 ID/链 ID、原施放者、原来源卡、目标等；新 Use 的来源是发动法宝，仍可读原触发事件。
- 统一 ILuaBindable 与 EventMgr 两通道的实际事件身份。同一事件对同一卡的多个条件最多成功 Use 一次；不能用事件名称作为永久去重键。
- 默认同一事件内同方卡按位置 Y、X、实例 ID 稳定处理；跨角色保持稳定角色 ID。多个候选法宝争夺唯一槽时可重放，列表注册顺序不隐式决定结果。
- 事件中的被动回调仍照常发生；条件主动只提交受控机会。保留旧生命周期必要效果，但不把 Passive.Start 的 Apply 当作绕过资源的主动 Use。
- 同一卡正在提交/执行 Use 时不能重入；链路内重复自触发需被识别，独立后续事件在重新满灵后仍可发动。
- 默认事件派生机会在当前效果完成的安全点依次处理，保证在扫描继续访问右侧格子前，其已完成的灵元移除等空间变化可见。
- 条件 Use 入槽不立即对拼，继续等行边界；若发生在本方已完成该次轮末强制处理之后，不倒回重跑那次轮末。以事件日志说明它属于随后等待状态。

### 7. AboveAll 与空间选择

正式入口是 APIDomainFunc 的 AboveAll，不是仅修改已弃用的 CombatBaseScope。

判定：`max(target.Y) < min(source.Y)`，不限列；按卡实例去重。来源卡自然不满足严格上方。主功法、伤口进入空间候选，具体效果决定接受性。

冻结的优先未冻结筛选发生在候选生成之后。加速/减速/充能的新目标是角色背包，不能把旧 AboveAll/All 选出的每张卡都当成一次背包效果，否则卡越多速度时间和充能量越多。

AboveOne、BelowOne、Adjacent 等仍有旧线性实现，本轮没有定案其二维语义；调用它们的未迁移内容要在兼容审计中列出，不能自动宣称 AboveAll 的迁移覆盖所有空间选择器。

### 8. 格上灵元操作

继续使用 CombatBackpack 的格子实体，不建立聚合池作为可支付真值。计数只用于查询。

| 操作 | 实际数量 | 副作用 |
| --- | --- | --- |
| Convert | min(非负请求, 合法候选格数, 非负 MP 空缺) | 移除所选实体，每个恢复 1 MP |
| ReduceMana | min(非负请求, 合法候选格数) | 移除所选实体，不改变 MP |

先按元素过滤，再将候选格按稳定行列排序后用场景 Soul/Rng 不放回抽样；每格等概率，不能先按元素种类等概率抽。结果包含实际坐标、元素、数量、MP 差额。

释放的位置立即可被后续抽取使用；扫描不会倒退重访。卡上点亮、卡牌占格、待发资源都不受影响。MP 变化事件沿现有管线发送，不能因为一次转换被拆成多格而无意重复触发多次“整次效果”事件。

### 9. 在既有数据上扩展，不另造正式内容体系

**功法**：在 CultivationDefine 和现有 Data/Practice/GongFa 文件补充宽、高，默认值 5、5。字段名建议 BackpackWidth/BackpackHeight。BackpackLevels 已存在，可保留为显式扩展/测试配置；正式旧数据不要求填写一大段 ValidCells/MainCardCells。解析后得到同一个背包定义。当前正式主功法固定中心 (3,3)，未来偶数尺寸或多格主功法的中心规则不在本次设计。

**形状**：正式 CardDefine 不必新增手写 Shape。Size n 派生相对横条偏移 (0,0)..(n-1,0)，这里的偏移为内部几何量，不是玩家坐标。所有旧 Size 0 定义明确迁移为 1，其他正 Size 保留。底层原有 Shape 几何能力可作为专用测试入口保留，不能让正式数据同时用 Size 和 Shape 任意冲突。

**位置**：新增/调整 Card 实例状态承载 Position；不要把实例位置存进共享 CardDefine。公开配置、实例位置、日志均为 1 起始坐标；内部数组允许 0 起始，但必须集中转换，不在各效果里散落减一。世界 Card 到 CombatCard 的复制必须包含位置。

**索引**：NpcCardData.Placements、CombatBackpack 的卡格映射如保留，只能从实例位置/形状派生。受控摆放原子更新实例与索引；失败不能留下两者不一致。主功法切换的未来操作不扩大本次范围。

**现有试验数据**：两份 BackpackTest.json 以及 bp_* Lua 可保留回归用途；不删除既有测试资产，不把演示继续绑在手工辅助函数而声称完成真实内容迁移。

### 10. 模板来源与实例绑定

NPC 来源要显式区分模板和非模板。NpcMgr.Assemble 可作为模板入口；Birth/其他生成流程保持原有来源策略。禁止通过“有无某个字段”碰巧决定是否自动发牌。

模板装配建议顺序：

1. 读取模板基础属性、主功法引用、位置条目和装备/功法属性绑定描述。
2. 为每条位置记录创建独立 Card，并保留条目序号到实例的绑定；同 key 不去重。
3. 将功法进度、装备属性绑定到已生成实例，不再调用会重复 GainCard 的入口；不发解锁子卡，不生成 FormList。
4. 从明确引用定位唯一主功法实例，检查 (3,3) 与尺寸。
5. 写入实例位置，派生背包占格并验证全部配置。
6. 验证通过才将该模板实例交给战斗。初始化失败需回收本次临时注册，不能污染全局 Card/Equip/GongFa 表。

以下只是拟定字段拼写的配置示意，不是第二套定义格式：

```json
{
  "MainGongFaId": "jin_fa",
  "InitCardPlacements": [
    { "Key": "jin_fa", "Value": { "X": 3, "Y": 3 } },
    { "Key": "card_jin_slash", "Value": { "X": 1, "Y": 1 } },
```

- 列表每项是一个实例，不是对已有同定义所有卡批量赋位置。

- 缺位置/越界/重复占格直接报配置错误，不自动挪位、不送候补。后续解锁与手动配置问题不是模板测试范围。

### 11. 兼容状态与旧内容迁移清单

| 类别 | 本次处置 | 验收要求 |
| --- | --- | --- |
| Freeze | 迁移为单卡标记 | 非 CD 目标也能冻结，优先未冻结 |
| Haste/Slow | 迁移为角色计时状态 | 不是按选中卡数量重复加时间 |
| Charge | 迁移为角色基准进度 | 无倍率缩放，不能推进旧卡 CD |
| FaShu/FaBao | 迁移为机会提供者 | 单独与组合均可使用同一效果 |
| ZhaoShi | 保持新扫描出手机会，关闭旧串行 CD | 空费用旧招式不得无条件免费使用；具体元素需求按内容迁移 |
| AboveAll | 二维判定 | 不受 Field 排序影响 |
| Convert/ReduceMana | 格实体操作 | 不触碰卡上点亮，不调用旧池接口 |
| Min/Max/ManaAdj | 废弃，保留并禁用 | 提供状态说明、装配诊断和运行防线 |
| Deploy/Recall/Displace | 待定，保留并禁用 | 标注神修后续；拒绝时状态不变 |

废弃字段/脚本不能靠注释就声称禁用。迁移数据应有可查询的兼容说明，注册入口/装配校验和运行入口保持一致。Lua 可以动态构造调用，静态字符串搜索只能辅助审计，运行防线仍不可缺少。

卡牌内容迁移优先使用原 ID 与原文件。冻结、加速、充能卡及长剑法宝等按已确认机制改写；例如金针依赖 ManaAdj，保留旧定义并标记不可用，不能擅自改成另一种奖励。现有元素 Buff 里随机加速某卡的逻辑也要审计，不能遗漏因不是 Card 脚本而仍使用旧对象。

资源费用保留既有元素设计，数量迁移至 Size；若旧卡为空、多元素比例或特殊需求无法明确推导，不猜成任意灵元。实现记录具体条目，先标记未迁移或在执行阶段处理内容决策。验收模板只引用已迁移可用卡。

## Risks / Trade-offs

| 风险 | 处理 |
| --- | --- |
| 事件与扫描都可 Use，旧入口保护失效 | 两种来源都走受控入口，共享状态提交，测试同一份点亮不能复用 |
| 空 Contest hook 被当成攻击 | 显式拼点能力或等价声明，覆盖满槽无拼点卡 |
| Keyword 误读事件归属 | 保留原事件，单独传监听/发动卡；用对手事件反例验证 |
| 充能触发抽灵再触发法宝形成环 | 队列化行推进、事件身份与循环检测；异常显式诊断 |
| 半速累计丢失小数、效果多扣时间 | 使用确定性进度表示，真实 Tick 只计时一次 |
| 解冻被缺灵或行额度早退绕过 | 末格冻结处理置于资格早退之前 |
| 旧卡选择器误把一次加速变多次 | 角色目标去重，逐个迁移旧调用签名和 Lua 包装 |
| 1 起始与旧 0 起始混用 | 单一转换边界、日志/模板一致，中心和边缘专项测试 |
| 同 key 卡或装备绑定串实例 | 保持列表条目身份，不转定义 ID 字典；重复条目验收 |
| 模板禁止发牌误伤其他来源 | 显式来源策略，非模板解锁回归 |
| 模板功法注册与卡生成重复 | 先实例化再绑定，失败回收临时注册 |
| 25 格不代表永远能放完整伤口 | 验证模板 SP 与伤口预留；极端碎片仍按既有设计保证报错，不偷偷放宽形状 |
| 修炼点数与背包等级未接通 | 本次正式默认 5×5，不声称已实现等级成长；保留明确测试配置 |
| 旧主规格格式妨碍归档 | 只在同步前修整 keyword-system 结构，保留已有内容，不扩大到全库 16 份 |

## Migration Plan

1. 固定当前工作区基线，保留前一变更的未提交实现，不重置、不删除 .cs 文件。新增测试围绕用户确认规则，不靠改断言掩盖回归。
2. 先完成 Card 位置、正式横条形状、默认功法尺寸和模板来源隔离，建立重复 ID 模板的可运行装配。
3. 建立统一机会入口和资源能力，再迁移 Keyword 与被动生命周期；新事件入口仍受资源和槽约束。
4. 实现冻结、时间倍率、进度充能与多行调度；再迁移相关 Lua 与元素效果，验证同 Tick 顺序。
5. 接通 AboveAll、格上转换/减灵，完善禁用与待定状态；逐项审计旧调用者。
6. 更新现有正式卡/功法/NPC 数据，以真实模板演示取代仅手工 bp_* 组牌的交付依据；保留专用几何回归。
7. 完成矩阵验证、构建、烟测、规格校验和实施记录。此时才可另行同步/归档，不将提案存在视为实现完成。

**回退策略**：按本变更的代码/数据 diff 回退至此前扫描核心；不回退到资源池/CD，不删除旧保留文件。数据与运行入口应同批切换，不能先放开旧卡再等以后补效果。保留原字段的兼容读取仅用于诊断/非模板路径，不能让同一正式模板两套装配同时生效。
