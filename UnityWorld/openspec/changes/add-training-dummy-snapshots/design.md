# 木桩模板与过程测量设计

## Context

现有模拟脚本通过 `NpcMgr.Assemble` 装配模板，逐步推进 `CombatScene`，已有种子、结束原因和数据指纹。其 `resourceTrace` 默认不开启，开启后在 0、250 的倍数及终局读取余额。终局的 `hpDamage` 按表现事件主体归到承伤者。要看修士在任意节点的输出，必须按攻击来源重新归属，并累计节点之间每笔结算。

## Goals / Non-Goals

策划维护一份测量清单。每条定义一个读数，LogMgr 在每个测量时点暂存读数，每场战斗结算后自动将该场条目写成一份 Markdown 文件。策划关掉模拟器，仍可打开某局查看过程，或按条目比较百场分布。木桩测自然输出，指定已有修士作对手即可观察受压过程。

```text
战斗中　50 Tick 伤害输出  ─┐
　　　　100 Tick 伤害输出 ─┼→ LogMgr 的本场快照记录
　　　　100 Tick 灵气消耗 ─┘             ↓ 本场结算
                               自动保存一场一份 .md
普通诊断日志 ──────────────────→ 控制台即时显示
```

## Decisions

### 木桩是一份能装配的角色数据

拟将 `training_dummy`（显示名「木桩」）按普通 `NpcDefine` JSON 放在项目的基准工具目录，由基准入口显式读取并传给 `NpcMgr.Assemble`。这样可沿用主功法及 SP 预检，也能避免世界随机模板池和普通全名单轮赛自动选中木桩。报告把这份独立文件也计入内容指纹。

| 模板项 | 配置 | 用途 |
| --- | --- | --- |
| 气血 / 气感 / 神识 / 体魄 | 10 / 10 / 10 / 10 | 开场 20 HP、30 MP、10 SP 上限，与基础修士的伤口阈值一致 |
| 主功法及位置 | 仅木桩专用白板主功法，5×5 背包，单格 (3,3)，修炼点 0 | 功法本身占 1 SP，开场占用 1/10 |
| 初始装备、其他卡与特性 | 空 | 木桩自身没有招式、待发攻击、护盾、反伤或自动治疗 |
| 每轮基础补灵 | 木桩实例专用属性覆盖 `ManaDrawCost = 0` | 木桩自身基础补灵不占盘、不花 MP，待测者照常补灵 |

拟新增同 ID 的功法定义与功法卡定义 `training_dummy_gongfa`。功法定义提供 5×5 布局和空解锁列表，卡定义采用 `GongFa`、`Passive`、单格、空费用。功法只提供背包与占格，没有属性加成、触发效果、战斗脚本或解锁子卡。NPC 模板草案如下。

```json
{
    "ID": "training_dummy",
    "DisplayName": "木桩",
    "InitStat": {
        "QiXue": 10, "QiGan": 10, "ShenShi": 10, "TiPo": 10
    },
    "MainGongFaId": "training_dummy_gongfa",
    "InitCardPlacements": [
        { "Key": "training_dummy_gongfa", "Value": { "X": 3, "Y": 3 } }
    ],
    "InitGongFa": [
        { "DefineId": "training_dummy_gongfa", "PlacementIndex": 1, "CurrentPoint": 0 }
    ],
    "InitEquip": [],
    "InitialTraits": []
}
```

模板的 `InitStat` 通过 `StatBlock.SetBase` 设置基础属性。实测把补灵量写在这里仍会开场抽 5 枚。因此基准入口在装配后、场景创建前，对木桩实例用已有的 `Stats.AddModifier` 和 `StatModifier.Override` 将补灵量设为 0；把该覆盖值随模板写入批次运行清单。选择普通对手时全用其自身属性。

以无盾木桩为例，两击各扣 10 HP，第一击留下 10 HP，第二击触发清零恢复并获得第一张伤口。体魄为 10，第二击没有超过体魄，按当前规则落入一格伤口，SP 占用从 1/10 变为 2/10。首次扣血在第一击，首次伤口在第二击。

### 一场在任何批次位置都能复测

建议在现有 `skills/combat-simulation/scripts/run.ps1` 加入显式基准模式，复用模板解析、场景推进、错误记录和输出路径。以下是**拟议用法**，工作目录为仓库根。

```powershell
pwsh -NoProfile -File skills/combat-simulation/scripts/run.ps1 -BenchmarkSubject roster_qu_ze -MeasurementPlan 'dummy-baseline.json' -Limit 250
```

默认对手为木桩，建议上限 250，未指定清单时加载随工具提供的默认清单。传入清单时按其中启用的条目采样，显式 Tick 必须在 0 与上限之间。复用 `-WorldSeed`、`-Seeds`，默认世界种子 12345、战斗种子 1 至 100，一种子一局，待测方先装配为 A 方。`-BenchmarkOpponent` 可指定已有模板。

现有轮赛批内共享世界，实例分配受前序局影响。基准模式按样本重建同一世界起点，先以逐样本独立进程复用单局执行路径，接受相应启动开销。固定世界种子和装配顺序，只改变战斗种子。批次开头冻结输入指纹，执行中发现文件或程序集变化时报错，避免一次汇总跨两个版本。某场失败继续其余种子，记录异常和阶段；单独使用同一战斗种子应重现该样本。

### 增加一条测量

每场记录是一组键值对，键是条目 ID，值是该场的一项数据。采集配置决定值从哪里来。定点条目在指定 Tick 结算后记值；首次事件条目在事件实际发生时锁定本场首次值，后续同类事件保留原值。以下是默认的三个测项。示例沿用待测者 A 的伤口视角，观察方属于配置。

```json
[
    {"id":"damageOut_50",  "side":"subject", "metric":"damageOutHp", "at":50},
    {"id":"damageOut_100", "side":"subject", "metric":"damageOutHp", "at":100},
    {"id":"firstWoundTick", "side":"subject", "metric":"firstWoundTick"}
]
```

添加已有指标只需在清单加一项，例如 `damageOut_150`。循环、资源等条目按需启用。首次伤口和首次扣血由指标自身定义触发事件，配置省略 `at`，每场各观察方各指标只允许一个首次值。预检定位重复键、与固定键重名、未知指标或角色、非法定点以及给首次事件配置固定 Tick 的错误。

### 用实际结算事实填充指标

从 `PreStart` 前开始观察，首次事件按实际结算顺序锁定，即使发生在两个采样节点之间也记录。`Start()` 返回为 Tick 0，之后每次 `Tick()` 返回先收齐当步结算，再写该时刻到期的条目。真实终局在收尾后、`Cleanup()` 前写终局条目。条目在一局内最多采一次。固定 Tick 条目与终局条目有不同 ID，即使同一 Tick 到期也各有一条。

| 建议字段 | 单位和口径 | 工程取数处 |
| --- | --- | --- |
| `damageOutHp`、`damageOutShield` | 从开场累计对敌扣血点数、被盾吸收点数 | `DamageResolved` 的 `SourceNpcId` 与 `TargetNpcId` 归属双方，分别累加 `HpDamage`、`ShieldAbsorbed`。沿用清零恢复前引擎记录的伤害，包含穿过零点的部分；自伤、无来源伤害不计对敌输出 |
| `roundsCompleted` | 完成本方背包扫描的轮数 | 逐次计入 `OnRoundEnd`。开场已进入第一轮时读数为 0；加速可让一个 Tick 内完成多轮 |
| `manaSpent`、`manaSpentByElement` | 已成功支付的灵元枚数及各五行枚数 | `CommitScanUse` 记录的 `CardUsed.Before` 是本次实付元素。分配、落格、剥离或被伤口替换各有自己的行为，不并入支付。后续通用费用也按实际支付的五行计 |
| `mpSpent`、`mpRecovered` | 从开场累计的 MP 实扣与实回点数 | `ChangeMP` 掌握有符号实变量，现有 `OnMPChanged` 未带该值。拟在提交处提供场景内只读观察，用负变化绝对值和正变化分别累计，初始赋满不算回复 |
| `firstHpLossTick`、`firstWoundTick` | 本人首次实际扣血、首次新增伤口成功落盘的 Tick | 前者按承伤者第一笔正 `HpDamage`；后者取首个含 `Wound` 的 `CardAddedToBackpack`。初始自带伤口属于模板起始状态。未发生为 null |
| `hp`、`mp`、`shield`、`spUsed` | 节点当时的点数 | 从双方战斗实例读取。期末余额用于解释累计量 |

例：某修士在 Tick 49 前累计完成 0 轮、实付 2 枚灵元、花费 5 MP。Tick 50 完成本轮、用卡实付 1 枚、下一轮补灵花费 3 MP，并在同一步回复 2 MP。该节点应读到 1 轮、累计实付 3 枚、累计消耗 8 MP，余额相对 Tick 49 减少 1。此例用于验收口径。

伤害、用卡、伤口复用已有表现事实。轮末与 MP 变动在场景内各取一个权威提交点，只抄录数值，不分派额外玩法事件、不取随机数。基准执行器每步只消费一次事实，再同时供逐局战报和快照使用，避免取走回放队列导致另一个统计者漏算。失败或清理均释放本场观察。另有在途提案调整补灵和费用规则，本方案按运行版本的真实提交取值，两项变更可独立验收。

### 战斗中采集，结算后自动导出 Markdown

LogMgr 拟提供独立的离线快照入口。每场维护按条目 ID 索引的值，定点读数在该 Tick 完成后写入，首次事件在第一次发生时写入。配置、单位和角色归属可由批次清单查阅。普通诊断沿用等级和 Tag 过滤，走控制台、普通日志文件和回调。快照入口直接接收读数，绕开 `Dbg`、`WriteConsole`、`History` 和 `OnLogEmitted`。即使关闭控制台日志或普通日志文件，快照仍完整。

每场正常结算时，先采终局条目，再由基准执行器调用 LogMgr 自动导出，最后清理本场。达到 Tick 上限或提前分胜负都走这条路径，无需等整批跑完。若运行异常，在可控的收尾阶段导出此前已完成的条目，单场结束键记录失败位置与失败原因类别，详细异常存入批次诊断。导出失败则在批次结果中记为失败并给出目标路径和原因。只有写入成功的完整报告才登记为可读文件。

建议默认落在项目目录 `UnityWorld/Reports/CombatBenchmarks/<批次ID>/<场次ID>.md`，也可指定持久化输出目录。每次运行分配独立批次目录，同种子复跑保留两次结果。以 UTF-8 写入同目录临时文件，完成后再改为最终文件名。模拟器关闭后可以直接用 Markdown 阅读器打开。

**单场 Markdown 完整示例**

| 条目ID | 值 |
| --- | --- |
| seed | 1 |
| NpcA | roster_qu_ze |
| NpcB | training_dummy |
| damageOut_50 | 12 |
| damageOut_100 | null |
| firstWoundTick | 75 |
| FinsihTick | 75 |
| Finishreson | AllDefeated |

文件内容只有上述两列表格。前三行是战斗种子和双方模板 ID，中间按配置顺序列启用的测项，最后两行是实际结束 Tick 和结束原因。键拼写沿用约定，正常结束原因取引擎返回值。真实零值写 `0`；未抵达的定点、整场未发生的首次事件均写字面量 `null`。例中 Tick 50 已输出 12 点，第 75 Tick 首次出伤口并结束，因此第 100 Tick 的输出无值。标题、说明、单位、独立状态列和复现元数据均不属于单场表格。

批次清单保留模板与程序集指纹、实例覆盖、种子顺序及测量清单。现有方案的批次 JSON 记录每份 Markdown 的相对路径和汇总统计。每场 Markdown 独立可读，汇总可从同批 Markdown 和清单重建。

按对手和条目 ID 汇总，只用到达该时点的成功局计算该项均值和分位数。分位数采用最近秩，排序后取第 ⌈p×n⌉ 项。成功且终局恰落在节点的样本计入该点，早于节点结束的局单列。失败场保留诊断读数，整场退出正式汇总。节点覆盖可核对为计划局数＝失败＋提前结束＋有效到达。首次事件按整场值汇总发生局数/成功局数，时间分布只取非空值。若需按节点分析，批次端从首次 Tick 和结束 Tick 推导；无人到达时比例和分布均为空。终点读数可按局追溯。

## Risks / Trade-offs

- **高输出构筑更容易提前结束。** 例如后段只剩 35/100 局，后段均值描述这 35 局。汇总并列展示覆盖数和终点，保留对测量窗口的解释。
- **木桩提供的刺激有限。** 依赖敌人出招、对拼或自身受击的构筑，在木桩上可能始终为零。用相同节点和种子另测指定对手，两类结果按对手分别查看。
- **累计和采样容易互相干扰。** 同一输入在密采、疏采、关闭快照三种情况下比对终局；密采与疏采的公共节点须逐项一致。
