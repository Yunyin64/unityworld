# 知识库生成规范（Write Agent 专用）

> 派生自 `ai-knowledge-md-architecture.md`（唯一权威源）。
> 本文档仅包含生成/写入 agent 所需的规范，权威源变更时需同步刷新。

---

## 0. 快速定向（读我先）

生成 agent 的任务：**将代码库知识提炼为结构化 MD 文档，存入 `.context/code/` 知识库，并更新文本索引。**

### 0.1 完整生成 = 哪些文档？

| 模块类型 | 必须产出 | 条件性产出（触发条件） |
|---------|--------|---------------------|
| infrastructure / game_foundation | `<name>.module.md`、核心交互 flow（≥1）、异常/降级 flow（≥1） | 核心状态 slice（若有状态）；persistence.slice（§10.2）；UI 章节/子模块（§7） |
| business/ | `<name>.module.md`、核心交互 flow（≥1）、异常/降级 flow（≥1）、核心状态 slice（≥1）、业务辐射面扫描（SPEC-business-module.md） | persistence.slice（§10.2）；`<name>.ui.module`（§7.4） |
| design_data/ | `profile.designdata.md`、`pipeline.designdata.md`、`coderef.designdata.md` | — |
| concept/ | `concept.<name>.md` | — |
| experience/ | `experience.<name>.md` | — |

### 0.2 生成执行流程（强制，禁止跳步）

```
【准备阶段】
Step 1: 输出规范加载确认 → 判定内容类型
Step 2: 按类型加载附加规范（§3.3）
Step 3: 加载对应模板 + Demo（§3.4）
Step 4: 执行 `svn info --show-item revision` 获取版本号
Step 5: 执行 KB 预扫描，输出预扫描结论（§3.5）← 开始生成前的最后一步

【生成阶段】
Step 6: 生成主 Module → 立即执行 §14.A 单文档自检
Step 7: 生成 P0 Flow/Slice（核心流 + 异常流）→ 每文档生成后立即执行 §14.A
Step 8: 生成 P1 Flow/Slice（周期流 + 持久化）+ UI 子模块（若触发 §7.4）→ 每文档后立即执行 §14.A

【收尾阶段】
Step 9: 执行 §14.B 整体自检 + §12 缺失内容追踪
Step 10: 执行 §14.C 索引更新（`--rebuild` 自动刷新 entry.md 和文本索引，无需 agent 手动操作）
```

**每步完成后再进入下一步；禁止"一次性全量生成后再自检"。**

## 1. 五层定义

| 层 | 文件后缀 | 核心职责 | 一句话 |
|---|---|---|---|
| Flow | `.flow` | 运行时动态行为链路（时序） | 管过程 |
| Slice | `.slice` | 数据结构与字段变化（状态） | 管状态 |
| Module | `.module` | 能力边界、对外接口/配置、内部组织 | 管边界 |
| Concept | `concept.` | 跨模块上位概念、分层认知与查询导航 | 管分类 |
| Experience | `experience.` | 跨模块组合、选型与落地经验 | 管组合决策 |

## 2. 内容优先级原则（强制）

**知识库的双重目标（强制，贯穿所有文档类型）**：

1. **快速整体了解**：读完一篇 Module 文档，能一眼看懂模块职责边界、对外接口、配置路径、总体架构。
2. **代码细节快速导航**：无需 grep 全项目，能从文档直接跳转到任意功能的实现文件和关键函数。

**两个目标缺一不可。** 没有代码定位锚点的架构描述是"空中楼阁"；没有架构框架的代码清单是"零件堆"。

**知识文档的核心目标：让 agent/开发者知道"怎么用、怎么配、去哪改"；能根据异常信号快速定位问题；理解系统运作原理以便做设计决策。**

优先级从高到低：

1. **使用与配置指引**（最高优先级）：怎么调用、怎么配置、配置文件在哪、新增功能时该改哪里。必须给出可直接操作的样例和文件路径。
2. **对外接口与对外配置**：Module 必须详细列出可调用的函数/类/命令和可修改的配置项，每个都附带最小使用样例和配置文件路径。
3. **异常定位与排障指引**：运行时链路（Flow）和状态字段（Slice）的首要价值是支撑 bug 定位——从错误日志/异常信号出发，沿链路逐节点排查，或在状态字段的写入/读取点间追溯数据流。必须确保每步都有代码定位锚点。
4. **架构与设计认知**：One-screen 架构、分层模型、概念定义，帮助开发者理解系统全貌、做设计决策时选对模块。

## 3. 生成前准备（强制四步）

### 3.1 输出规范加载确认

必须在回答开头输出本次加载的规范文件名：

```
[规范加载] SPEC-write.md
```

### 3.2 判定内容类型

根据目标文档将存放的目录，判定内容类型：

| 目标目录 | 内容类型 | 判定标准 |
|---------|--------|--------|
| `infrastructure/` | 基础组件 | 与游戏业务无关；其他行业（金融/互联网）也有同类 |
| `game_foundation/` | 业务组件 | MMO 相关，但玩家不直接感知；是玩法的底层支撑 |
| `business/` | 具体业务 | 玩家直接感知的玩法功能；有明确 UI 入口和业务闭环 |
| `design_data/` | 策划数据表 | 策划配置表三维文档（profile/pipeline/coderef） |
| `concept/` | 跨模块概念 | 跨模块上位认知与分类 |
| `experience/` | 经验教训 | 跨模块组合与选型决策 |

**路径隔离（强制）**：不同类别目录下的文档完全独立，即使名称相同也不可混淆：
- `.context/code/game_foundation/skill/skill.module.md` — 代码模块文档（Skill 系统的代码架构）
- `.context/code/design_data/status/skill.designdata.md` — 策划数据表文档（Skill 表的填表/校验/引用）

生成文档时，只关注本类别目录，不要因为在其他类别目录下看到同名文件就认为"已生成过"而跳过。

### 3.3 加载附加规范

根据内容类型追加加载：

| 内容类型 | 追加加载 |
|---------|--------|
| `business/`（具体业务） | `generator_pack/SPEC-business-module.md` |
| `design_data/`（策划数据表） | `generator_pack/SPEC-design-data.md` |
| 涉及策划配置数据定位 | `generator_pack/GUIDE-design-data-location.md` |

**输出本次加载的完整规范文档清单，确认无遗漏后再继续。**

### 3.4 加载模板与 Demo

必须按顺序加载：

1. `.context/code/generator_pack/README.md`
2. 对应类型模板（按需选择）：
   - `templates/template.module.md`
   - `templates/template.flow.md`
   - `templates/template.slice.md`
   - `templates/template.concept.md`
   - `templates/template.designdata.md`
3. `generator_pack/demos/` 中对应类型 demo（仅用于风格与结构参考，**禁止复制 demo 的 ID**）

规则：
- 不允许跳过模板直接生成
- 生成结果必须保持模板结构完整

### 3.5 知识库上下文预扫描（强制，生成前执行）

加载完规范和模板后、开始写任何内容之前，必须先查知识库，建立对"邻近已有文档"的认知。

**Step A：查找已有相关文档**

```bash
# 用目标模块名/功能关键词查找邻近文档
powershell .context/code/generator_pack/kb_index_query.ps1 <module_keyword>
```

- 若已有同名/同功能文档 → **必须先读这些文档**，确认是"更新"还是"新建"
- 若查到邻近文档（如依赖关系中的模块）→ 加载 2~4 篇，理解该领域的命名惯例和已有描述深度

**Step B：查找本模块直接依赖的模块**

从代码中识别出本模块调用/依赖的其他模块后，逐个在 KB 中查询：

```bash
powershell .context/code/generator_pack/kb_index_query.ps1 <dependency_keyword>
```

目的：
- 获取依赖模块在 KB 中的正确名称（用于横向辐射模块章节填写，避免写源码目录名）
- 了解依赖模块的对外接口描述深度，避免在本文档中重复文档化已有内容

**Step C：输出预扫描结论**

预扫描完成后，输出一段简短结论：

```
[KB 预扫描结论]
- 本模块（<name>）在 KB 中的现有文档：有/无（若有，列文件名）
- 直接依赖模块在 KB 中的覆盖情况：
  - <dep_1>：已有文档（<doc_name>.module.md），将引用该文档术语
  - <dep_2>：无文档，将追加至 TODO-knowledge-gaps.md
- 发现的可复用内容：<简述，如"通用领奖流程已有文档，Flow 中引用即可">
```

**禁止行为**：禁止不做预扫描就直接开始生成；禁止为"已在 KB 中有完整文档"的通用机制重复写链路细节。

### 3.6 子 Agent 探查规范（主 Agent 派遣时强制）

当主 agent 将探查任务拆分给子 agent（如"去搞清楚 XXX 模块的持久化链路"），子 agent 必须遵守以下规范。

#### 探查流程：KB 优先四步（强制，与 ENTRY.md Q1~Q4 一致）

```
Q1. kb_index_query.ps1 索引查询（PowerShell，grep + 自动读 entry.md）
  ↓ 有命中 → Q2 加载 KB 文档
  ↓ [too_many] 关键词太泛 → 加入更精确关键词重试
  ↓ [no_match] 无命中 → 换宽泛短关键词重试；仍无 → Q3 代码搜索
Q2. 按需加载 KB 文档（2~6 篇）
  ↓ 已足够回答问题 → 直接进入 Q4
  ↓ KB 有轮廓但缺细节 → Q3 定向代码查询
Q3. 知识库不足时转代码库（定向原则）
  ↓ 按 KB 提供的路径线索定位，不做全项目搜索
Q4. 往返补充（发现新模块名 → 回 Q1 以新词重查）
```

**Q1 示例命令**：

```bash
# 按目标关键词查（返回命中目录的 entry.md 完整内容）
powershell .context/code/generator_pack/kb_index_query.ps1 <target_keyword>

# 多关键词 OR 查询（空格分隔）
powershell .context/code/generator_pack/kb_index_query.ps1 <kw1> <kw2>

# 关键词太泛或无命中的处理：
#   [too_many] → 加入更精确的关键词缩小范围
#   [no_match] → 换用更宽泛的短关键词重试
```

#### 禁止的探查行为

| 禁止行为 | 正确替代 |
|---------|---------|
| 收到探查任务后直接 grep 代码 | 先跑 Q1，KB 有结果则先读文档 |
| 在项目根目录做全量 grep/glob | KB 已有路径线索时，按线索定向搜索 |
| 探查某系统时跳过对应的 concept 文档 | concept 文档提供跨模块视图，优先加载 |
| 仅返回代码摘录，不说明 KB 已覆盖了什么 | 报告中必须区分"KB 已有"与"代码新发现" |

#### 子 Agent 探查报告格式（强制）

子 agent 完成探查后，必须以以下结构向主 agent 汇报：

```
【探查报告：<探查目标>】

1. KB 已覆盖的内容：
   - <文档名>：<已知道了什么，一句话>
   - <文档名>：<已知道了什么，一句话>
   （若 KB 无覆盖，写"KB 无相关文档"）

2. 代码新发现（KB 未覆盖的部分）：
   - <发现1>：<代码定位：相对路径 + 搜索关键字>
   - <发现2>：<代码定位：相对路径 + 搜索关键字>

3. 推荐主 Agent 加载的 KB 文档（可直接支撑生成）：
   - <doc_path>：<理由>

4. 建议追加至 TODO-knowledge-gaps.md 的缺口：
   - <缺口描述> → 建议目录：<directory>
```

**主 agent 收到报告后**：优先读"推荐加载的 KB 文档"，再结合"代码新发现"生成文档；禁止将子 agent 报告中"KB 已覆盖"的部分重复文档化。

## 4. 命名规则（强制）

- 主文档：`<name>.<category>.md`
- 子文档：`<name>.<subname>.<category>.md`

适用类别：

- `<name>.module` / `<name>.<subname>.module`
- `<name>.<flow_name>.flow` / `<name>.<subname>.<flow_name>.flow`
- `<name>.<slice_name>.slice` / `<name>.<subname>.<slice_name>.slice`
- `concept.<name>`
- `experience.<name>` / `experience.<name>.<subname>`
- `adr.<name>` / `adr.<name>.<subname>`

约束：

- `<name>` 必须使用英文小写 + 下划线（snake_case），禁止大写字母和驼峰（如 `Gameplay` → `gameplay`，`AutoChess` → `auto_chess`）
- 目录名与 `<name>` 保持一致，均为小写
- 名称必须是语义命名，不是源码目录命名
- `engine`、`server_common`、`game`、`mmo` 等目录词不应进入知识名，除非它本身就是稳定业务概念
- 代码归属与源码边界通过 `layer`、`domain`、`module_root`、`owners`、正文锚点来表达

## 5. Summary 与 SVN 版本号（强制）

每个知识文档的标题行之后，必须紧跟 summary 和 svn_rev：

```markdown
# <文档标题>
> summary: <≤150字的一句话简介，说明该文档的核心职责>
> svn_rev: <SVN修订版本号>
```

示例：
```markdown
# ArkPipe 网络组件
> summary: 进程间通信底座，负责连接生命周期、多线程收发、RPC注册分发。
> svn_rev: 52847
```

约束：
- summary 必须是完整的句子（含句号），不超过 150 字
- svn_rev 通过 `svn info --show-item revision` 获取
- 不允许省略（工具自动生成 entry.md 时依赖此字段）
- 更新文档时必须刷新 svn_rev 为当前版本号

**判定是否需要更新已有文档**：

```bash
svn log -r <doc_svn_rev>:HEAD <文档涉及的代码路径>
```

有相关提交 → 需要更新文档并刷新 svn_rev；无相关提交 → 文档仍然有效，无需更新。

## 6. 路径与代码定位规则（强制）

### 6.1 路径规则

- 知识文档中的代码路径必须是相对路径
- 禁止本机绝对路径（如 `S:/...`、`C:/...`）
- 禁止 `source_root` 字段
- 完整路径通过入口规则还原：`<project_root>/<relative_path>`
- `project.source_root` 仅允许存在于本地生成器配置，不进入共享知识文档

### 6.2 代码定位规则

- 禁止记录行号
- 必须记录"文件 + 文件内搜索关键字/函数名/结构名"
- Flow 文档：触发点必须包含可定位锚点（相对路径 + 文件内搜索关键字，函数名或事件名均可）
- Flow 文档：主链路中的每一个节点必须内联"文件 + 搜索关键字"，禁止将"主链路步骤"和"关键定位"拆成两个独立区块

## 7. UI 交互与表现文档要求（强制）

### 7.1 判定条件

以下任一条件成立即触发 UI 文档要求：

- 模块存在 VVM 视图类（继承 CViewBase 的类）
- 模块有 Panel 注册（`Panel2Prefab` / `Panel2Class`）
- 客户端有 `g_*Mgr` 管理 UI 状态（如红点、弹窗队列、面板开关）
- 模块的核心交互通过 UI 面板触发（如任务追踪栏、活动面板）

### 7.2 Module 文档中的 UI 章节

触发 UI 文档要求的 Module，**必须**新增"UI 入口与交互"章节，内容：

1. **主要面板清单**：Panel 名、VVM 类名、Prefab 路径、m_CreateArgs 关键字段、打开方式
2. **关键交互入口**：按钮/操作 → 触发的 RPC 或事件 → 预期响应
3. **UI 驱动的状态变更**：哪些操作通过 UI 触发而非代码直接调用

### 7.3 Flow / Slice 补充

- 若 UI 交互涉及独立状态流转（如任务完成弹窗序列、提交物品选择、追踪栏切换），**必须**产出对应 Flow 或 Slice
- 若 UI 交互是模块核心能力的一部分（如任务追踪导航），该 Flow/Slice 属于模块必需文档，非可选项

### 7.4 UI 子模块拆分条件（必须单列 `<name>.ui.module`）

以下情况**必须**将 UI 文档单列为子模块：

- 模块有 ≥5 个主要 UI 面板
- UI 交互是模块的核心能力（如任务追踪栏、蝶恋任务树）
- UI 交互流程独立且复杂（如多步弹窗、客户端-服务端协作的跳过流程）

### 7.5 game_foundation 模块的 UI 文档侧重

`game_foundation/` 模块的 UI 文档侧重"怎么用 UI 触发/查看"，不展开表现细节（动画/特效/布局）。表现细节属于 `business/` 模块的文档范围。

## 8. 完整生成要求（强制）

生成目标是"模块全闭环"，非"只出 P0 级别文档"。

### 8.1 Module 必须覆盖

1. 对外接口（函数/RPC/命令/回调）
2. 对外配置（配置表/配置文件/枚举映射）
3. 配置路径汇总表
4. 总体架构（One-screen）
5. 边界（In / Out）
6. 横向辐射模块
7. **UI 入口与交互**（若触发 §7 条件）
8. **关键实现定位**（文件 + 搜索关键字，按职责分组，见 §13.3 质量标准）
9. **诊断信号**（关键日志/错误模式反查索引，见 §13.3 质量标准）

### 8.2 Flow 必须覆盖

1. 核心交互流（P0）
2. 异常/降级/回退流（P0）
3. UI 触发流（若有 UI 且交互涉及独立状态流转，§7.3）
4. 周期性/定时流程（如日重置、周重置）
5. 客户端→服务端→客户端的完整请求链路

### 8.3 Slice 必须覆盖

1. 核心运行时状态（如状态机、任务进度）
2. 持久化状态（若有，按 §10 拆分为 persistence.slice）
3. UI 状态（若触发 §7 条件，如客户端缓存/弹窗状态/NPC 显隐缓存）
4. 共享/同步状态（如队伍进度、世界进度）

### 8.4 生成顺序

1. 主 Module（定边界）→ 立即执行 §14.A 自检
2. P0 Flow/Slice（核心交互 + 异常流程）→ 每文档后立即执行 §14.A 自检
3. P1 Flow/Slice（周期流程 + 客户端→服务端完整链路）→ 每文档后立即执行 §14.A 自检
4. UI 子模块（若触发 §7.4）→ 立即执行 §14.A 自检
5. 整体完成后执行 §14.B + §12 缺失内容追踪
6. 执行 §14.C 索引更新

### 8.5 交付标准

- 禁止交付 `partial` 状态而不标注 `missing_info`
- 文档标记为 `complete` 前必须通过 §14 自检清单
- 所有子模块文档生成完毕后才算模块整体 `complete`

## 9. 模块拆分规则

### 9.0 模块边界判定原则：功能内聚优先（强制，最高优先级）

**模块边界由业务/功能内聚度决定，不由编程语言、文件目录、进程位置决定。**

这是所有拆分判定的前提——在考虑"该不该拆"之前，必须先确认"边界在哪里划"。

#### 禁止的切割方式

| 禁止 | 错误示例 | 正确做法 |
|------|--------|--------|
| 按编程语言切割 | "C# 任务模块" + "Lua 任务模块" | 合并为一个模块，覆盖所有语言层 |
| 按文件目录切割 | `Assets/Scripts/Task/` 一个模块，`program/game/gas/lua/task/` 再建一个 | 同一功能的所有目录合并为一个模块 |
| 按进程/端切割 | "客户端 Task 模块" + "服务端 Task 模块" | 端到端作为一个模块，跨进程 RPC 链路在 Flow 中描述 |

#### 跨语言模块必须统一生成的触发条件

以下任一条件成立，必须将所有语言层合并为同一个模块文档，不得按语言/目录拆分：

- C# 通过 XLua 调用 Lua，或 Lua 通过 Luna 调用 C++，且这些跨语言调用是该功能的**核心链路**
- 客户端（GAC Lua / C#）与服务端（GAS Lua）通过 RPC 协作完成一个业务闭环
- 同一状态或数据在多个语言层之间流转（如 C++ 计算 → Lua 处理 → C# 展示）
- 修改某一语言层的逻辑时，必须同步理解另一语言层才能做出正确决策

#### 跨语言模块的文档要求

1. **总体架构（One-screen）**：必须展示完整的跨语言调用链，例如：
   ```
   C# UI → XLua → Lua GAC Mgr → Gac2Gas RPC → Lua GAS Handler → Luna → C++ Engine
   ```
   不得只写单语言层的架构，其余语言层用"…"略过。

2. **关键实现定位**：按**功能职责**分组，同一职责下并列多语言文件；**禁止按语言分组**（如"C# 部分"/"Lua 部分"）。
   ```markdown
   ### 核心处理逻辑
   - `dev/client/nshm/Assets/Scripts/Task/TaskManager.cs`  ← C# 层
     - 搜索关键字：`OnTaskComplete`
   - `program/game/gac/lua/task/task_mgr.lua`              ← Lua GAC 层
     - 搜索关键字：`OnTaskComplete`
   - `program/game/gas/lua/task/task_handler.lua`          ← Lua GAS 层
     - 搜索关键字：`Gac2Gas_TaskComplete`
   ```

3. **Flow 文档**：跨语言调用链路必须在同一个 Flow 文档中连续描述，不得把"C# 触发"和"Lua 处理"拆成两个 Flow。

4. **对外接口**：跨语言 binding 点（XLua wrap 函数、Luna binding、RPC 入口）必须作为对外接口列出。

#### 允许按语言/进程拆分的情况（满足以下任一）

- C++/C# 组件是通用框架，被大量模块共用 → 归 `infrastructure/`，不属于某业务模块
- 客户端与服务端逻辑完全独立，仅通过 RPC 松散连接，各自有独立的状态管理和业务闭环，且理解一侧不需要了解另一侧
- 跨语言 binding 层是通用基础设施（如 ArkPipe、XLua gen），不特属于某一业务功能

### 9.1 拆分判定

- 若无法给出"总体架构（One-screen）"，必须触发拆分
- 拆分方案：多个主模块（跨域职责混杂时），或同域多模块（职责过重时）

### 9.2 模块分层分类标准（强制）

新建模块时必须按以下标准判定目录归属：

| 层级 | 目录 | 判定标准 |
|------|------|----------|
| 基础组件 | `infrastructure/` | 与游戏业务无关；金融/互联网等其他行业也有同类组件 |
| 业务组件 | `game_foundation/` | 与MMO游戏相关，但玩家玩游戏不需要了解；是玩法的底层支撑 |
| 具体业务 | `business/` | 玩家直接感知的玩法功能；有明确的UI入口和业务闭环 |
| 策划数据表 | `design_data/` | 策划配置表的三维文档（profile/pipeline/coderef）；横跨多层，从数据视角服务策划/QA/程序 |

判定决策流程：

1. 这个组件是否只存在于游戏行业？如果不是（金融/互联网也有），→ `infrastructure/`
2. 玩家是否能直接感知并主动使用？如果有明确UI入口和业务闭环，→ `business/`
3. 是否是游戏特有的底层支撑但玩家无感知？→ `game_foundation/`

边界规则：框架归 `game_foundation/`，具体实现归 `business/`（如活动框架 vs 中秋活动）；`business/` 可依赖 `game_foundation/`，`game_foundation/` 可依赖 `infrastructure/`，禁止反向依赖。

### 9.3 拆分识别步骤

触发拆分判定后，按以下步骤从复杂模块中识别子模块边界：

1. **扫描职责集合**：列出该模块当前承担的所有职责（功能点）。方法：遍历所有对外接口、所有触发入口、所有配置表，归纳出功能清单。
2. **识别聚合域**：将功能点按"能共享同一 One-screen 架构"的原则聚合，每个聚合域即一个子模块候选。
3. **验证独立性**：每个子模块候选必须满足以下任一条件：有独立的触发入口 / 独立的状态管理 / 独立的配置定义 / 职责可用单一动词短语描述（不需要"和"连接两个不同职责）。
4. **确认边界清洁**：子模块间只能通过对外接口互调，禁止绕过接口直接访问对方内部状态。

### 9.4 拆分方案产出（人工确认后才执行）

识别完子模块后，必须先输出拆分提案，**等待人工确认，禁止在确认前开始生成任何文档**：

```
【拆分提案】
父模块：<parent_name>（放置于 <directory>）
触发原因：<具体原因，如"无法给出统一 One-screen，职责同时含 X 和 Y">

子模块清单：
1. <submodule_1>：<一句话职责> → 预计文档：module + <N> flow + <M> slice
2. <submodule_2>：<一句话职责> → 预计文档：module + <N> flow + <M> slice

主模块（索引模块）：<parent_name>.module（仅组织索引，不重复子模块接口）
```

### 9.5 主模块（索引模块）文档规范

父模块在拆分后变为**索引模块**，职责变为组织子模块关系，而非承载具体实现知识。

**索引模块必须包含**：

1. **组织说明**：说明本模块为何拆分、按什么原则划分子模块
2. **子模块目录**：所有子模块名 + 一句话职责 + 文档路径
3. **整体边界（In / Out）**：整体负责/不负责的范围（各子模块各自的边界在各自文档中详述）
4. **公共配置**（若有）：跨子模块共享的配置项；若各子模块配置独立，写"各子模块配置独立，见各子模块文档"

**索引模块不需要**：

- 对外接口详细说明（由各子模块文档承担）
- 独立的 Flow/Slice 文档（由各子模块文档承担）
- 横向辐射模块清单（由各子模块文档各自列出）

**索引模块格式示例**：

```markdown
# <父模块名>（索引模块）
> summary: <描述为何拆分、包含哪些子模块及其分工>
> svn_rev: <版本号>

## 模块组织
本模块因<原因>拆分为以下子模块：

| 子模块 | 文档 | 职责 |
|--------|------|------|
| `<submodule_1>` | `<submodule_1>.module.md` | <一句话> |
| `<submodule_2>` | `<submodule_2>.module.md` | <一句话> |

## 整体边界（In / Out）
- In：<整体负责的范围>
- Out：<整体不负责的范围>

## 公共配置（跨子模块）
<若无，写"各子模块配置独立，见各子模块文档">
```

### 9.6 子模块 Flow/Slice 系统完善引导

确认拆分方案后，按以下四步系统完善每个子模块的文档。

#### Phase 1：为每个子模块输出文档计划

在开始生成前，对每个子模块先输出计划，明确需要生成哪些文档：

```
【子模块文档计划：<submodule_name>】
- <name>.module.md：✅ 必须
- <flow_name_1>.flow.md：P0，核心交互流（触发入口：<入口函数/事件>）
- <flow_name_2>.flow.md：P0，异常/降级流
- <flow_name_3>.flow.md：P1，周期性重置流（触发：日重置/登录/周重置）[若有]
- <slice_name_1>.slice.md：核心运行时状态（<状态字段概述>）
- persistence.slice.md：有/无（触发信号：<具体信号，如"调用了 SetBitSet_At">）
```

#### Phase 2：按依赖顺序完善

若子模块间有依赖关系，被依赖的先完善：

- 判断方法：哪个子模块的对外接口会被其他子模块调用，该子模块优先
- 若无明显依赖，按"核心链路优先"原则排序（负责主要玩家交互的子模块优先）

每个子模块内部走 §8.4 的生成顺序（Module → P0 Flow/Slice → P1 → 自检）。

#### Phase 3：Flow 文档完善策略

每个子模块的 Flow 按以下顺序生成：

| 优先级 | Flow 类型 | 触发条件 |
|-------|---------|--------|
| P0 | 核心交互流 | 必须，覆盖玩家最常触发的主路径（含内联异常处理） |
| P0 | 异常/降级流（独立） | 异常路径复杂到需要独立描述时拆出 |
| P1 | 周期性/定时流 | 有日重置、周重置、定时器、登录触发等 |
| P1 | UI 触发流 | 有独立 UI 状态流转（§7.3）时生成 |

**Flow 覆盖完整性检查**（每个子模块 Flow 全部生成后执行）：

- [ ] 是否覆盖了该子模块所有的对外 RPC 入口（Gac2Gas / Gas2Gac 各方向）？
- [ ] 是否覆盖了该子模块所有的事件监听触发点（MsgHub_* / EventMgr 等）？
- [ ] 是否覆盖了该子模块所有的定时/周期触发点（定时器、日重置回调、登录触发等）？
- [ ] 每个 Flow 的主链路步骤是否都内联了代码定位（相对路径 + 搜索关键字）？

#### Phase 4：Slice 文档完善策略

每个子模块的 Slice 按以下顺序生成：

| 优先级 | Slice 类型 | 触发条件 |
|-------|---------|--------|
| P0 | 核心运行时状态 | 状态机、进度数据、计数器等；必须有 |
| P0 | persistence.slice | §10.2 任一触发条件成立时必须创建 |
| P1 | UI 状态 Slice | 有独立客户端 UI 状态（缓存/显隐/弹窗队列）时生成 |

**Slice 覆盖完整性检查**（每个子模块 Slice 全部生成后执行）：

- [ ] 是否覆盖了该子模块管理的所有持久化状态？
- [ ] 是否存在"隐式持久化"信号（UserPlayData 写操作/位集操作/DoAction 数据修改）未被 persistence.slice 捕捉？
- [ ] 每个状态字段是否有完整的定义点、写入点、读取点？

## 10. 数据结构与持久化拆分（强制）

### 10.1 复杂数据结构必须拆分 Slice

当 Module 文档正文中对某数据结构的描述超过 3 行，或需要表格列举字段/枚举时，即触发拆分。以下任一情况必须创建独立 Slice：

| 触发条件 | 说明 |
|---------|------|
| C++ 结构体/类有 ≥5 个字段 | 如 CoreGrid_t、CoreObject_t 等引擎核心结构 |
| 位掩码/枚举体系，常量 ≥4 个 | 如 Flag 常量、Barrier 类型分级 |
| 多层级联结构（链表/树/嵌套）需图示说明 | 如 Z 轴链表 |
| 磁盘→内存多步变换 | 如压缩→解压→反序列化→填充 |
| 字段含义不直观（位域打包、高低位复用） | 不文档化会导致误用 |

Slice 拆分后 Module 正文仅保留简要概述和指向 Slice 的引用。

### 10.2 持久化 Slice 触发条件

以下任一条件成立即触发 `<name>.persistence.slice` 创建：

**通用信号**：
- 模块有 MySQL/Redis 写操作
- 模块有跨进程缓存（如 SlaveDb LRU）
- 模块有 Pdef/序列化定义
- 模块有显式脏标记或保存链路

**项目特有信号（nshm）**：
- 调用了 `PlayProp():GetUserPlayData(key)` 的写操作（如 `SetBitSet_At`、`AddXxx` Action 等）——UserPlayData 是隐式持久化，无显式脏标记，通过 Action 系统和下线保存链路入库
- 调用了 `SyncUserPlayDataSingleToGac` 或类似同步函数——说明有客户端持久化状态同步
- 使用了 `SetBitSet_At` / `GetBitSet_At` 操作位集——位集是 UserPlayData 的常见持久化形式
- 通过 `g_ActionMgr:DoAction` 修改玩家数据——Action 系统可能触发持久化副作用

若模块无持久化需求（纯客户端逻辑/无状态），**不需要**创建空的持久化 Slice。

### 10.3 持久化 Slice 必须包含

1. **主存储**：存储类型（MySQL/Redis/文件/纯内存）、存储位置（表名/key模式/文件路径）、加载函数与时机、保存函数与脏标记机制、持久化时机（下线时/周期性/即时/事件触发）
2. **数据结构定义**：Pdef/Proto/结构体定义路径，说明是否自动生成、是否可手动修改
3. **脏标记与持久化链路**：脏位定义、置脏机制（setter 自动触发/显式调用/比对差异）、写库完整链路（如 GAS→DBProxy→MySQL）
4. **客户端同步**（如有）：同步方式、时机、代码定位
5. **异步缓存**（如有）：缓存实现、缓存内容、刷新策略、批量上限与降级、与主存储的一致性保证

### 10.4 通用存储通道简化规则

当模块使用以下通用存储通道时，持久化 Slice **不需要**展开完整链路，只需注明存储 Key 或 pdef 字段：

| 通道 | Slice 中应写 |
|------|------------|
| PlayDataMgr（服务器级） | 使用的 `EnumGameplay` 枚举值（如 `EnumGameplay.AchieveData`） |
| 角色级 UserPlayData | 使用的 Key 枚举及具体 Key 名（如 `EnumPlayDataKey.XXX` / `EnumDailyPlayDataKey.XXX` 等） |
| AutoSyncKV | 使用的 KV Key 名称（如 `Competition_Stage`）及 `bSave`/`bBroadcast` 属性 |
| MySQL 角色属性 | 使用的 pdef 属性名或 `CacheCharacterPropMapping` 中的属性类型 |

简化写法示例：

```markdown
## 主存储
- 存储通道：角色级 UserPlayData（日重置）
- 存储 Key：EnumDailyPlayDataKey.DailyOnlineTime
- 完整机制参见 concept.storage_layer.md → 通用存储通道 → 角色级 UserPlayData
```

**例外**：若模块对通用存储通道有特殊使用方式（自定义序列化逻辑、额外脏标记处理、非标准保存时机），仍需展开该特殊部分。

## 横向辐射模块

### 11.2 需列入的情况（以下任一）

- 本模块调用了其他模块的对外接口（函数/RPC/事件/命令）

- 本目录下的同模块子文档（目录内关联由索引自动建立）

### 11.4 特殊说明

1. `business/` 模块的业务域辐射面（任务/道具/红点等）按 SPEC-business-module.md §4.5 的辐射面扫描为准，此处不重复列举；但若引用了 `infrastructure/` / `game_foundation/` 层的具名模块，仍需在本节列出
2. 引用模块名应与知识库中的模块名一致；若知识库中尚无该模块文档，需按 §12 追加至 `.context/TODO-knowledge-gaps.md`
3. 引用代码位置遵循 §6.2 代码定位规则：相对路径 + 文件内搜索关键字/函数名，禁止行号

### 11.5 如何获取正确的 KB 模块名（强制操作步骤）

填写横向辐射模块清单前，对每个依赖都必须通过 KB 查询确认名称，**禁止凭直觉或源码目录名填写**：

```bash
# 1. 用依赖关键词查询（如函数名、管理器名、RPC 名等）
powershell .context/code/generator_pack/kb_index_query.ps1 <dependency_keyword>

# 2. 若查到结果，entry.md 路径中的目录名即为正确的 KB 模块名
# 例：命中 infrastructure/arkpipe/entry.md → 模块名为 arkpipe

# 3. 若查不到，换更精确的词或更宽泛的短关键词重试
powershell .context/code/generator_pack/kb_index_query.ps1 <broad_keyword>

# 4. 仍无结果 → 该模块尚未入库，使用语义命名（snake_case），并追加至 TODO-knowledge-gaps.md
```

**KB 模块名与源码目录名的典型差异**：

| 源码路径/调用 | 错误写法（源码词） | 正确写法（KB 模块名） |
|-------------|---------------|-----------------|
| `gas/lua/rpc/arkpipe_rpc.lua` | `arkpipe_rpc` | `arkpipe` |
| `g_AchieveMgr:OnAchieveFinished` | `AchieveMgr` | `achieve` |
| `EventFlowStateMachine` | `EventFlowStateMachine` | `eventflow` |

## 13. 质量门槛 DoD（强制）

### 13.1 Flow

1. 必须给出终态可校验断言
2. 主链路每个步骤都必须包含代码定位锚点（相对路径 + 文件内搜索关键字）
3. 触发点必须包含代码定位锚点（相对路径 + 文件内搜索关键字，函数名或事件名均可）
4. 步骤中若存在关键运行时日志（可用于验证该步骤是否执行、排查该步骤的异常），**必须**在该步骤内联 `日志关键字`，格式：`- 日志关键字：\`<log_keyword>\``；无日志的步骤无需此行

### 13.2 Slice

1. 至少列出 1 个写入方 + 1 个读取方
2. 必须按"状态字段"展开，且每个字段至少包含：
   - 定义/声明点：文件 + 类名（如有）+ 成员名
   - 写入点：文件 + 函数名（复杂逻辑可附简述）
   - 读取点：文件 + 函数名（复杂逻辑可附简述）

### 13.3 Module

1. 必须明确写出"对外接口"和"对外配置"两个维度：
   - 对外接口：函数、类方法、命令、RPC、回调、消息入口等调用面
   - 对外配置：协议表、注册表、模板表、配置文件、枚举映射、约定数据表等配置面
   - 若某一维度不存在，必须显式写"无显式对外接口"或"无显式对外配置"
   - 若模块通过配置向外暴露能力，配置视为 Public Surface，优先级等同于接口
2. 对外接口和对外配置都必须提供可直接使用的描述，至少包含：
   - 作用
   - 使用前置/配置前置
   - 输入输出或关键字段/取值
   - 最小使用样例或典型调用/加载链
   - **配置定义路径**（代码配置填相对路径；策划配置表填 `BookName_SheetName`，不加文件路径前缀，定位方式见 `GUIDE-design-data-location.md`）
3. 必须给出"配置路径汇总"表格（即使只有一行），列出本模块所有相关配置的定义文件路径和用途
4. 必须给出"总体架构（One-screen）"，让使用方一眼看懂核心运作原理
5. 若无法给出简明总体架构，必须触发拆分（多个主模块 或 主模块 + 子模块）
6. 若模块触发 §7 UI 文档要求，必须包含"UI 入口与交互"章节
7. **必须包含"关键实现定位"章节**，满足以下质量标准：
   - **覆盖范围**：总体架构中提到的每一个组件/职责，都必须在关键实现定位中有对应条目；不允许架构提到但找不到代码入口
   - **组织方式**：按职责分组（如"初始化/启动"、"核心处理逻辑"、"配置加载"、"RPC/事件处理"、"数据结构定义"），而非平铺文件列表
   - **每条格式**：`相对路径` + 至少 1 个可在文件内直接搜索的关键字（函数名/类名/变量名）
   - **必须覆盖的职责类型**（存在时）：

     | 职责类型 | 说明 |
     |---------|------|
     | 初始化/启动入口 | 模块的 Init/StartUp/Register 调用点 |
     | 核心处理逻辑 | 主业务函数/主循环/核心算法 |
     | 配置/注册表加载 | 配置读取、注册回调、表格加载的位置 |
     | RPC/事件处理入口 | Gac2Gas/Gas2Gac handler、MsgHub 监听注册 |
     | 关键数据结构定义 | 核心 struct/class 的声明文件 |
     | 异常/错误处理路径 | 降级逻辑、错误回调、兜底代码 |

   - **验证标准**：开发者拿到这份定位清单后，无需在整个项目中 grep，就能直接跳转到任意模块职责的实现

8. **必须包含"诊断信号"章节**（关键日志/错误模式反查索引），满足以下质量标准：
   - **格式**：表格，列：`日志关键字/错误模式` | `归属 Flow/位置` | `含义` | `接下来检查`
   - **来源**：汇总本模块所有 Flow/Slice 文档中内联的日志关键字；不另起炉灶，不重复解释链路细节
   - **覆盖要求**：模块产生的所有可用于排障的关键日志都应在此列出；以下类型优先级最高：
     - 模块初始化成功/失败的标志性日志
     - 主链路关键节点的日志（可用于确认"走到了这一步"）
     - 异常/降级路径的错误日志
     - 跨模块调用失败的日志
   - **"接下来检查"列**必须给出具体方向（字段名/Flow名/配置表/依赖模块），不允许写"查日志"、"排查问题"等空话
   - **若模块无关键运行时日志**（如纯计算模块），显式写"本模块无关键运行时日志"，不允许省略该章节

### 13.4 Concept

1. 必须包含：概念定义、为什么重要、核心组织结构（由 `concept_shape` 决定子模板）、模块映射、典型查询路径（决策表形式）、诊断信号映射（日志关键字/错误模式 → 归属层/实现 → 下钻目标）、常见误区、In / Out 边界
2. 不承载具体 Public API 明细，不替代 `Module / Flow / Slice`
3. 当文档主要回答"这套东西该怎么理解、怎么分层、先看谁后看谁"时，应建 `Concept`，不应伪装成 `Module`

### 13.5 Experience

1. 必须涉及至少 2 个不同模块的交互或选型

### 13.6 通用

1. 文档之间保持独立解耦，不声明相互关联关系（关联由索引自动建立）

## 16. 索引更新（生成后必须执行）

### 16.1 常用命令

```bash
# 全量重建（索引 + entry.md，约 1-2 秒）
python .context/code/generator_pack/kb_index_write.py --rebuild --root .context/code

# 全量重建（自定义参数：每目录至少50关键词，比例0.01，上限30万）
python .context/code/generator_pack/kb_index_write.py --rebuild --min-keywords 50 --token-ratio 0.01 --max-total-keywords 300000

# 只刷新 entry.md（不改索引）
python .context/code/generator_pack/kb_index_write.py --rebuild-entries --root .context/code
```

### 16.2 约束

1. 文档变更后执行 `--rebuild` 重建索引（全量重建约 1-2 秒，无需增量更新）
2. 索引输出到 `index/knowledge_index.txt`，entry.md 输出到各知识库子目录

### 16.3 关键词预算参数

`--rebuild` 支持以下可配置参数：

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `--min-keywords` | 30 | 每目录最少关键词数（保底） |
| `--max-total-keywords` | 200000 | 全局关键词总数上限 |
| `--token-ratio` | 0.005 | token→关键词提取比例 |

算法：每目录关键词数 = `max(min_keywords, int(目录加权token总量 × effective_ratio))`。当 `token_ratio × 全库token总量` 超过上限时，自动反算 `effective_ratio = max_total_keywords / 全库token总量`。

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `--min-keywords` | 30 | 每目录最少关键词数（保底） |
| `--max-total-keywords` | 200000 | 全局关键词总数上限 |
| `--token-ratio` | 0.005 | token→关键词提取比例 |

算法：每目录关键词数 = `max(min_keywords, int(目录加权token总量 × effective_ratio))`。当 `token_ratio × 全库token总量` 超过上限时，自动反算 `effective_ratio = max_total_keywords / 全库token总量`。

## 17. 构建方式（强制）

采用"人定边界，机做填充"：

1. 人工给出模块命题与边界（先主模块）
2. AI 产出 `Module` 文档（含代码定位与关系描述）
3. 人工确认后，AI 批量补子模块
4. AI 按优先级补 P0 Flow/Slice，再补 P1/P2 Experience

禁止"一次性全自动全量生成"。
