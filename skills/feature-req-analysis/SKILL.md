# Feature Requirements Analysis Skill

## 总体约束

- **只读阶段不得写文件**：Phase 1–2 全程 read-only，禁止提前创建输出文件。
- **证据必须精确**：所有代码引用必须包含文件路径 + 行号（或函数名），禁止模糊描述。
- **不得跳相**：必须严格按 Phase 1 → 2 → 3 → 4 → 5 → 6 → 7 顺序执行，前置 Phase 的输出是下一 Phase 的输入。
- **估时单位**：0.5 人天为最小粒度，不得使用小时或其他单位。
- **文件命名**：所有输出文件使用 `analysis/` 子目录（相对于当前工作目录），自动创建。

---

## Phase 1 — 文档解析 & 需求提取

### 步骤

1. 解析文档，提取所有功能点，按如下三类归类：
   - **策划配置**：数值表、配置文件、gameplay 参数、关卡/道具/活动策划数据等
   - **客户端开发**：UI、特效、动画、本地逻辑、客户端状态机等
   - **服务器开发**：业务逻辑、RPC、数据库读写、定时任务、公会/社交系统等
2. 对于模糊功能点，优先根据上下文判断归类；若确实无法归类，标记 `[待确认]`。
3. 对每一条 **策划配置** 功能点，额外判断是否存在 **通用机制可行性**——即现有系统（如通用奖励、通用触发、通用条件判断、通用道具模板等）是否已能覆盖此需求，无需新增专用配置表。若疑似可通用机制实现，在 ID 后追加标记 `[⚠ 疑似可通用]`，待 Phase 2 核实。
4. **在主对话中直接输出**需求列表（不写文件），格式如下：

```
## 策划配置需求（N条）
1. [CONFIG-001] <功能点名称> — <一句话描述>
...

## 客户端开发需求（N条）
1. [CLIENT-001] <功能点名称> — <一句话描述>
...

## 服务器开发需求（N条）
1. [SERVER-001] <功能点名称> — <一句话描述>
...
```

### CRITICAL RULES — Phase 1

- 每个功能点必须有唯一 ID（前缀 CONFIG- / CLIENT- / SERVER-，三位数序号）。
- 不得合并语义不同的功能点；宁可拆细，不可合并。
- 不写任何文件，输出到对话即可。
- **每一条 CONFIG- 功能点都必须考虑通用机制可行性**，不得跳过此判断步骤。

## Phase 2 — 并行代码现状分析

### 步骤

1. 将三类需求分别交给 **3 个并发 sideAgent**，每个 agent 负责一类：
   - `sideAgent(name="code-config")` — 分析策划配置功能点（**必须调用 game-data-helper skill 读取实际表结构与数据**）
   - `sideAgent(name="code-client")` — 分析客户端功能点
   - `sideAgent(name="code-server")` — 分析服务器功能点
2. 每个 sideAgent 的 prompt 必须包含：
   - 完整的功能点列表（从 Phase 1 输出）
   - 代码库根目录与目录结构说明（参考 project-introduction skill）
   - 分析要求（见下方模板）
3. 等待全部 3 个 sideAgent 完成后，汇总结果。

### sideAgent Prompt 模板（code-config 专用）

```
你是一个策划配置分析专家。请对以下策划配置需求逐条分析，判断现有配置是否已覆盖，以及是否可通过通用机制实现。

## 强制要求：使用 game-data-helper skill 读取数据
对每一条配置需求，你必须：
1. 调用 game-data-helper skill，查询与该功能相关的策划表（如奖励表、道具表、活动配置表、触发器表等）。
2. 读取并确认表的实际字段结构、现有数据行样例，作为判断依据。
3. **严禁**凭印象或文件名猜测表结构——所有字段描述必须来自 game-data-helper 的实际查询结果。

## 通用机制检查（必做）
对每一条配置需求，额外评估：
- 现有通用机制（如通用奖励 reward_define、通用触发 trigger_define、通用条件 condition_define、通用道具模板等）是否已能支撑该需求？
- 若已有通用机制可覆盖，标注 `通用机制可行: ✅`，说明使用哪张表/哪套机制，以及需要填写的具体字段。
- 若通用机制不足，说明缺口，标注 `通用机制可行: ❌`，并说明需新增什么字段或新表。

## 待分析功能点
[粘贴 Phase 1 的 CONFIG-xxx 列表，含 [⚠ 疑似可通用] 标记]

## 输出格式（每条）
[CONFIG-001] <功能点名称>
  状态: 已有配置 / 部分支持 / 需新配置
  game-data-helper 查询结果:
    - 表名: <table_name>，查询字段: <field_list>
    - 关键现有数据/字段: <摘要>
  通用机制可行: ✅ / ❌
  通用机制说明: <若✅，说明使用的表和字段；若❌，说明缺口>
  已实现部分: <仅状态为"部分支持"时填写，逐项列出已覆盖的子功能，注明表名+行ID或字段名>
  未实现部分: <仅状态为"部分支持"时填写，逐项列出未覆盖或缺失的子功能>
  证据来源: <状态为"已有配置"或"部分支持"时必填；格式：表名[行ID] 或 表名.字段名；禁止只写表名>
  备注: <补充说明>
```

### CRITICAL RULES — Phase 2

- sideAgent **必须并发**调用，不得串行等待。
- 每个 sideAgent 的 prompt 必须是**自包含**的，不依赖对话历史。
- 代码证据必须来自 **实际 Grep/Glob/Read 结果**，禁止凭印象填写。
- sideAgent 不得写入文件；所有结果通过返回值传回主 agent。
- **三个 sideAgent 均必须调用 game-data-helper skill**：code-config 查通用机制表，code-client 和 code-server 查与各自功能相关的配置驱动表；未提供 game-data-helper 查询记录的，主 agent 必须拒绝接受并重试。
- **配置机制/通用机制检查不可省略**：CONFIG- 需有 `通用机制可行: ✅/❌`，CLIENT- 和 SERVER- 需有 `配置机制已有: ✅/❌`，缺失视为不合格输出。
- **"部分实现/部分支持"必须分项说明**：凡标注为部分实现/部分支持的功能点，`已实现部分` 和 `未实现部分` 两个字段均不得为空，必须逐项列出，笼统填写"部分完成"视为不合格。
- **"已实现/已有配置"必须有精确证据**：代码证据必须精确到函数名（`function XXX()`）或行号；配置证据必须精确到表名+行ID（如 `reward_define[1024]`）或具体字段；仅写文件路径或表名视为不合格。

## Phase 3 — 分类汇总，输出三份 md 文件

### 步骤

基于 Phase 1 需求列表 + Phase 2 分析结果，创建以下三个文件：

#### `analysis/config-requirements.md`

```markdown
# 策划配置需求分析

| ID | 功能点 | 分类 | 通用机制可行 | 状态 | 相关表/字段（game-data-helper 确认） | 备注 |
|----|--------|------|------------|------|--------------------------------------|------|
| CONFIG-001 | ... | 可复用 / 需要新配置 | ✅ 使用 reward_define / ❌ 需新增字段 | ... | table_name.field | ... |
```

- **分类**：`可复用`（现有配置表/文件可支撑，只需填充数据）；`需要新配置`（需要新增配置表或字段）。
- **通用机制可行**：必须基于 Phase 2 game-data-helper 查询结果填写，不得主观判断。若标注 ✅，则该功能点优先走通用机制，无需新建专用表。
- **相关表/字段**：必须来自 game-data-helper 实际查询，禁止凭印象填写表名。

#### `analysis/client-requirements.md`

```markdown
# 客户端功能需求分析

| ID | 功能点 | 分类 | 配置机制已有 | 状态 | 代码证据 | 备注 |
|----|--------|------|------------|------|---------|------|
| CLIENT-001 | ... | 已支持 / 需开发 | ✅ 表名.字段 / ❌ | ... | file:line | ... |
```

- **分类**：`已支持`（已有实现，验收后可用）；`需开发`（需要新开发或较大改造）。
- **配置机制已有**：基于 Phase 2 game-data-helper 查询结果填写。若标注 ✅，说明该功能可通过策划填表直接生效，无需新增客户端逻辑，估时应相应降低。

#### `analysis/server-requirements.md`

```markdown
# 服务器功能需求分析

| ID | 功能点 | 分类 | 配置机制已有 | 状态 | 代码证据 | 备注 |
|----|--------|------|------------|------|---------|------|
| SERVER-001 | ... | 已支持 / 需开发 | ✅ 表名.字段 / ❌ | ... | file:line | ... |
```

- **分类**：`已支持`（已有实现，验收后可用）；`需开发`（需要新开发或较大改造）。
- **配置机制已有**：基于 Phase 2 game-data-helper 查询结果填写。若标注 ✅，说明该功能可通过策划填表直接生效，无需新增服务器逻辑代码，估时应相应降低。

### CRITICAL RULES — Phase 3

- 三个文件必须**全部写入**后再进入 Phase 4。
- 代码证据列禁止留空：若 Phase 2 无证据，填 `—`，不得留 `?` 或空白。
- 分类必须二选一，禁止模糊标注如"部分支持"——若有争议，按保守原则选`需开发`/`需要新配置`。
- `config-requirements.md` 的**通用机制可行**列和**相关表/字段**列禁止留空——未查询即填写视为无效，主 agent 须返回 Phase 2 补查。
- `client-requirements.md` 和 `server-requirements.md` 的**配置机制已有**列同样禁止留空；若确无相关表，填 `❌`，不得省略。

## Phase 4 — 逐点核验 & 修订

### 步骤

1. 对 Phase 3 三份文件中每一行功能点，**逐一重新验证**：
   - 重新 Grep 关键词，确认证据文件/行号仍然准确。
   - 检查分类是否与代码现状一致。
2. 发现不一致时：
   - 直接用 Edit 修改对应 md 文件中的行。
   - 在文件末尾追加 `## 核验修订记录` 章节，记录每处修改原因。
3. 核验完成后，在对话中输出摘要：
   ```
   核验完成：共 N 条，修订 M 条
   修订明细：
   - [ID] 原分类 → 新分类，原因：...
   ```

### CRITICAL RULES — Phase 4

- 每个功能点必须独立核验，禁止批量"确认无误"。
- 至少为每类（策划/客户端/服务器）各做一次 Grep 抽样验证。
- 本 Phase 不得新增功能点，只允许修订分类和证据。
- **策划配置类功能点的核验必须包含 game-data-helper 二次确认**：重新查询相关表的字段，验证 Phase 3 中填写的表名/字段是否准确；若发现偏差，修正并记录。
- **客户端和服务器功能点的配置机制判断亦须抽样核验**：从 CLIENT- 和 SERVER- 中各抽取至少 2 条标注 ✅ 的功能点，用 game-data-helper 再次确认对应表字段确实存在且语义匹配，避免误标。
- 若通用机制可行性判断在 Phase 3 中标注为 ✅，核验阶段须确认通用机制的字段**确实存在且语义匹配**，避免误判。

## Phase 5 — 实现方案设计 & 复杂度估时

### 步骤

1. 读取 Phase 4 三份 md 文件，筛选出所有 **`需开发`/`需要新配置`** 的功能点。
2. 为每个功能点启动一个 **sideAgent**（最多 3 个并发），每个 sideAgent 负责设计一个功能点的实现方案。
3. 每个 sideAgent 完成后，将方案写入 `analysis/plans/` 目录下，文件名为 `<ID>-plan.md`。

### CRITICAL RULES — Phase 5

- sideAgent 最多 3 个并发；如功能点超过 3 个，分批次并发执行，每批最多 3 个。
- 每个方案 md **由 sideAgent 自己写入文件**（sideAgent 需要有 Write 工具）——若 sideAgent 不支持写文件，由主 agent Write 工具写入。
- 估时必须有明确依据，禁止直接给整数人天（如"2人天"），必须说明拆分（如"0.5天配置 + 1天逻辑 + 0.5天联调"）。
- `需要新配置` 类别的功能点估时只评估**配置设计与填表工作量**，不含程序开发。
- **通用机制可行（✅）的 CONFIG- 功能点方案**必须优先描述如何套用通用机制完成配置，而非设计新方案；估时只计填表与验证时间，通常不超过 0.5 人天。

## Phase 6 — 功能排序、估时汇总 & 排期

### 步骤

1. 读取 `analysis/plans/` 下所有 `*-plan.md` 文件。
2. 建立依赖图，拓扑排序（被依赖的功能点排前）。
3. 按以下优先级规则二次排序：
   - **P0**：被多个功能点依赖 或 复杂度综合 ≥ 4
   - **P1**：独立功能点 且 复杂度综合 ≥ 3
   - **P2**：独立功能点 且 复杂度综合 ≤ 2
4. 假设单人执行，按排序生成甘特式排期表（以人天累加）。
5. 输出到 `analysis/schedule.md`：

```markdown
# 功能排期

- 客户端开发工作量：N 人天

- **合计：N 人天**

## 排期表

| 优先级 | ID | 功能点 | 估时 | 累计天数 | 依赖 | 备注 |
|--------|----|--------|------|---------|------|------|
| P0 | SERVER-001 | ... | 1.5天 | 1.5 | — | ... |
| P0 | CLIENT-002 | ... | 1天 | 2.5 | SERVER-001 | ... |
...
```

### CRITICAL RULES — Phase 6

- 策划配置项排期在最前，作为其他功能的基础。
- 排期表中 `累计天数` 必须正确累加（不考虑并行）。

## 全局 CRITICAL RULES

1. **不跳相**：任何 Phase 未完成时，不得开始下一 Phase。
2. **只写 analysis/ 目录**：所有文件必须输出到 `analysis/` 子目录，禁止修改项目源代码。
3. **Grep 优先**：代码搜索优先用 Grep；若 Grep 无结果，再用 Glob + Read。
4. **不捏造证据**：若找不到代码证据，如实标注 `未找到`，不允许推断或猜测路径。
5. **估时保守原则**：有不确定性时向上取整到最近 0.5 人天。
6. **game-data-helper 强制调用**：**三类功能点（CONFIG- / CLIENT- / SERVER-）均必须**通过 game-data-helper skill 查询相关策划表作为分析依据，**严禁凭印象或文件名猜测表结构与字段**；未经 game-data-helper 验证的分析结论一律无效。
7. **通用机制/配置机制优先检查**：在判定任何功能点「需开发」或「需要新配置」之前，**必须先确认现有配置驱动机制是否已能覆盖**（CONFIG- 查通用机制表，CLIENT-/SERVER- 查对应配置驱动表）；只有明确配置机制无法覆盖后，才可标注「需开发」/「需要新配置」。过早标注「需开发」视为分析失误，需在 Phase 4 核验时纠正。
6. **sideAgent 并发上限**：全程任意时刻最多 3 个 sideAgent 并发。
